Node.js 与全栈基础 ​

本页对应 JD 要求 B9（Node.js / 服务端基础，出现 4 份：#1 星河视控、#4 中科创达、#6 鹏业软件、#10 欣农互联）、A4（工程化工具链） 与 模块 12（全栈与后端协作，#4 #10）。目标是把 Node.js 从"了解"升到"能读懂、能写最小服务 / BFF / SSR"：理解事件循环与异步模型，会用核心模块与中间件框架，能跑通一个最小 HTTP 服务，并在面试中把前端与 Node 的能力边界讲清楚。

一、Node.js 是什么：运行时，而非语言 ​

Node.js = V8 引擎 + libuv + 内置模块（C++/JS）+ 事件驱动。它把 JS 的运行环境从浏览器搬到服务端，因此 window/document 不存在，取而代之的是 process/global 与文件、网络等原生能力。

维度浏览器Node.js
全局对象window / documentglobal / process
顶层 thiswindowmodule.exports
模块规范仅 ESMCJS + ESM 双轨
I/Ofetch/XHR、DOM 事件fs/net/http，无 DOM
并发模型单线程 UI + Web Worker单线程主循环 + libuv 线程池
定时器window.setTimeout全局 setTimeout（同签名）
C++ 能力无原生 addon / N-API / WASM

一句话：浏览器负责"渲染与交互"，Node 负责"I/O 与脚本"，二者共享同一条 JS 语言与事件循环思想。

二、事件循环与 libuv 阶段 ​

2.1 六大阶段 ​

libuv 的事件循环按固定顺序轮转，每个阶段维护一个回调队列：

  1. timers：setTimeout / setInterval 到期回调
  2. pending callbacks：上一轮延迟的系统回调（如 TCP 错误）
  3. idle / prepare：内部使用
  4. poll：等待 I/O，执行 I/O 回调，会在此阻塞（有 setImmediate 或到期 timer 时不阻塞）
  5. check：setImmediate 回调
  6. close callbacks：socket.on('close') 等

每个阶段之间，Node 会清空两个"插队队列"：process.nextTick 队列，以及 Promise 微任务队列。优先级是 nextTick > Promise 微任务 > 下一阶段回调。

js
console.log('1 script');
setTimeout(() => console.log('2 setTimeout'), 0);
setImmediate(() => console.log('3 setImmediate'));
Promise.resolve().then(() => console.log('4 promise'));
process.nextTick(() => console.log('5 nextTick'));
console.log('6 script end');

输出稳定为 1 6 5 4 ...，其中 2 setTimeout 与 3 setImmediate 的先后在主模块中不确定（受进程启动耗时影响），但在 I/O 回调内部 setImmediate 一定早于 setTimeout。

2.2 微任务与 nextTick 的差异 ​

  • process.nextTick 的回调属于 Node 私有队列，优先级高于微任务，递归调用会饿死事件循环（nextTick 递归可导致 I/O 永不执行）。
  • queueMicrotask 与 Promise.then 同属微任务队列，V8 统一调度。
  • 实践建议：不要用 nextTick 做需要排到 I/O 之后的逻辑，需要"本轮结束再执行"用 setImmediate。

2.3 单线程 ≠ 只用一个线程 ​

Node 的主线程（JS 执行）是单线程，但 libuv 维护一个默认 4 线程的线程池（可用 UV_THREADPOOL_SIZE 调整，最大 1024），fs、dns.lookup、crypto 等异步操作在这里执行。真正的 CPU 密集计算会阻塞主线程，需用 worker_threads 或 child_process。

js
// CPU 密集任务放 worker，主线程不被阻塞；heavy.js 内用 parentPort.postMessage 回传
const w = new Worker(new URL('./heavy.js', import.meta.url));
w.on('message', (r) => console.log('结果', r));

判断规则：.mjs 恒为 ESM，.cjs 恒为 CJS，.js 由最近的 package.json 的 "type" 决定（"module" 为 ESM，缺省/"commonjs" 为 CJS）。

js
// CJS 拿到 __dirname
const path = require('node:path');
const file = path.join(__dirname, 'data.json');

// ESM 等价写法
import { fileURLToPath } from 'node:url';
import path from 'node:path';
const __dirname = path.dirname(fileURLToPath(import.meta.url));
const file = path.join(__dirname, 'data.json');

3.1 package.json 的 exports 字段 ​

exports 是现代包对外的精确入口表，支持条件导出（import/require/node/browser/types）。

json
{
  "name": "my-lib",
  "type": "module",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs"
    },
    "./utils": "./dist/utils.js"
  }
}

坑：一旦声明 exports，未列出的路径不可访问（比旧的 main 更严格）；同时提供 import/require 两份产物时，容易出现 Dual Package Hazard——同一依赖被 CJS 与 ESM 各加载一份，instanceof 判定失败、状态不共享。解决：只发 ESM 或全程 CJS，必要时用 require(esm)（Node 20.17+ / 22+ 支持同步 require ESM）。

四、核心模块速览 ​

ts
import path from 'node:path';
import fs from 'node:fs';
import { EventEmitter } from 'node:events';

const p = path.join(process.cwd(), 'logs', 'app.log'); // path：一律用 join/resolve 拼路径
path.parse(p);                // { dir, base, ext, name, root }
path.resolve('a', '..', 'b'); // 归一化绝对路径

fs.readFile(p, 'utf8', (err, data) => { /* 错误优先回调 */ }); // fs：回调式
const data = await fs.promises.readFile(p, 'utf8');            // 或 Promise 式

class Order extends EventEmitter {}                            // events：观察者模式基石
new Order().on('paid', (id: number) => console.log('paid', id));
  • Buffer：Node 的二进制字节容器，继承 Uint8Array。Buffer.from('hi') 得到 2 字节；Buffer.alloc(8) 预分配并清零；buf.toString('utf8') 转字符串。fs 不传 encoding 时返回 Buffer。
  • stream：处理大文件 / 大响应的核心，Readable/Writable/Duplex/Transform。默认对象模式关闭，pipe() 自动管理"背压（backpressure）"。
  • process：process.argv（[node路径, 脚本路径, ...参数]）、process.env、process.cwd()、process.exitCode、process.nextTick。
js
// 大文件流式复制：不把整文件读进内存
import { createReadStream, createWriteStream } from 'node:fs';
import { pipeline } from 'node:stream/promises';
await pipeline(
  createReadStream('big.mp4'),
  createWriteStream('copy.mp4'), // 自动处理背压
);

五、异步编程演进 ​

错误优先回调 → Promise → async/await 是同一件事的三代写法：

js
// 1) 错误优先回调
fs.readFile('a.txt', 'utf8', (err, data) => {
  if (err) return console.error(err);
  console.log(data);
});
// 2) Promise 化
const readFile = promisify(fs.readFile);  // import { promisify } from 'node:util'
readFile('a.txt', 'utf8').then(console.log).catch(console.error);
// 3) async/await（Promise 语法糖，等待期间让出主线程）
async function main() {
  try { console.log(await readFile('a.txt', 'utf8')); }
  catch (e) { console.error(e); }
}

要点与坑：

  • await 会让出事件循环，因此是"非阻塞等待"，不是阻塞式 sleep。
  • 并行用 Promise.all（任一失败即 reject，快速失败）；允许部分失败用 Promise.allSettled；限并发用 p-limit。
  • Promise.all 返回顺序与传入顺序一致，与完成顺序无关。
  • 未捕获的 Promise 会触发 unhandledRejection；未捕获的 throw 触发 uncaughtException。生产环境应注册这两个事件做兜底日志并优雅退出，而不是继续跑在不确定状态。
  • 不要 await 在 for 循环里逐个串行（除非确有顺序依赖），大列表用 Promise.all：for (const id of ids) await fetchOne(id) 是串行，await Promise.all(ids.map(fetchOne)) 才有并发。

六、npm / pnpm 与包管理 ​

package.json 关键字段：

字段作用
dependencies运行时依赖，随包发布
devDependencies构建/测试工具，不随包发布
peerDependencies宿主提供的依赖（如 vue/react），库必备，避免多份实例

scripts生命周期脚本，pre/post 前缀自动挂载

  • semver：^1.2.3 允许 <2.0.0 的次版本升级；~1.2.3 只允许 <1.3.0 的补丁升级；精确版本不加符号。锁文件（package-lock.json / pnpm-lock.yaml）保证团队一致。
  • npm ci：按锁文件精确安装，比 npm install 快且可复现，CI 首选；要求 package-lock.json 存在。
  • npx：临时执行包，不污染全局；pnpm dlx 是等价命令。
  • pnpm：用内容寻址存储 + 硬链接/符号链接，同一版本磁盘只存一份，天然隔离幽灵依赖（node_modules 是符号链接结构）。pnpm workspace 搭配 workspace:* 协议管理 monorepo（见 pnpm workspace 与 Monorepo）。
  • .npmrc：可配置 registry、strict-peer-dependencies=true、shamefully-hoist=true（pnpm 兼容老依赖时的兜底，慎用）。

七、Express / Koa / Egg 对比 ​

框架中间件模型特点适合
Express(req, res, next)，线性逐个执行，错误中间件带 4 参生态最大、API 简单轻量服务 / BFF 起步
Koaasync (ctx, next)，洋葱模型，await next() 前后可包夹更纯粹，只提供请求响应抽象，靠社区中间件需要精细控制流程
Egg约定优于配置，controller/service/middleware/plugin阿里系企业级，内置多进程、加载器中大型团队规范项目
Nest底层用 Express/Fastify，装饰器 + DI架构最重，工程化最好中大型后端（见 Nest.js）

洋葱模型是理解 Koa 与 Nest 拦截器的钥匙——中间件像俄罗斯套娃，await next() 之前是"请求下行"，之后是"响应上行"：

js
// Koa 洋葱模型
app.use(async (ctx, next) => {
  const start = Date.now();
  await next();                       // 交给内层中间件
  ctx.set('X-Response-Time', `${Date.now() - start}ms`); // 内层返回后再执行
});
app.use(async (ctx) => { ctx.body = 'hello'; });
js
// Express 线性模型 + 错误中间件
app.use((req, res, next) => { console.log(req.method, req.url); next(); });
app.get('/user/:id', (req, res, next) => {
  if (!req.params.id) return next(new Error('bad id')); // 抛给错误中间件
  res.json({ id: req.params.id });
});
// 4 个参数才是错误处理中间件，必须放在最后
app.use((err, req, res, next) => { res.status(500).json({ msg: err.message }); });

八、用 Node 写一个最小 HTTP 服务 / BFF ​

8.1 原生 http：看清最底层 ​

ts
import { createServer } from 'node:http';

const server = createServer((req, res) => {
  const url = new URL(req.url ?? '/', `http://${req.headers.host}`);
  if (url.pathname === '/health') {
    res.writeHead(200, { 'Content-Type': 'application/json' });
    return res.end(JSON.stringify({ ok: true }));
  }
  res.writeHead(404).end('Not Found');
});

server.listen(3000, () => console.log('listening on http://localhost:3000'));

8.2 Express 版 BFF：聚合 + 裁剪 + 鉴权透传 ​

BFF 的职责是站在前端视角聚合多个后端服务、裁剪冗余字段、透传鉴权。

ts
import express from 'express';

const app = express();
app.use(express.json());

// 聚合：一次请求拼装「用户 + 订单数」
app.get('/api/overview', async (req, res, next) => {
  try {
    const headers = { Authorization: req.headers.authorization ?? '' }; // 透传鉴权
    const [user, stats] = await Promise.all([
      fetch('http://user-svc/users/me', { headers }).then((r) => r.json()),
      fetch('http://order-svc/stats', { headers }).then((r) => r.json()),
    ]);
    // 裁剪：只返回前端需要的字段，隐藏内部细节
    res.json({ name: user.name, avatar: user.avatar, orderCount: stats.total });
  } catch (e) { next(e); } // 交给统一错误中间件
});

app.use((err: any, _req: express.Request, res: express.Response, _next: express.NextFunction) => {
  res.status(err.status ?? 500).json({ code: err.code ?? 'INTERNAL', message: err.message });
});
app.listen(3000);

8.3 最小 SSR：模板字符串版 ​

ts
createServer((req, res) => {
  const html = `<!doctype html><html><body>
    <div id="app">${renderToString()}</div>
    <script type="module" src="/client.js"></script></body></html>`;
  res.writeHead(200, { 'Content-Type': 'text/html; charset=utf-8' }).end(html);
}).listen(3000);

// 真实 SSR 把这步换成框架 renderToString，并做「服务端预取 → 序列化注入 → 客户端 hydrate」
const renderToString = () => `<h1>SSR 首屏</h1>`;

真实 SSR（Vue createSSRApp + renderToString、React renderToString/renderToPipeableStream）就是把这一步换成框架渲染函数，并在同构时处理"服务端预取数据 → 序列化注入 → 客户端 hydrate"。

九、前端与 Node 的能力边界 ​

前端工程师掌握 Node 后，典型落点是：

  • 工具链：CLI、脚手架、构建插件、代码生成、Git hooks、发版脚本（见 CI/CD 与自动化发布）。
  • BFF 层：聚合/裁剪接口、SSR、埋点上报转发、鉴权透传。
  • 本地/脚本：批量改文件、抓取数据、监控告警脚本、数据分析脚本。

不属于前端主场的部分要如实区分：数据库与事务、鉴权体系、并发与分布式、部署运维、安全加固、性能容量规划。面试时的稳妥话术是"能独立写 Node BFF 与工具链，数据库/分布式等复杂后端与后端团队协作或按需补齐"，而不是硬说"我全都能做"。

十、常见坑速查 ​

坑现象解法
内存泄漏RSS 持续上涨全局事件监听未解绑、闭包持有大对象、无上限的 Map 缓存
CPU 阻塞接口卡死、心跳超时重计算移入 worker_threads，大 JSON 用流式解析
背压未处理内存暴涨 OOM用 pipeline/pipe 而非手动 on('data') 里 push
回调里抛错吞掉请求无响应error-first 必须 if (err) return next(err)
unhandledRejection进程崩溃或静默失败全局兜底 + 结构化日志 + 优雅退出
.env 未加载process.env.X 为 undefineddotenv/--env-file（Node 20.6+）
require 缓存改了配置不生效认识 require.cache，配置热更新需监听文件
未处理 SIGTERM部署时请求被硬切监听信号：停止接收新连接，等待在途请求结束

面试要点 ​

  1. Node.js 事件循环有哪些阶段？ 答：timers → pending → poll → check(setImmediate) → close，阶段间清空 nextTick 与 Promise 微任务，nextTick 优先级高于微任务。
  2. nextTick 和 setImmediate 的区别？ 答：nextTick 在本轮操作结束立即执行、优先级最高；setImmediate 在 check 阶段执行，需排到 I/O 之后用 setImmediate。
  3. CommonJS 与 ESM 的核心差异？ 答：CJS 运行时同步加载、导出值拷贝；ESM 编译期静态分析、导出实时绑定、支持顶层 await，__dirname 需用 import.meta.url 换算。
  4. Node 是单线程吗？为什么能高并发？ 答：JS 执行单线程，I/O 由 libuv 线程池与内核异步完成，主线程只跑回调，因此 I/O 密集型高并发能力强，CPU 密集会阻塞。
  5. 如何避免内存泄漏？ 答：及时解绑事件监听、避免闭包长期持有大对象、给缓存设上限与过期、定期用 heap snapshot 对比排查。
  6. Koa 洋葱模型和 Express 中间件的区别？ 答：Express 是线性 (req,res,next)，Koa 用 async/await 包夹，await next() 前后可分请求下行与响应上行。
  7. BFF 解决了什么问题？ 答：为前端聚合多后端接口、裁剪冗余字段、统一鉴权与错误处理，降低前端联调成本并隐藏后端细节。
  8. async/await 是阻塞的吗？ 答：不是，await 让出事件循环，等待期间可执行其他任务，本质是 Promise 语法糖。
  9. pnpm 相比 npm 的优势？ 答：内容寻址存储 + 硬链接，磁盘更省、安装更快、天然隔离幽灵依赖，配合 workspace 管理 monorepo。
  10. 前端全栈能覆盖到哪一层？ 答：工具链、CLI/脚本、BFF/SSR 可独立负责；数据库、鉴权体系、分布式与运维属后端主场，协作或按需补齐。
