数据库与 BFF ​

本页对应 JD 要求 B4（WebSocket / 实时数据 / 接口联调 RESTful，5 份）、B5（HTTP 协议 / 请求层设计，5 份） 与 模块 12（全栈与后端协作，#4 中科创达、#10 欣农互联）。前端转全栈最容易踩的坑不在语法，而在数据从哪来、怎么存、怎么给前端——本页把"选型 → SQL → 缓存 → BFF → 接口契约"串成一条线，目标是能读懂表设计、能设计接口契约、能写一个聚合裁剪的 Node BFF。

一、数据库选型：关系型 / 文档型 / 缓存 ​

类型代表数据模型强项典型场景
关系型 (RDBMS)MySQL / PostgreSQL表 + 行 + 外键事务、强一致、复杂关联查询订单/账户/权限，B 端后台
文档型 (NoSQL)MongoDB集合 + 文档（JSON）schema 灵活、水平扩展、嵌套读写日志、内容、结构多变的数据
键值缓存RedisKey-Value + 多数据结构内存级读写、TTL、原子操作会话、热点数据、限流、排行榜
搜索引擎Elasticsearch倒排索引全文检索、聚合分析日志检索、商品搜索

选型口诀：要事务和关联 → 关系型；要灵活 schema 与海量写入 → 文档型；要快、要减压 → Redis 做缓存；要搜索 → ES。真实系统多为组合：MySQL 存核心业务 + Redis 做缓存/会话 + MongoDB/ES 存日志与检索。

二、SQL 基础 ​

2.1 增删改查（CRUD） ​

sql
-- 建表
CREATE TABLE users (
  id         BIGINT PRIMARY KEY AUTO_INCREMENT,
  email      VARCHAR(120) NOT NULL UNIQUE,
  nickname   VARCHAR(50),
  status     TINYINT NOT NULL DEFAULT 1,   -- 1 正常 0 禁用
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

-- 增
INSERT INTO users (email, nickname) VALUES ('a@x.com', '阿杰');
-- 查（明确字段，别写 SELECT *；分页 + 排序）
SELECT id, email, nickname FROM users WHERE status = 1 ORDER BY id DESC LIMIT 10 OFFSET 0;
-- 改
UPDATE users SET nickname = 'Jay' WHERE id = 1;
-- 删（生产优先"软删除"：加 is_deleted 标记而非物理删除）
DELETE FROM users WHERE id = 1;

关联查询用 JOIN，聚合用 GROUP BY + COUNT/SUM：

sql
-- 每个用户的订单数（只统计未删除订单）
SELECT u.id, u.email, COUNT(o.id) AS order_count
FROM users u
LEFT JOIN orders o ON o.user_id = u.id AND o.is_deleted = 0
GROUP BY u.id, u.email
ORDER BY order_count DESC;

2.2 索引 ​

索引是用空间换时间的加速结构，MySQL 默认 B+ 树：所有值有序、叶子节点存数据并链表相连，因此范围查询与排序都高效。

  • 最左前缀原则：联合索引 (a, b, c) 只能命中 a、a+b、a+b+c 的查询，WHERE b = 1 单独查不命中。
  • 索引失效常见原因：在索引列上做函数/运算（WHERE YEAR(created_at)=2024）、隐式类型转换（WHERE id = '1'）、LIKE '%x' 前置通配、OR 连接非索引列。
  • 回表：二级索引只存主键，查非索引字段需回到主键索引取数据；覆盖索引（查询字段全在索引里）可免回表。
  • 索引不是越多越好：每个索引都增加写入成本与存储，写多读少的表要克制。
sql
CREATE INDEX idx_status_created ON users (status, created_at);
EXPLAIN SELECT id, email FROM users WHERE status = 1 ORDER BY created_at DESC;
-- EXPLAIN 关注：type（const/ref/range 好，ALL 全表扫差）、key（命中的索引）、rows（扫描行数）

2.3 事务与 ACID ​

事务保证一组操作的原子性：要么全成功，要么全回滚。

  • ACID：原子性 Atomicity、一致性 Consistency、隔离性 Isolation、持久性 Durability。
  • 隔离级别（从低到高）：读未提交 → 读已提交(RC) → 可重复读(RR，MySQL 默认) → 串行化。级别越高越安全但并发越差。
  • 常见并发问题：脏读、不可重复读、幻读；InnoDB 用 MVCC + 间隙锁 在 RR 下缓解。
sql
START TRANSACTION;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;                 -- 出错时 ROLLBACK

2.4 慢查询 ​

排查链路：开启慢查询日志 → 定位 SQL → EXPLAIN 看执行计划 → 加索引 / 改写 SQL / 减少返回行。

sql
SET GLOBAL slow_query_log = 'ON';
SET GLOBAL long_query_time = 1;   -- 超过 1 秒记入慢日志
SHOW VARIABLES LIKE 'slow_query_log_file';

三、ORM 概念 ​

ORM（Object-Relational Mapping） 把"表/行"映射成"类/对象"，用代码而非手写 SQL 操作数据库。

  • 价值：类型安全、少写样板 SQL、屏蔽方言差异（MySQL/PG 切换）。
  • 代价：N+1 查询（循环里逐条查关联对象）、生成的 SQL 不可控、复杂聚合难表达。
  • 常见实现：TypeORM / Prisma（Node）、Sequelize、Hibernate（Java）、MyBatis（半 ORM）。
  • find / findOne / save / delete 是通用四件套；关联查询要显式 include/relations，避免懒加载触发大量 SQL。
ts
// Prisma：一次带出关联，避免 N+1
const users = await prisma.user.findMany({
  where: { status: 1 },
  select: { id: true, email: true },
  include: { orders: { where: { isDeleted: false }, take: 5 } },
  orderBy: { id: 'desc' },
  skip: 0,
  take: 10,
});

四、Redis 与缓存策略 ​

4.1 常用数据结构 ​

结构命令示例场景
StringSET k v EX 60 / GET / INCR缓存对象、计数器、分布式锁
HashHSET user:1 name 阿杰 / HGETALL存对象字段，可单字段更新
ListLPUSH / RPOP / LRANGE消息队列、最新列表
SetSADD / SISMEMBER / SINTER去重、共同好友、标签
ZSetZADD / ZRANGE / ZINCRBY排行榜、延时队列、带权排序

4.2 过期与淘汰 ​

  • 过期（TTL）：EXPIRE key 60 / SET k v EX 60，到点删除；Redis 用惰性删除 + 定期抽样删除。
  • 淘汰策略 maxmemory-policy：noeviction（拒写）、allkeys-lru（全体最近最少使用）、volatile-lru（仅设了 TTL 的键）、allkeys-lfu（按频率）等。缓存服务一般用 allkeys-lru。
  • 缓存与数据库一致性：常用 Cache Aside——读时先查缓存，未命中查库并回填；写时先更新数据库，再删除缓存（而非更新缓存），并设 TTL 兜底。

4.3 三大缓存故障 ​

问题现象原因对策
缓存穿透大量请求打到 DB，DB 压力骤增查不存在的 key，缓存永远不命中缓存空值(短 TTL)、布隆过滤器、参数校验
缓存击穿单个热点 key 失效瞬间打爆 DB热点 key 过期，并发同时回源互斥锁/单飞(singleflight)、逻辑过期不设 TTL
缓存雪崩大批 key 同时失效，DB 被打挂同一时间批量过期 或 Redis 宕机TTL 加随机抖动、多级缓存、Redis 高可用集群
js
// 单飞 + 空值缓存：同时缓解击穿与穿透
async function getUser(id) {
  const key = `user:${id}`;
  const cached = await redis.get(key);
  if (cached !== null) return cached === 'NULL' ? null : JSON.parse(cached);

  const user = await db.findUser(id);
  // 空值也缓存（短 TTL）防穿透；正常值 TTL 加随机抖动防雪崩
  const ttl = user ? 300 + Math.floor(Math.random() * 60) : 30;
  await redis.set(key, user ? JSON.stringify(user) : 'NULL', 'EX', ttl);
  return user;
}

五、BFF（Backend For Frontend） ​

5.1 为什么需要 BFF ​

移动端/PC/小程序对同一份业务数据的字段需求与聚合粒度不同，若让每个后端微服务直接对前端暴露接口：

  • 前端要发起 N 次请求再自己拼装，首屏变慢、逻辑前移；
  • 后端接口为兼容多端变得臃肿，或频繁为前端改接口；
  • 鉴权、错误处理、埋点在每个前端重复实现。

BFF 是夹在前端与后端微服务之间的适配层（通常由前端团队用 Node 维护），职责是：聚合多个下游接口、裁剪冗余字段、透传鉴权、统一错误与响应格式、做 SSR/页面级缓存。

5.2 Node BFF 实现要点 ​

ts
import express from 'express';

const app = express();
const UP = { user: 'http://user-svc', order: 'http://order-svc' };

async function call(base: string, path: string, token?: string) {
  const res = await fetch(base + path, {
    headers: token ? { Authorization: `Bearer ${token}` } : {},
  });
  if (!res.ok) throw Object.assign(new Error('downstream error'), { status: res.status });
  return res.json();
}

// 页面级聚合：一次返回渲染所需的全部数据，前端只发一个请求
app.get('/bff/order-detail/:id', async (req, res, next) => {
  try {
    const token = req.headers.authorization?.replace('Bearer ', ''); // 鉴权透传
    const order = await call(UP.order, `/orders/${req.params.id}`, token);
    const [user] = await Promise.all([
      call(UP.user, `/users/${order.userId}`, token),
    ]);
    // 裁剪：只下发前端要的字段，屏蔽内部 id / 成本价等
    res.json({
      id: order.id, amount: order.payAmount, statusText: order.statusName,
      buyer: { name: user.nickname, phone: user.phoneMasked },
    });
  } catch (e) { next(e); }
});

// 统一错误体 + 超时/并发控制是 BFF 的必备中间件
app.use((err: any, _req, res, _next) => {
  res.status(err.status ?? 500).json({ code: err.status ?? 'BFF_ERROR', data: null, message: err.message });
});
app.listen(7001);

要点：给下游加超时（AbortSignal.timeout）与并发限流，避免一个慢下游拖垮整页；聚合用 Promise.all，可降级的数据用 Promise.allSettled 允许部分失败；BFF 只做编排不做业务规则，别把领域逻辑堆进来。

六、前后端接口契约设计 ​

6.1 RESTful 规范 ​

  • 资源用复数名词：/users、/orders；动作用 HTTP 方法：GET 查、POST 增、PUT 全量改、PATCH 局部改、DELETE 删。
  • 嵌套资源用路径表达从属：/users/1/orders。
  • 状态码语义化：200 成功、201 已创建、204 无内容、400 参数错、401 未认证、403 无权限、404 不存在、409 冲突、422 校验失败、500 服务端错。
  • 幂等性：GET/PUT/DELETE 应幂等，POST 不幂等（重复提交需前端防抖 + 后端幂等键）。

6.2 统一响应信封 ​

前后端约定唯一响应结构，前端拦截器只需处理一种格式：

json
{
  "code": 0,
  "message": "ok",
  "data": { "id": 1, "nickname": "阿杰" },
  "traceId": "a1b2c3d4"
}
  • code：业务码，0 表示成功；非 0 由前端统一 toast 或跳登录（如 40101 未登录）。
  • data：业务数据，成功才有意义；失败时为 null，不要返回 {} 混淆。
  • traceId：链路追踪 id，便于报障时定位（前端可透传到错误上报）。
  • 分页统一放进 data：{ list: [], total: 100, page: 1, pageSize: 20 }。

6.3 错误码设计 ​

分段编码，例如：0 成功；1xxxx 通用（10001 参数错误）；2xxxx 认证授权（20001 token 过期）；3xxxx 业务（30001 余额不足）；5xxxx 系统（50000 未知错误）。前端按段位处理，而不是逐个硬编码。

6.4 分页 ​

  • 偏移分页：page + pageSize（后端 LIMIT/OFFSET），实现简单，但深分页（翻到很后面）性能差，且数据变动时会漏/重。
  • 游标分页：用 cursor（通常是最后一条的 id/时间）+ limit，稳定且高效，适合信息流/无限滚动。

七、接口联调与 Mock ​

  • 契约先行：先定接口文档（OpenAPI/Swagger、Apifox、YApi），前后端并行开发。
  • Mock：MSW（Service Worker 拦截，能在浏览器与 Node 复用同一套 handler，推荐配合 Vitest/Playwright）；或 Mock 服务器（json-server、msw、Vite server.proxy 指向后端本地）。
  • 跨域联调：开发期用 Vite/Webpack proxy 转发，生产期用 Nginx 或 BFF 同源部署，避免 CORS 到了上线才暴露。
  • 契约校验：用 OpenAPI 生成 TS 类型（openapi-typescript），让接口返回结构与前端类型同源，减少"字段名对不上"的低级错误（详见 HTTP 与请求层设计）。
ts
// Vite dev proxy，把 /api 转发到本地后端，规避跨域
export default defineConfig({
  server: {
    proxy: { '/api': { target: 'http://localhost:3000', changeOrigin: true } },
  },
});

八、常见坑速查 ​

坑现象解法
N+1 查询循环里逐条查，接口慢显式 include/relations，一次带出
深分页慢翻到第 1000 页卡死改游标分页或限制最大页
索引列做运算EXPLAIN 显示全表扫改写条件或用函数索引
大事务锁等待、超时事务尽量短，先算后写
缓存与 DB 不一致读到旧数据Cache Aside + 先更库再删缓存 + TTL
缓存雪崩DB 被打挂TTL 随机抖动 + 多级缓存
BFF 无超时一个慢下游拖垮整页下游设超时 + 降级
响应结构不统一前端到处写兼容统一信封 + 拦截器
错误码随便定前端无法归类处理分段编码 + 文档维护
前端直接连 DB严重安全事故前端只经 BFF/网关，绝不直连数据库

面试要点 ​

  1. 关系型与文档型数据库怎么选？ 答：要事务/强一致/复杂关联选 MySQL/PG；schema 灵活、水平扩展、海量嵌套读写选 MongoDB；二者常组合使用。
  2. Redis 为什么快？ 答：纯内存操作、单线程避免锁竞争、I/O 多路复用、高效数据结构；适合缓存、会话、计数器、排行榜。
  3. 索引失效有哪些常见原因？ 答：索引列上做函数/运算、隐式类型转换、LIKE '%x' 前置通配、不满足最左前缀、OR 非索引列等。
  4. 事务的隔离级别与对应问题？ 答：读未提交/读已提交/可重复读/串行化，分别对应脏读、不可重复读、幻读的解决，MySQL 默认 RR 且用 MVCC。
  5. 缓存穿透、击穿、雪崩的区别与对策？ 答：穿透是查不存在数据（空值缓存/布隆过滤器）；击穿是热点 key 失效（互斥/单飞）；雪崩是批量失效（TTL 抖动/多级缓存）。
  6. 如何保证缓存与数据库一致？ 答：Cache Aside，写时先更新数据库再删除缓存，读时未命中回填，并设 TTL 兜底，接受最终一致。
  7. 什么是 BFF，解决什么问题？ 答：夹在前端与微服务间的适配层，聚合裁剪接口、透传鉴权、统一响应，减少前端请求数与耦合。
  8. 前后端接口契约应该包含什么？ 答：资源化 URL + HTTP 方法 + 状态码、统一响应信封 {code,message,data}、分段错误码、分页协议与字段类型定义。
  9. 偏移分页和游标分页的区别？ 答：偏移用 page/LIMIT-OFFSET 简单但深分页慢且易漏重；游标用 cursor+limit 稳定高效，适合信息流。
  10. ORM 的优缺点？ 答：优点是类型安全、少写 SQL、屏蔽方言；缺点是可能 N+1、生成的 SQL 不可控、复杂聚合弱，需按需手写 SQL。
