大屏与大数据可视化性能 ​

对应 JD 中「数据大屏 / 数字孪生 / 多图表实时刷新」要求。读者做过大屏全尺寸适配（clamp，360px→3840px）与 IoT 实时数据展示，本页把适配方案与渲染调度讲透，并给出 ECharts 大数据量的可验证配置。

一、大屏场景特征与性能预算 ​

特征表现性能预算
超大分辨率1920×1080 起，常见 3840×2160 或多屏拼接单屏 DOM 节点 ≤ 2000
常驻运行7×24 不刷新，内存只增不减就是事故Heap 稳态波动 < 20MB
多图表一屏 8–20 个 ECharts 实例每个实例甘特/堆叠数据 ≤ 5000 点
实时刷新WebSocket 每秒推送多路 IoT 指标刷新帧率 ≥ 30fps，无长任务
无人值守无用户输入，一旦卡死无人重启加看门狗 + 自动降级

结论：大屏不是"把网页放大"，而是长时间、高负载、无人干预的稳定性工程。

二、全尺寸等比适配 ​

2.1 方案对比 ​

方案做法问题
rem + JS 动态根字号监听 resize 改 html.fontSize字体随屏幕放大到不可读，非等比内容易变形
vw 等比缩放1px = 100vw/设计宽字体也等比放大；小屏（360px）字小到看不清
PostCSS px→vw + clamp 上下限构建期把 px 转 vw，对字号/间距用 clamp 锁定区间需合理设定上下限
媒体查询断点手写断点100 处适配就 100 个 @media，维护地狱

推荐：PostCSS 转换 px→vw 做整体等比缩放，再用 clamp() 给关键尺寸（尤其是字号与圆角）锁定上下限，做到"100 处 clamp、零 @media"。

2.2 PostCSS px→vw 配置 ​

js
// postcss.config.js
module.exports = {
  plugins: {
    'postcss-px-to-viewport-8-plugin': {
      unitToConvert: 'px',
      viewportWidth: 1920,       // 设计稿宽度
      unitPrecision: 5,
      viewportUnit: 'vw',
      fontViewportUnit: 'vw',
      minPixelValue: 1,          // ≤1px 不转换（保留 1px 边框物理像素）
      mediaQuery: false,
      exclude: [/node_modules/], // 第三方库不动
      landscape: true,
    },
  },
};

2.3 clamp 上下限锁定（核心） ​

css
/* 根字号不用 vw，保留浏览器/用户字体缩放能力（无障碍要求） */
html { font-size: 16px; }

/* 正文：在 360px→3840px 之间用 clamp 锁定，超出即封顶/封底 */
:root {
  /* 兜底：小于 1280px 时按最小宽算，大于 3840px 时封顶 */
  --scale-min: 1280;
  --scale-max: 3840;
}

/* 标题：随屏宽缩放，但不小于 18px、不大于 64px */
.title {
  font-size: clamp(18px, 1.6vw, 64px);
}

/* 关键数字（大屏 KPI）：320px→3840px 间用 vmin 平滑缩放 */
.kpi-value {
  font-size: clamp(28px, 3.2vmin, 120px);
  line-height: 1.2;
}

/* 间距与圆角：小屏别挤，大屏别空，都用 clamp 收口 */
.gap { gap: clamp(8px, 0.8vw, 32px); }
.card { border-radius: clamp(4px, 0.4vw, 16px); padding: clamp(12px, 1vw, 40px); }

要点：

  • vmin 而非 vw 做数字类缩放：超宽/超高的非标准屏（如 3840×1080 带鱼屏）用 vmin 按短边缩放，避免数字被拉爆。
  • 根字号用固定 px 或 clamp，绝不用纯 vw：否则用户浏览器放大字体时会失效，且 360px 屏上正文会缩小到 8px。
  • 布局容器用 Grid/Flex 自适应，不要用固定 px 宽度拼位置；断点只在"布局结构真的变了"时使用（如 >2560px 三列变四列），而不是为每个元素写断点。
  • 设计稿按 1920 宽产出时，3840 屏即 2× 等比放大；clamp 上限用设计稿 2× 数值即可。

2.4 残留像素对齐问题 ​

vw 转换会产生小数像素，边框与 1px 分割线可能变虚。解决：

  • minPixelValue: 1 保留 1px；
  • 需要物理像素精确的线用 border: 1px solid 且 transform: scaleY(0.5)；
  • 或直接用 border-width: max(1px, 0.05vw)。

三、多图表渲染调度与节流 ​

3.1 分批初始化 ​

ts
// 一屏 20 个 ECharts，切忌一次性全部 init + setOption
const charts = [...document.querySelectorAll<HTMLElement>('.chart')];
async function initChartsInBatches(batchSize = 4) {
  for (let i = 0; i < charts.length; i += batchSize) {
    const batch = charts.slice(i, i + batchSize);
    await new Promise<void>((r) => requestAnimationFrame(() => r()));
    batch.forEach((el) => {
      const inst = echarts.init(el, undefined, { renderer: 'canvas', useDirtyRect: true });
      inst.setOption(buildOption(el.dataset.id!));
      registry.set(el.dataset.id!, inst);
    });
    // 让出主线程，避免一次性长任务
    await new Promise<void>((r) => requestIdleCallback(() => r(), { timeout: 200 }));
  }
}
// 窗口 resize：所有图表统一节流，且必须调用 resize
const onResize = throttle(() => registry.forEach((c) => c.resize()), 200);
window.addEventListener('resize', onResize, { passive: true });
  • useDirtyRect: true：ECharts 开启脏矩形渲染，只重绘变化区域，多图表场景实测可降 30%+ 绘制开销。
  • renderer 选择：数据量大/实时刷新用 canvas；需要 CSS 交互/无障碍/极少节点用 svg。
  • 图表在不可见时不渲染：用 IntersectionObserver 检测，不可见时 dispose() 或暂停刷新（大屏滚动区域尤其重要）。

3.2 统一 30fps 调度 ​

ts
// 所有实时图表共用一个调度器，避免各自 setInterval 造成密集刷新
class FrameScheduler {
  private dirty = new Set<() => void>();
  private raf = 0;
  private last = 0;
  private interval = 1000 / 30; // 目标 30fps
  mark(fn: () => void) { this.dirty.add(fn); this.schedule(); }
  private schedule() { if (!this.raf) this.raf = requestAnimationFrame(this.tick); }
  private tick = (now: number) => {
    this.raf = 0;
    if (now - this.last >= this.interval) {
      this.last = now;
      const fns = [...this.dirty];
      this.dirty.clear();
      for (const fn of fns) fn();
    }
    if (this.dirty.size) this.schedule();
  };
}

四、ECharts 大数据量性能 ​

4.1 大数据量 series 配置 ​

ts
// 10 万点折线：必须开 large + 采样 + 关闭动画与符号
const option = {
  animation: false,             // 实时大屏一律关动画
  series: [{
    type: 'line',
    large: true,                // 开启大数据量优化，走简化绘制路径
    largeThreshold: 2000,       // 超过 2000 点自动启用 large 模式
    sampling: 'lttb',           // 下采样：lttb 保留趋势，avg/max/min 更快
    showSymbol: false,          // 关闭点符号（符号是最贵的绘制项）
    lineStyle: { width: 1 },
    progressive: 2000,          // 分片渲染：每片 2000 点，避免单帧长任务
    progressiveThreshold: 3000, // 超过 3000 点启用 progressive
    data: hugeData,
  }],
  dataZoom: [{ type: 'inside', throttle: 100 }],
};
  • large + largeThreshold：走简化的绘制路径，跳过大量状态判断，是万级点的关键开关。
  • progressive / progressiveThreshold：把一次性绘制拆成多帧完成，避免单帧长任务。
  • sampling: 'lttb'：Largest-Triangle-Three-Buckets，保留极值与趋势，视觉几乎无损；点数少时（<2000）不必开。
  • animation: false：动画会持续触发绘制，实时刷新的场景直接关。
  • showSymbol: false：点符号数量 = 数据点数量，是最容易被忽视的绘制开销。

4.2 增量更新 appendData ​

ts
// 实时追加数据：必须 appendData 或 setOption 局部更新，禁止整包 setOption
function onMessage(e: MessageEvent) {
  const point = JSON.parse(e.data); // { ts, value }
  // 方式一：appendData（对 line 等已渲染类型有效，开销最小）
  chart.appendData({ seriesIndex: 0, data: [[point.ts, point.value]] });
  // 方式二：滑动窗口——超出上限时用局部 option 替换（默认 merge，不会整包 diff）
  win.push([point.ts, point.value]);
  if (win.length > MAX_POINTS) win.shift();
  if (++tick % 30 === 0) {   // 攒 30 帧再刷一次，降低刷新频率
    chart.setOption({ series: [{ data: win, animation: false }],
      xAxis: { min: 'dataMin', max: 'dataMax' } }); // 轴跟随数据，避免全量重算
  }
}

关键坑：chart.setOption(option) 默认是 merge（notMerge 默认 false），传整包会逐项 diff，数据量大时非常贵；传局部 option只更新变化的 series。若确实要替换全部，用 notMerge: true 但只在必要时。

4.3 canvas vs svg 与内存 ​

维度canvassvg
绘制像素级，节点多时更快生成 DOM，节点多则慢
交互/无障碍需自绘天然支持 CSS/ARIA
大数据量首选不推荐
缩放清晰度需按 DPR 放大 canvas矢量无损
ts
// 高清屏：ECharts 自动按 devicePixelRatio 处理，但 4K 大屏要注意 canvas 内存
const chart = echarts.init(el, null, {
  renderer: 'canvas',
  devicePixelRatio: Math.min(window.devicePixelRatio, 2), // 4K 屏限制到 2，防显存爆炸
});
  • 每个实例都有 canvas 与内存开销，图表销毁必须 dispose()，只 clear() 不释放 DOM/事件/定时器。
  • 高频重建（如分组切换）要复用实例，用 setOption(opt, { replaceMerge: ['series'] }) 而非 destroy + init。

六、实时数据刷新策略 ​

ts
// 方案 A：节流 + 合并窗口（高频推送 → 低频渲染）
const buffer: Point[] = [];
let flushTimer: number | null = null;
ws.onmessage = (e) => {
  buffer.push(JSON.parse(e.data));
  if (flushTimer) return;
  flushTimer = window.setTimeout(() => {
    flushTimer = null;
    const batch = buffer.splice(0);
    applyBatch(batch);   // 一次性更新多个图表
  }, 200);               // 200ms 合并窗口 ≈ 5Hz 刷新
};

// 方案 B：requestAnimationFrame 对齐刷新
let pendingBatch: Point[] = [];
ws.onmessage = (e) => {
  pendingBatch.push(JSON.parse(e.data));
  if (pendingBatch.length === 1) requestAnimationFrame(() => {
    const batch = pendingBatch; pendingBatch = [];
    charts.forEach((c) => c.update(batch));
  });
};

// 方案 C：分级刷新——重要 KPI 高频、趋势图低频
const level = { kpi: 5, trend: 1, table: 0.2 }; // Hz
  • 降级策略：数据频率超过渲染能力时，按优先级丢弃（保留最新值而非全部历史），或把刷新率按图表重要性分级。
  • 时间对齐：多个图表用同一 now 时间戳更新，避免不同步导致视觉抖动。
  • 背压（backpressure）：推送速率 > 消费速率时主动丢包或降采样，防止 buffer 无限增长（内存泄漏）。

七、内存与常驻稳定性 ​

  • 销毁即释放：chart.dispose()、worker.terminate()、ws.close()、clearInterval、removeEventListener 全都要在"图表切换/组件卸载"时执行。
  • ResizeObserver 断连：适配逻辑常用 RO，忘记 disconnect() 会持续持有 DOM 引用。
  • 看门狗：长时间常驻页面加自检——记录最后一次成功刷新时间，超过阈值（如 30s）触发重连/重载。
ts
// 看门狗：异常卡死时自动恢复
let lastTick = Date.now();
setInterval(() => { if (Date.now() - lastTick > 30_000) location.reload(); }, 5_000);
ws.onmessage = () => { lastTick = Date.now(); /* ... */ };
// 页面隐藏时降频（大屏一般不隐藏，但投屏/多标签场景有用）
document.addEventListener('visibilitychange', () => {
  scheduler.setFps(document.hidden ? 2 : 30);
});

八、大屏常见坑清单 ​

  1. 根字号用 vw → 用户字体缩放失效、小屏字过小；应用固定 px 或 clamp。
  2. 每个元素写 @media → 维护地狱；用 clamp + 容器自适应替代。
  3. 整包 setOption 刷新 → 千级点就卡；改 appendData 或局部 option；图表不 dispose → 内存暴涨。
  4. 4K 屏 canvas 内存爆炸 → devicePixelRatio 限制到 2；longtask 未治理 → 分批 init + 时间切片。
  5. 多个 setInterval 各自刷新 → 用统一调度器对齐 rAF；未做非等比屏兜底 → 关键尺寸用 clamp + vmin。
  6. 无降级与看门狗 → 无人值守时一次异常就白屏到天亮。

九、与目标 JD 的对应点 ​

  • #7 润信智能（智慧能源 + 数据大屏 + 数字孪生）：clamp 适配、ECharts 大数据量、实时刷新策略是硬考点；数字孪生侧（Cesium/Three）另见地图与三维。
  • #1 星河视控（监控/IoT + 大屏）：WebSocket 高频推送 + 图表刷新节流 + 内存常驻稳定直接对口；#2 四方精创的分段加载 + dataZoom 采样 + Worker 聚合是数据密集页面通用解法。
  • #9 今天国际（架构/组件库）：把适配与调度封装成可复用组件（如 <AutoScale>、useFrameScheduler），是对"公共能力建设"的直接体现。

面试要点 ​

  1. 大屏全尺寸适配你选什么方案，为什么？ 答：PostCSS px→vw 做整体等比缩放 + clamp() 锁定关键尺寸上下限，做到百处 clamp、零 @media；根字号保留固定 px 以免丧失字体缩放与可读性。
  2. 为什么根字号不能用 vw？ 答：vw 根字号会随屏宽缩放，360px 屏正文过小、用户浏览器放大字体失效，破坏无障碍；应用固定值或 clamp 收口。
  3. 超宽/竖屏拼接屏怎么兜底？ 答：数字类用 vmin 按短边缩放避免拉爆，关键尺寸一律 clamp 封顶/封底，布局用 Grid/Flex 自适应而非固定 px 定位。
  4. ECharts 10 万点怎么优化？ 答：开 large + largeThreshold: 2000、showSymbol: false、animation: false、sampling: 'lttb'、progressive 分片渲染，并用 dataZoom 只加载视窗数据。
  5. 实时刷新应该 appendData 还是 setOption？ 答：优先 appendData 或传局部 option；setOption 默认 merge 会逐项 diff 整包，数据量大时很贵，避免每次整包刷新。
  6. 图表切换内存暴涨怎么排查？ 答：检查是否 dispose()（clear() 不释放实例与事件）、ResizeObserver 是否 disconnect、定时器/WS 是否清理；用 Heap Snapshot 对比确认。
  7. 一屏 20 个图表怎么调度？ 答：分批 init（每批 3–4 个 + rAF/rIC 让出主线程）、统一 30fps 调度器对齐 rAF、不可见图表暂停、resize 全局节流并调用 resize()。
  8. 高频 WebSocket 推送如何避免渲染雪崩？ 答：节流/合并窗口（如 200ms 攒批）、按图表重要性分级刷新率、rAF 对齐、背压丢弃或降采样，防止 buffer 无限增长。
  9. canvas 与 svg 怎么选？ 答：大数据量、实时刷新选 canvas（可用 useDirtyRect 脏矩形）；节点少、需 CSS/无障碍交互选 svg；4K 屏限制 devicePixelRatio 防显存爆炸。
  10. 常驻大屏怎么做稳定性保障？ 答：统一销毁与释放（dispose/terminate/close/clearInterval）、看门狗按最后刷新时间自动重连或重载、页面隐藏降频、稳态 Heap 波动控制在阈值内。
