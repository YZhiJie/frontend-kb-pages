依赖治理与供应链 ​

对应 JD 的「前端安全 / 工程化 / 组件库建设」交叉项。依赖治理不是「升级到最新版」这么简单，而是风险识别 → 可机器化的门禁 → 升级策略 → 供应链防御的闭环。架构层面的依赖约束见 架构约束与依赖治理，安全侧的依赖视角见 前端 Web 安全。

一、第三方依赖风险类型 ​

引入一个 npm 包，就同时引入了五类风险：

风险说明度量手段
体积增大 bundle，拖慢首屏bundle 分析、体积预算
许可证GPL / AGPL 等可能传染闭源项目license-checker、SBOM
维护活跃度无更新、issue 无人回应、被弃用npm 下载量、最近提交、open issues
已知漏洞（CVE）依赖中存在可直接利用的漏洞npm audit / OSV / Snyk
供应链攻击包被投毒、作者账号被盗lockfile 审计、--ignore-scripts

「体积」是最直观的：一个 moment 全量包约 300KB、lodash 全量约 70KB；改用 dayjs（约 7KB）与 lodash-es（tree-shaking 友好）能立刻瘦身。「许可证」是法务风险：AGPL 要求衍生作品开源，闭源商业产品引入会踩雷，需在 CI 里扫描并拦截。

二、npm / pnpm audit ​

audit 基于漏洞库比对依赖树，报告等级（low / moderate / high / critical）：

bash
# 只报 high 及以上，CI 中可作门禁
pnpm audit --audit-level=high

# 输出可解析的 JSON，便于脚本统计
pnpm audit --json > audit.json

# 直接修复（遵守 semver 约束）
pnpm audit --fix

要点：audit 依赖漏洞库的时效性与包的元数据，会漏报未被收录的漏洞、也会误报「devDependencies 里不影响运行时的」问题；区分直接依赖与传递依赖，传递依赖的漏洞往往你无法直接升级，需要 pnpm.overrides 强制覆盖：

json
// pnpm.overrides：强制传递依赖的版本
{
  "pnpm": {
    "overrides": {
      "minimist@<1.2.6": "^1.2.6",
      "semver@<7.5.2": "^7.5.2"
    }
  }
}

三、锁定版本（lockfile） ​

pnpm-lock.yaml 记录整个依赖树的精确版本与完整性哈希（integrity），是可复现构建的基础。

  • lockfile 必须提交进仓库，否则 CI 每次解析出不同版本，「本地能跑、CI 挂」。
  • CI / 生产安装必须 --frozen-lockfile（pnpm）/ npm ci：lockfile 与 package.json 不一致时直接失败，而不是悄悄改 lockfile。
yaml
# .github/workflows/ci.yml（节选）
- name: Install (strict)
  run: pnpm install --frozen-lockfile --ignore-scripts

integrity 字段（如 sha512-...）保证下载的 tarball 与首次解析时一致，是防供应链篡改的关键——若发布方替换了同版本 tarball，integrity 校验会失败。绝不要在 CI 里跑 pnpm install（不加 frozen）自动改 lockfile，那等于放弃了可复现性。

四、依赖升级策略 ​

手动升级跟不上漏洞速度，用机器化升级：

工具特点配置位置
Renovate功能强、可分组、支持 monorepo / 自定义规则renovate.json
DependabotGitHub 原生、配置简单.github/dependabot.yml
json
// renovate.json —— 分组升级 + 自动合并策略
{
  "$schema": "https://docs.renovatebot.com/renovate-schema.json",
  "extends": ["config:base", ":semanticCommits"],
  "packageRules": [
    {
      "matchUpdateTypes": ["patch", "minor"],
      "matchCurrentVersion": "!/^0/",
      "automerge": true,
      "groupName": "非破坏性升级"
    },
    {
      "matchPackageNames": ["react", "react-dom", "vue"],
      "groupName": "框架核心",
      "automerge": false
    },
    {
      "matchDepTypes": ["devDependencies"],
      "matchUpdateTypes": ["patch"],
      "automerge": true
    }
  ],
  "vulnerabilityAlerts": { "labels": ["security"], "automerge": true }
}
yaml
# .github/dependabot.yml
version: 2
updates:
  - package-ecosystem: "npm"
    directory: "/"
    schedule: { interval: "weekly" }
    open-pull-requests-limit: 10
    groups:
      dev-dependencies:
        dependency-type: "development"

要点：patch / minor 自动合并（需有测试保障），major 必须人工评审（破坏性变更）；框架核心单独分组、不自动合并；安全告警（vulnerabilityAlerts）优先级最高，可自动合并；升级 PR 必须跑完整 verify 门禁（type-check + test + build + 体积审计），否则「升个包悄悄坏了」。

五、构建产物审计 ​

源码里的依赖最终体现在 bundle，必须用数字说话：

bash
# 可视化分析：哪些包占了体积
npx vite-bundle-visualizer
# 或 rollup-plugin-visualizer 输出 stats.html
ts
// scripts/check-bundle-size.ts —— 体积预算门禁（超预算即失败）
import { gzipSync } from 'node:zlib';
import { readFileSync, statSync } from 'node:fs';

const BUDGET_KB: Record<string, number> = {
  'dist/index.js': 200,        // 入口 gzip 预算
  'dist/vendor.js': 350,       // 三方依赖预算
};

let failed = false;
for (const [file, budget] of Object.entries(BUDGET_KB)) {
  try {
    statSync(file);
  } catch {
    console.error(`FAIL 产物缺失: ${file}`);   // 产物路径变了要立即发现（如改构建配置）
    failed = true;
    continue;
  }
  const gzipKb = gzipSync(readFileSync(file)).length / 1024;
  console.log(`${file}: ${gzipKb.toFixed(1)}KB / 预算 ${budget}KB`);
  if (gzipKb > budget) {
    console.error(`FAIL 超预算 ${(gzipKb - budget).toFixed(1)}KB`);
    failed = true;
  }
}
process.exit(failed ? 1 : 0);

要点：预算按 gzip 计（网络传输的真实成本）；预算只增不减地收紧，每次上调要走评审（否则门禁被逐步稀释）；检查产物存在性——构建配置一改（entry 改名 / 分包调整）路径就变，不检查会「静默通过」。体积膨胀常来自「偷偷引入大依赖」（AI 生成代码尤其爱引 lodash / moment），体积门禁正是拦截它最有效的手段。

六、架构层面的依赖约束 ​

体积与漏洞之外，还有「合法但结构错误」的依赖——跨层引用、深路径 import、循环依赖、底层反向依赖上层。这类问题 audit 与体积审计都发现不了，需 dependency-cruiser 把规则变成 CI 红线（完整配置与反向验证见 架构约束与依赖治理）：

js
// .dependency-cruiser.cjs（节选）
module.exports = {
  forbidden: [
    { name: 'no-circular', severity: 'error', from: {}, to: { circular: true },
      comment: '循环依赖导致初始化顺序与 chunk 不可预测' },
    { name: 'no-npm-in-leaf', severity: 'error', from: { path: '^packages/(shared|core)' },
      to: { dependencyTypes: ['npm', 'npm-optional', 'npm-peer'] },
      comment: '底层包零运行时依赖，引 npm 包须显式评审' },
    { name: 'no-deep-import', severity: 'error', from: { path: '^(apps|pages)' },
      to: { path: '^packages/[^/]+/src/(?!index\\.ts)' },
      comment: '跨包只走公开入口，禁止深路径 import 内部文件' },
  ],
  options: { doNotFollow: { path: 'node_modules' }, tsConfig: { fileName: 'tsconfig.base.json' } },
};

要点：只有 severity: 'error' 拦得住（warn 不失败）；规则本身要被反向 fixture 验证（否则规则写错会「假绿」）；必须配 tsConfig 解析别名，否则 @/x 被判无法解析、规则失效。

七、供应链攻击 ​

npm 生态的供应链攻击手法：

手法说明防御
域名抢注（typosquatting）crossenv vs cross-env、lodahs vs lodash拼写核对、锁定 lockfile、私有 registry 审核
postinstall 脚本安装时执行恶意代码窃取 env / 凭证--ignore-scripts（或用 allowlist 放行少数）
作者账号被盗攻击者发布「合法包」的恶意新版本锁定精确版本 + integrity 校验
依赖混淆发布与内网私有包同名的公共包，诱导误装私有 registry 优先、scope 限定
恶意版本回滚老版本被替换为恶意内容integrity 哈希校验、lockfile 冻结
bash
# CI 安装时禁用生命周期脚本，阻断 postinstall 攻击
pnpm install --frozen-lockfile --ignore-scripts

# 若必须放行某些包的脚本（如 esbuild / sharp 需下载二进制），用 allowlist
# .npmrc
# ignore-scripts=true
json
// pnpm：只允许白名单包的构建脚本执行（pnpm 10+ 默认禁止所有脚本）
{
  "pnpm": {
    "onlyBuiltDependencies": ["esbuild", "sharp", "@swc/core"]
  }
}

要点：integrity 哈希是供应链的最后一道闸——即使发布方替换了同版本 tarball，--frozen-lockfile 也会校验失败；「包名拼写」是最便宜也最有效的防御（考 PR review 时逐个核对新包）；发布自己的包时开启 2FA / provenance（npm provenance 让消费者可验证构建来源）。

八、镜像与私有 registry ​

企业与信创环境常用私有 registry / 内网镜像：

ini
; .npmrc —— 项目级，锁定 registry 与认证
registry=https://registry.npmmirror.com
@myorg:registry=https://npm.internal.example.com
//npm.internal.example.com/:_authToken=${NPM_TOKEN}    ; token 从环境变量注入，绝不硬编码
strict-ssl=true
save-exact=true                                       ; 安装即锁定精确版本

要点：scope 包（@myorg/*）必须走私有 registry，避免同名公共包被误装（依赖混淆攻击）；认证 token 走环境变量注入，绝不写进仓库；save-exact=true 让 package.json 直接写精确版本，减少「^(caret) 自动跨版本」的意外升级；信创 / 离线环境需自建 registry 并定期同步，否则无法安装。

九、常见坑 ​

  1. lockfile 未提交或 CI 不用 --frozen-lockfile：依赖树不可复现，「本地能跑 CI 挂」。
  2. pnpm.overrides 覆盖后未回归测试：强制升级传递依赖可能引入不兼容，必须跑全量测试。
  3. 把 audit 的 moderate/low 一律当阻塞：会堆积大量「devDep 里不影响运行时」的噪音，导致团队关掉门禁；应按等级与依赖类型分级。
  4. 体积预算只在本地跑：体积会缓慢膨胀，必须进 CI 且只增不减地收紧。
  5. 体积预算写死路径：构建配置一改产物名就变，脚本因「取不到文件」而静默通过或误报，必须检查产物存在性。
  6. 依赖升级自动合并所有类型：major 破坏性变更被自动合并，线上直接崩；major 必须人工评审。
  7. 直接删掉不用的依赖以为省体积：若它仍是传递依赖，删 package.json 无用，要用 bundle 分析确认真正来源。
  8. 未开启 --ignore-scripts：postinstall 恶意脚本照常执行，等于把执行权交给每个依赖包。
  9. 私有 registry 与公共 registry 混用未限定 scope：同名公共包可能被误装（依赖混淆）。
  10. 新增依赖不核对包名：typosquatting 包名（lodahs）一条 pnpm add 就装进来了。
  11. audit fix 无脑升级：--fix 可能跨 major 升级，破坏兼容性，改完必须跑 verify。
  12. 许可证扫描缺失：引入 AGPL / GPL 依赖后才被法务发现，回滚成本高。

面试要点 ​

  1. 引入第三方依赖要评估哪些风险？ 答：体积、许可证、维护活跃度、已知 CVE、供应链攻击五类。
  2. lockfile 为什么必须提交且 CI 用 --frozen-lockfile？ 答：它记录精确版本与 integrity 哈希，保证可复现安装；frozen 让不一致时直接失败而非悄悄改。
  3. audit 有什么局限？ 答：依赖漏洞库时效性会漏报，也会误报无关的 devDependencies；传递依赖漏洞需用 pnpm.overrides 覆盖。
  4. 依赖升级策略怎么定？ 答：patch/minor 可自动合并（有测试保障），major 人工评审；Renovate/Dependabot 分组 + 安全告警优先。
  5. 体积预算为什么进 CI？ 答：体积随时间缓慢膨胀，必须数字化门禁且只增不减地收紧，是拦截「偷偷引大依赖」最有效的手段。
  6. dependency-cruiser 管什么？ 答：管「合法但结构错误」的依赖——循环依赖、跨层引用、深路径 import、底层引 npm 包，需配 tsConfig 并以 error 级生效。
  7. 什么是 typosquatting？怎么防？ 答：用近似包名（lodahs/crossenv）冒充正品；拼写核对 + lockfile + 私有 registry 审核。
  8. postinstall 攻击怎么防？ 答：安装加 --ignore-scripts，或 pnpm 的 onlyBuiltDependencies 白名单放行必要包（esbuild/sharp）。
  9. integrity 哈希的作用？ 答：校验下载 tarball 与首次解析一致，发布方替换同版本内容时会校验失败，是供应链最后一道闸。
  10. 私有 registry 怎么配才安全？ 答：按 scope 指向私有源、认证 token 走环境变量、save-exact=true、避免与公共源同名混淆。
  11. audit --fix 有什么风险？ 答：可能跨 major 升级引入不兼容；改完必须跑完整 verify（类型 / 测试 / 构建 / 体积）。
