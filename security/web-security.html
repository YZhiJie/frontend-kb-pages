前端 Web 安全 ​

对应 JD 的「前端安全（XSS / CSRF）」B 级高频项（4 份提及）。前端安全的核心是「永不信任任何进入 DOM 的数据」，并把防线机器化（CSP、依赖扫描、CI 门禁）。本文按「XSS → CSRF → 点击劫持 → 敏感信息 → iframe 沙箱 → CSP → 依赖安全 → 速查表」组织。

一、XSS（跨站脚本） ​

XSS 是攻击者把恶意脚本注入到页面、在其他用户浏览器中执行。按注入与存储方式分三类：

类型触发路径典型场景数据流向
存储型恶意内容存服务端，被他人读取执行评论区、昵称、私信DB → 页面
反射型恶意内容在 URL / 响应中即时反射搜索回显、错误页URL → 响应
DOM 型前端 JS 直接把不可信数据写入 DOMinnerHTML、location.hrefURL → JS → DOM

三种危险入口（前端必须重点防 DOM 型与存储型）：

js
// 危险 1：innerHTML 拼接用户数据
el.innerHTML = `<div>${userComment}</div>`;                 // 错误：可注入 <img src=x onerror=...>

// 危险 2：React 的 dangerouslySetInnerHTML
return <div dangerouslySetInnerHTML={{ __html: htmlFromServer }} />;   // 错误：绕过 React 转义

// 危险 3：Vue 的 v-html
// <div v-html="userContent"></div>                        // 错误：等同 innerHTML

// 危险 4：跳转协议注入
location.href = userInput;                                  // "javascript:alert(1)" 可直接执行

防御：

ts
// 正确 1：优先用框架默认转义能力（React 的 {}、Vue 的 {{ }} 都会转义）
return <div>{userComment}</div>;     // 安全：React 会转义 < > & 等

// 正确 2：必须渲染富文本时，先净化（DOMPurify 是事实标准）
import DOMPurify from 'dompurify';
const clean = DOMPurify.sanitize(htmlFromServer, {
  ALLOWED_TAGS: ['p', 'br', 'strong', 'em', 'a', 'ul', 'ol', 'li', 'code'],
  ALLOWED_ATTR: ['href', 'title', 'rel'],
  FORBID_TAGS: ['script', 'style', 'iframe'],
  FORBID_ATTR: ['onerror', 'onload', 'onclick'],
});
return <div dangerouslySetInnerHTML={{ __html: clean }} />;

// 正确 3：跳转前校验协议白名单
function safeHref(url: string) {
  const u = new URL(url, location.origin);
  return ['http:', 'https:'].includes(u.protocol) ? u.href : 'about:blank';
}

要点：能转义就别渲染 HTML；必须渲染时用 DOMPurify（不要自己写正则过滤，正则过滤 HTML 几乎必被绕过）；URL 参数、href、src 都要做协议白名单（杜绝 javascript: / data: 协议注入）；服务端也要转义 / 净化——前端防不住「其他客户端（App/第三方系统）读到未净化数据」的存储型 XSS。DOMPurify 的默认配置已足够严格，不要为了「能显示更多标签」随意放宽 ALLOWED_TAGS。

二、CSRF（跨站请求伪造） ​

CSRF 利用「浏览器自动携带 Cookie」的特性：用户登录 A 站后访问攻击者页面，攻击者诱导浏览器向 A 站发请求，Cookie 自动带上，服务端误以为是用户操作。

防御组合拳：

手段原理局限 / 注意
SameSite=Lax/Strict跨站请求不携带 Cookie现代浏览器默认 Lax，能挡大部分
CSRF Token请求带一次性 / 会话绑定的随机 token需服务端配合，且不能被 XSS 读到
双重提交 Cookie请求头 token 与 Cookie 中 token 比对依赖子域名不可被写 Cookie
Referer / Origin 校验校验请求来源Referer 可能被裁剪，Origin 更可靠
自定义请求头要求 X-Requested-With 等简单请求无法自定义头，天然抬高门槛
html
<!-- SameSite=Lax 的默认行为：跨站 POST 不带 Cookie，顶层 GET 导航带 -->
Set-Cookie: session=abc; SameSite=Lax; Secure; HttpOnly; Path=/
ts
// 双重提交：从 Cookie 读 token，再放进请求头（服务端比对两者）
function getCookie(name: string) {
  return document.cookie.split('; ').find((c) => c.startsWith(name + '='))?.split('=')[1];
}
fetch('/api/transfer', {
  method: 'POST',
  headers: { 'X-CSRF-Token': getCookie('csrf_token') ?? '' },
  credentials: 'include',
});

要点：CSRF Token 必须放在请求头或 body，绝不能只放 Cookie（只放 Cookie 就等于没有防护）；HttpOnly 保护 session 但保护不了需要 JS 读的 CSRF Token，所以双重提交方案里 CSRF Token 不能用 HttpOnly；接口只接受非简单请求（强制预检 + 自定义头）本身就是一层防护。REST API + Token（Bearer）天然免疫 CSRF，因为浏览器不会自动携带 Authorization 头——这也是前后端分离架构更少 CSRF 的原因。

三、点击劫持（Clickjacking） ​

攻击者用透明 iframe 覆盖你的页面，诱导用户点击真实按钮（如「确认转账」）：

http
# 方案 1：请求头（老但有效）
X-Frame-Options: DENY
X-Frame-Options: SAMEORIGIN            # 仅允许同源嵌入

# 方案 2：CSP（现代首选，可精确到来源）
Content-Security-Policy: frame-ancestors 'self' https://trusted.example.com

X-Frame-Options 有三种值：DENY（禁止任何嵌入）、SAMEORIGIN（同源可嵌）、ALLOW-FROM uri（已废弃且兼容性差）。CSP frame-ancestors 取代 X-Frame-Options，可配多个来源。前端兜底（frame-busting）可用 CSS @media 或 JS 判断 window.self !== window.top，但可被绕过，不能作为唯一防线。

四、敏感信息管控 ​

存储位置风险适用
localStorage任何 XSS 都能读取，持久不过期禁止存 Token / 敏感数据
sessionStorage同样可被 XSS 读，但随标签关闭清除低敏感临时态
内存（JS 变量）XSS 可读，但刷新即失效推荐存 Access Token
HttpOnly CookieJS 读不到，防 XSS 窃取推荐存 Refresh Token / Session
IndexedDB可被 XSS 读缓存数据，不放密钥

安全存储组合（业界共识）：

  • Access Token（短过期 15min）存内存，JS 变量，配合请求层注入请求头。
  • Refresh Token（长过期）存 HttpOnly; Secure; SameSite Cookie，仅用于换新 Access Token。
  • 绝不把敏感信息（密码、身份证、密钥）写进 localStorage / sessionStorage。

传输层：

  • HTTPS 全覆盖，禁用明文 HTTP。
  • 混合内容（Mixed Content）：HTTPS 页面里加载 HTTP 资源会被浏览器拦截（主动内容直接 block，被动内容警告）。用 Content-Security-Policy: upgrade-insecure-requests 自动升级。
  • HSTS（Strict-Transport-Security: max-age=31536000; includeSubDomains）强制后续只用 HTTPS。
http
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
Content-Security-Policy: upgrade-insecure-requests; default-src 'self'

五、iframe 沙箱 ​

嵌入第三方内容时，sandbox 必须最小化权限（详见 浏览器跨域机制 的 iframe 章节）：

html
<iframe
  src="https://third-party.example.com"
  sandbox="allow-scripts"                       <!-- 只给脚本，不给同源、不给弹窗 -->
  referrerpolicy="no-referrer"
  allow="clipboard-read 'none'; camera 'none'; microphone 'none'"></iframe>

要点：allow-scripts + allow-same-origin 同开等于无沙箱（脚本可移除沙箱并重载）；默认不写 sandbox 就是全权限；用 allow 属性（Permissions Policy）进一步限制摄像头 / 麦克风 / 剪贴板。

六、CSP（内容安全策略）详解 ​

CSP 通过响应头（或 meta，但 meta 无法用部分指令）白名单限制资源加载与脚本执行，是对抗 XSS 的最后一道强防线。

http
Content-Security-Policy:
  default-src 'self';
  script-src 'self' 'nonce-abc123' https://cdn.example.com;
  style-src 'self' 'unsafe-inline';
  img-src 'self' data: https://img.example.com;
  connect-src 'self' https://api.example.com wss://ws.example.com;
  font-src 'self';
  object-src 'none';
  base-uri 'self';
  form-action 'self';
  frame-ancestors 'self';
  upgrade-insecure-requests
指令作用常见设置
default-src其他指令的兜底'self'
script-src脚本来源用 nonce-* / sha256-*，避免 unsafe-inline
style-src样式来源'unsafe-inline' 常被迫使用（可换 nonce）
img-src图片来源'self' data: https:
connect-srcfetch / XHR / WebSocket必须显式加 wss://！
object-src插件必须 'none'（防 Flash / 插件类攻击）
base-uri<base> 标签'self'（防 base 劫持）
frame-ancestors谁可嵌入我取代 X-Frame-Options
report-uri / report-to违规上报先 Content-Security-Policy-Report-Only 观察

要点：先上 Report-Only 模式收集违规，确认不误伤后再强制生效；'unsafe-inline' 会让 CSP 对 XSS 近乎失效（内联脚本仍可执行），用 nonce 替代；connect-src 漏配 wss:// 会导致 WebSocket 被拒，这是实时应用上 CSP 后最常见的报错；nonce 每次响应必须随机，由服务端模板注入。

七、依赖安全 ​

第三方依赖是「从别人代码里进来的 XSS / 供应链风险」：

  • npm audit / pnpm audit 扫描已知 CVE，--audit-level=high 可只报高危。
  • 锁文件（lockfile）必须提交，pnpm install --frozen-lockfile 保证 CI 与本地依赖一致。
  • 谨慎使用 postinstall 脚本：供应链攻击常在此执行，CI 可加 --ignore-scripts。
  • 定期升级：用 Renovate / Dependabot 自动开 PR。

详细治理见 依赖治理与供应链。

八、常见漏洞清单与防御速查表 ​

漏洞一句话原理防御
存储型 XSS服务端存恶意脚本被他人执行服务端转义 + 前端 DOMPurify + CSP
反射型 XSSURL 参数反射进响应输出转义 + 白名单
DOM 型 XSS前端把不可信数据写入 DOM避免 innerHTML / dangerouslySetInnerHTML
CSRF自动携带 Cookie 伪造请求SameSite + CSRF Token + 自定义头
点击劫持透明 iframe 诱骗点击frame-ancestors / X-Frame-Options
混合内容HTTPS 页加载 HTTP 资源HTTPS + upgrade-insecure-requests
Token 窃取XSS 读 localStorageToken 存内存 / HttpOnly Cookie
开放重定向跳转参数可指向恶意站跳转协议 + 域白名单
依赖投毒恶意 npm 包 / 脚本audit + lockfile + --ignore-scripts
原型污染恶意 __proto__ 覆盖原型输入键名白名单 / Object.create(null)

原型污染值得单列：攻击者通过 merge({}, JSON.parse(userInput)) 里的 __proto__ 篡改 Object.prototype，影响全站。防御：合并前过滤 __proto__ / constructor / prototype 键，用 Object.create(null) 建裸对象，或升级 lodash 等已修复版本的库。

面试要点 ​

  1. XSS 分哪几类？ 答：存储型（脏数据落库）、反射型（URL/响应即时反射）、DOM 型（前端直接写入 DOM），危害相同、注入路径不同。
  2. React dangerouslySetInnerHTML 为什么危险？ 答：它绕过 React 的自动转义，直接写入 HTML；必须渲染富文本时先过 DOMPurify。
  3. 为什么不能用正则过滤 HTML？ 答：HTML 语法极其复杂，正则几乎必被绕过；必须用 DOMPurify 这类基于解析器的库。
  4. CSRF 的原理一句话？ 答：浏览器自动携带同站 Cookie，攻击者诱导请求让服务端误认为是用户本人操作。
  5. CSRF 防御怎么组合？ 答：SameSite Cookie + CSRF Token（放请求头/body）+ Origin/Referer 校验 + 强制非简单请求。
  6. 为什么 REST API + Bearer Token 天然免疫 CSRF？ 答：浏览器不会自动携带 Authorization 头，攻击者无法伪造该凭证。
  7. Token 应该存哪？ 答：Access Token 存内存，Refresh Token 存 HttpOnly; Secure; SameSite Cookie；绝不存 localStorage。
  8. 点击劫持怎么防？ 答：CSP frame-ancestors（首选，取代 X-Frame-Options）+ X-Frame-Options: DENY/SAMEORIGIN。
  9. CSP 上线注意什么？ 答：先 Report-Only 观察避免误伤；用 nonce 替代 unsafe-inline；connect-src 别漏 wss://；object-src 设 'none'。
  10. 什么是原型污染？怎么防？ 答：通过 __proto__ 篡改原型影响全站；合并输入前过滤危险键、用 Object.create(null)、保持库升级。
