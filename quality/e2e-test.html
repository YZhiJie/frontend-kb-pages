端到端测试（Playwright） ​

E2E 是金字塔顶端最贵的一层：跑在真实浏览器、驱动真实交互，因此只该覆盖「关键链路 + 视觉回归」这类单测覆盖不到的盲区。本文按「定位与成本 → 配置 → 选择器策略 → 自动等待 → 视觉回归 → 测试分类 → CI 与调试 → 常见坑」组织。上游单元测试见 单元测试（Vitest），下游门禁见 架构约束与依赖治理。

一、E2E 的定位与成本 ​

E2E 的价值与代价都很明确：

  • 价值：覆盖单测覆盖不到的真实问题——跨组件协作、真实事件序列（拖拽/键盘/焦点）、真实浏览器渲染（布局、动画、滚动）、构建产物/CDN 资源加载、双端（Vue/React）行为一致性。
  • 代价：单个用例秒级到十秒级；受网络、字体、动画、机器性能影响，天然更 flaky；失败时定位成本高，需 trace/截图回溯。

因此 E2E 不追求数量，而追求「每条用例都对应一个不能靠单测保证的断言」：

适合 E2E不适合 E2E（下沉到单测/集成）
组件文档页可访问、无编译错误单个函数的边界值
「展开下拉→选中→回显」交互链路Props 透传、类名断言
双端 demo 切换后行为一致分支条件覆盖
整页视觉回归局部 DOM 结构

对组件库而言，E2E 通常跑在文档站上——文档站的每个 demo 就是组件的真实用法，一条交互用例同时验证了「组件 + 文档集成 + 构建产物」三件事。

二、Playwright 配置实战 ​

2.1 一份可用的配置 ​

ts
// playwright.config.ts
import { defineConfig } from '@playwright/test';

const PORT = 4173;

export default defineConfig({
  testDir: './e2e',
  workers: 1,          // 视觉回归串行更稳；dev server 首轮编译慢
  timeout: 30_000,     // 单用例上限
  retries: 2,          // 失败重试，降 flaky 噪声；CI 建议 process.env.CI ? 2 : 0
  fullyParallel: false,
  use: {
    baseURL: `http://localhost:${PORT}`,   // 用例里 page.goto('/components/button/') 会用相对路径
    viewport: { width: 1280, height: 720 },
    navigationTimeout: 20_000,
    trace: 'on-first-retry',              // 首次重试即录 trace，兼顾磁盘与可调试性
    screenshot: 'only-on-failure',
  },
  expect: {
    toHaveScreenshot: {
      maxDiffPixelRatio: 0.02,            // 允许 2% 像素差异，抗反锯齿/字体渲染抖动
    },
  },
  webServer: {
    command: `pnpm --filter @xui-design/docs dev:e2e`,
    url: `http://localhost:${PORT}`,
    reuseExistingServer: !process.env.CI, // 本地复用已启的 dev server，CI 必须新建
    timeout: 60_000,                      // 首轮按需编译慢，放宽启动超时
  },
  reporter: [['list'], ['html', { open: 'never' }]],
});

2.2 关键字段说明 ​

  • testDir：用例根目录，通常独立于 src，避免被单测/构建卷入。
  • workers：并行数。视觉回归建议串行（workers: 1），并行渲染会引入像素抖动；纯交互测试可放开。
  • retries：重试是双刃剑——它能把真 flaky 掩盖成「偶尔通过」，也会让真 bug 在 CI 里拖到第 3 次才暴露。建议 CI 开 1-2 次重试，但把「第 1 次失败」记录下来持续治理，而不是默认容忍。
  • baseURL：所有 page.goto() 的相对路径都基于它，避免用例里硬编码端口。
  • webServer：Playwright 会自动拉起 dev server 再跑测试，跑完关掉。url 是就绪探针——Playwright 轮询该 URL 直到 200 才算启动完成，因此 url 必须是能返回 200 的页面地址，不能填不存在的路径。reuseExistingServer: !process.env.CI 让本地开发时复用已开着的服务器，CI 环境里强制新建，保证干净。

2.3 webServer 启动命令的坑 ​

webServer.command 必须走 package.json 里的 script，不要直接内联 vite/vitepress dev 的原始命令：

ts
// 正确：走 script，路径、环境变量、端口都在 script 里统一
webServer: { command: 'pnpm --filter @xui-design/docs dev:e2e', url: 'http://localhost:4173' }
json
// package.json
{
  "scripts": {
    "dev:e2e": "vitepress dev --port 4173 --strictPort"
  }
}
ts
// 错误：内联原始命令
webServer: { command: 'pnpm --filter @xui-design/docs exec vitepress dev --port 4173' }

原因：

  1. 端口一致性：baseURL 与 webServer.url 都写死了 4173，如果 script 里没加 --strictPort，端口被占用时 vite 会静默换到 4174，于是 Playwright 探针一直连不上 4173 而超时——报错信息是「Timed out waiting for …」这类误导性提示。加 --strictPort 让端口冲突直接失败，快速暴露问题。
  2. 环境变量与过滤范围：pnpm --filter <pkg> <script> 会在正确的包目录下、带正确的 env 执行，内联 exec … 容易丢掉工作目录与 .env。
  3. 可维护性：命令只在 script 里维护一份，测试与人工启动同一入口。

三、选择器策略 ​

选择器决定用例的稳定性。优先级从高到低：

优先级选择器说明
1getByRole / getByLabel / getByText面向可访问性语义，最稳，还能顺带验证 a11y
2getByTestId（data-testid）语义查询表达不了时的兜底，改动面可控
3稳定类名（BEM）如 .xui-select__trigger，与样式单一来源一致时可用
4CSS / 层级 / 位置最脆弱，尽量不用
ts
// 语义优先
await page.getByRole('button', { name: '提交' }).click();
await page.getByRole('tab', { name: 'React' }).click();

// 注意：组件内部结构用稳定 BEM 类名（与双端样式单一来源对齐）
const select = page.locator('.xui-select').first();
await select.locator('.xui-select__trigger').click();

// 脆弱：层级/位置/nth-child 依赖
await page.locator('div > div:nth-child(2) > button').click();

为什么 getByRole 优于 CSS：CSS 与 DOM 结构强耦合、结构一改用例就碎；role/name 来自用户可感知的语义（按钮、标签页、对话框），是组件对外的稳定契约，用 role 查询还顺带验证了元素是不是合格的可访问控件。Playwright 对 role 查询做了可访问性树的自动等待与可见性检查，比 locator(...).click() 的原始匹配更少踩竞态。

first() / nth() 的使用原则：一个页面常有多组同款 demo，用 page.locator('.xui-select').first() 指定「第一组」是有意的结构约定，需配合注释说明（如「第二个 demo 为多选模式」），否则后续加 demo 会让序数失效。

四、自动等待与稳定性 ​

Playwright 的核心竞争力是自动等待（auto-waiting）：所有 locator 动作（click/fill/check）与断言（expect(locator)）在执行前会等到元素满足动作前提——可见、稳定（停止动画）、可接收事件、未被遮挡。因此不要手写 waitForTimeout 来兜底，它会随机器变慢而假失败、随机器变快而浪费时间。

ts
// 自动等待：可见 + 可交互
await expect(select.locator('.xui-select__dropdown')).toBeVisible();
await select.locator('.xui-select__option').first().click();
await expect(select.locator('.xui-select__dropdown')).toBeHidden();

何时才允许等待：

  • 等待页面整体就绪：await page.waitForLoadState('networkidle')（尽量用 'load'/'domcontentloaded'，networkidle 在有轮询/长连接页面可能永不触发）。
  • 等待过渡动画/字体稳定再截图：视觉回归里用固定 waitForTimeout(800) 是可接受的，因为目的正是「等动画结束」，而非替代动作等待。
  • 断言渲染完成：优先 await expect(locator).toHaveCount(n) 或 toHaveText，而不是 sleep。

视口外元素的点击竞态：click() 会自动滚动到元素，但如果元素在滚动容器内、或页面有 position: fixed 的遮挡层，自动滚动后仍可能点到错误位置（Playwright 会在超时后报「element is outside of the viewport」或「intercepts pointer events」）。稳妥做法是先 await locator.scrollIntoViewIfNeeded() 再点：

ts
const block = page.locator('.xui-tree-select').nth(1);
await block.scrollIntoViewIfNeeded();
await block.locator('.xui-tree-select__trigger').click();

五、视觉回归 ​

视觉回归用整页/区域截图与基线图逐像素比对，捕捉「样式悄悄退化」。Playwright 的 toHaveScreenshot：

ts
const VISUAL_PAGES = [
  { path: '/', name: 'home' },
  { path: '/components/button/', name: 'button' },
  { path: '/components/steps/', name: 'steps' },
] as const;

for (const { path, name } of VISUAL_PAGES) {
  test(`${name} 页面截图对比`, async ({ page }) => {
    await page.goto(path);
    await page.waitForLoadState('networkidle');
    await page.waitForTimeout(800); // 等过渡动画与字体稳定
    await expect(page).toHaveScreenshot(`${name}.png`, {
      fullPage: true,
      animations: 'disabled', // 关键：冻结动画，否则每帧都在变
    });
  });
}

要点：

  • animations: 'disabled' 是必须项。CSS 动画/过渡正在运行时，前后两帧像素不同，比对必然失败；该选项会在截图瞬间冻结动画与过渡到稳定终态。
  • 容差参数：thread 决定单像素颜色差是否算「不同」（默认 0.2，基于 YIQ 色彩空间）；maxDiffPixels 是允许的绝对差异像素数；maxDiffPixelRatio 是比例（如 0.02 即 2%）。用比例抗整体抖动（字体渲染、抗锯齿），用绝对像素数抗小区域噪声，二者可同时设置、同时满足才通过。
  • 基线文件与平台后缀：默认快照路径模板含 snapshotSuffix，即平台名，因此同一页基线在不同系统上是不同文件——button-darwin.png（macOS）、button-linux.png（CI 的 Linux）。CI（Linux）需要 Linux 基线；只在 mac 上生成会使 CI 无基线可对。跨平台团队常见做法是：基线统一在 CI 容器内生成并提交，本地 mac 只做参考。
  • 更新基线：样式/布局有意变更后运行 --update-snapshots（简写 -u），并把新基线一并提交：
bash
pnpm e2e e2e/visual.spec.ts --update-snapshots        # 全量更新
pnpm e2e --update-snapshots=missing                   # 只补缺失基线（首次入库推荐）
  • 基线入库策略：基线图是产物，必须提交进仓库，否则 CI 无从比对。首次生成时若基线不齐，maxDiffPixelRatio 配合生成逻辑可减少「首跑即失败」的噪声。
  • 选页原则：优先截静态内容为主的页面（首页、Button、Steps），避开有随机内容/实时进度/上传动画的 demo（如带 mock 上传进度的页面），否则每次截图都不同。

六、测试分类：smoke / interactions / visual ​

把 E2E 分成三类文件，职责清晰、失败时定位快、可按需在 CI 分阶段执行：

6.1 smoke（冒烟）：页面可访问性 ​

覆盖「能不能打开、有没有编译错、有没有未捕获异常」，用数据驱动遍历组件列表，避免手写几十条重复用例：

ts
// 从与文档生成同源的数据模块读取 slug，保证覆盖不漏
const slugs = [...componentListSource.matchAll(/slug: '([^']+)'/g)].map((m) => m[1]);

for (const slug of slugs) {
  test(`页面 /components/${slug}/ 正常渲染`, async ({ page }) => {
    const errors: string[] = [];
    page.on('pageerror', (error) => errors.push(String(error)));

    const response = await page.goto(`/components/${slug}/`);
    expect(response?.status()).toBe(200);
    await expect(page.locator('main h1')).toBeVisible();            // 内容渲染完成
    await expect(page.locator('vite-error-overlay')).toHaveCount(0); // 无 Vite 编译错误遮罩
    expect(errors, `未捕获错误: ${errors.join('; ')}`).toEqual([]);
  });
}

要点：组件清单从单一数据源读取（与文档生成共用 component-list.ts），新增组件自动纳入冒烟，不会漏测。断言 vite-error-overlay 数量为 0 是 Vite 站点特有且高性价比的一条——它专抓「编译失败」。

6.2 interactions（交互）：关键链路 ​

覆盖用户可见的核心操作，断言状态迁移而非实现细节：

ts
test('单选：展开面板 → 选中选项 → 触发器回显', async ({ page }) => {
  await page.goto('/components/select/');
  const block = page.locator('.xui-select').first();
  await block.scrollIntoViewIfNeeded();

  await block.locator('.xui-select__trigger').click();
  await expect(block.locator('.xui-select__dropdown')).toBeVisible();

  const option = block.locator('.xui-select__option').first();
  const optionText = (await option.textContent()) ?? '';
  await option.click();

  await expect(block.locator('.xui-select__dropdown')).toBeHidden();
  await expect(block.locator('.xui-select__value')).toHaveText(optionText);
});

双端一致性：同一交互在 Vue/React tab 下都要用一次。文档站每个 demo 默认 Vue，点 getByRole('tab', { name: 'React' }) 切换后再跑一遍：

ts
test('TreeSelect React demo 同样可展开面板', async ({ page }) => {
  await page.goto('/components/tree-select/');
  await page.getByRole('tab', { name: 'React' }).first().click();
  const block = page.locator('.xui-tree-select').first();
  await block.locator('.xui-tree-select__trigger').click();
  await expect(block.locator('.xui-tree-select__panel')).toBeVisible();
});

复杂原生交互（拖拽）用 evaluate 在页面上下文构造 DataTransfer 并派发：

ts
await dropzone.evaluate((el) => {
  const dt = new DataTransfer();
  el.dispatchEvent(new DragEvent('dragenter', { bubbles: true, cancelable: true, dataTransfer: dt }));
});
await expect(dropzone).toHaveClass(/is-dragover/);

6.3 visual（视觉）：回归 ​

见第五节。三类文件分开的好处：冒烟失败=站点/构建坏了；交互失败=组件行为坏了；视觉失败=样式漂移了。CI 可把冒烟放在最前（最快暴露整体不可用）。

七、CI 集成与调试 ​

  • CI 运行：CI 环境用 reuseExistingServer: false 强制自建 server；用 --reporter=github（或 line）让失败直接标注到 PR；矩阵里按浏览器 project（chromium/firefox/webkit）分片。
  • 并行与分片：用例多时用 --shard=1/4 在多台机器分片，或用 Playwright 原生 fullyParallel + 多 worker。视觉回归例外，建议单 worker 串行。
  • trace / report：trace: 'on-first-retry' 在首次重试时录制 trace.zip；产物查看用：
bash
npx playwright show-trace test-results/<test>/trace.zip   # 逐步骤回放 DOM/网络/控制台
npx playwright show-report                               # 打开 HTML 报告
  • 失败后的标准排查顺序：先看 trace 的失败步骤截图与 DOM 快照 → 看该步网络请求是否 pending → 看 console/pageerror → 再判断是应用 bug、用例不稳、还是环境问题。

八、常见坑 ​

  1. Vue 异步更新需 await：点击触发的状态更新落在 Vue 更新队列（微任务）里。await locator.click() 只保证「点击动作完成」，不保证框架已重渲染。断言必须用会自动重试的 web-first assertion（await expect(locator).toBeVisible()），而不是点击后立刻 isVisible() 取一次布尔值。

  2. 视口外元素点击竞态：自动滚动后元素仍被固定层遮挡、或滚动容器内位置计算延迟，会报「outside of the viewport / intercepted by another element」。解法：await locator.scrollIntoViewIfNeeded() 后再点，或用 click({ force: true })（谨慎，会跳过可操作性检查）。

  3. networkidle 永不触发：站点若有轮询、SSE、长连接，网络永不「空闲」。改用 waitForLoadState('load') + 针对具体元素的 toBeVisible()。

  4. 视觉基线平台不匹配（-darwin / -linux）：本机 mac 生成的 xxx-darwin.png 在 Linux CI 上不被采用，导致 CI「基线不存在」而失败。统一在 CI 容器生成并提交 Linux 基线。

  5. 动画未冻结：截图时动画在跑，比对必失败。务必 animations: 'disabled'。

  6. -u 一把梭更新基线：CI 红了就跑 --update-snapshots 提交，会把真实的样式退化一起「更新」掉。先看 diff 再更新，确认变化是有意为之。

  7. 重试掩盖 flaky：retries 让偶发失败的用例最终绿灯，但根因（等待不足、时序竞态）没解决。应把重试当作降噪而非修复，持续统计并治理 flaky。

  8. 只测 Vue 不测 React（或反之）：双端组件库若交互用例只跑默认的 Vue tab，React 适配层的回归不会被发现。关键链路必须切 tab 各跑一次。

面试要点 ​

  1. E2E 和单测的边界怎么划？ 答：E2E 只覆盖真实浏览器、跨组件链路与视觉回归这类单测盲区；逻辑与边界下沉到 Vitest，避免金字塔倒置。
  2. Playwright 的自动等待是什么？ 答：动作与断言执行前会等元素可见、稳定、可交互、未被遮挡，因此不需要手写 sleep。
  3. 为什么 webServer.command 要走 package.json script？ 答：端口/env/工作目录在 script 里统一维护；且必须 --strictPort，否则端口被占用时静默换端口导致就绪探针超时，报错误导。
  4. 选择器为什么首选 getByRole？ 答：它基于可访问性语义、与 DOM 结构解耦、最稳定，并顺带验证 a11y；CSS/层级选择器结构一变就碎。
  5. 视觉回归为什么必须 animations: 'disabled'？ 答：动画/过渡在截图时会持续变帧，像素比对必然不一致，需冻结到稳定终态。
  6. maxDiffPixelRatio 和 maxDiffPixels 区别？ 答：前者是允许差异像素占页面总像素的比例，后者是绝对像素数，两者可同时生效、需同时满足。
  7. 为什么本机生成的基线 CI 用不了？ 答：Playwright 快照文件名带平台后缀（-darwin/-linux），CI 是 Linux，需要 Linux 基线，通常统一在 CI 容器生成并提交。
  8. 点击后为什么不能直接断言 isVisible()？ 答：Vue/React 的重渲染在微任务里，click 完成不代表已重渲染；要用会自动重试的 web-first assertion（await expect(...).toBeVisible()）。
  9. retries 是好事还是坏事？ 答：能降 flaky 噪声，但也会掩盖真 bug 与真竞态；应记录首次失败并持续治理，而非无脑依赖重试。
  10. trace 有什么用？ 答：录制每个步骤的截图、DOM 快照、网络与控制台，可在失败后逐帧回放，是 E2E 失败定位的核心工具。
