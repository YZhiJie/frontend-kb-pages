架构约束与依赖治理 ​

测试保证「功能对不对」，架构约束保证「结构会不会随时间烂掉」。团队从 3 人涨到 10 人、AI 开始批量产出代码后，唯一挡得住架构退化的不是规范文档，而是会失败的 CI 红线。本文按「为什么需要 → dependency-cruiser → 反向验证 fixture → 契约对齐 → verify 门禁 → 拦截 AI → 渐进式治理 → 常见坑」组织。上游测试见 单元测试（Vitest） 与 端到端测试（Playwright）。

一、为什么需要架构约束 ​

架构腐化不是一次性的，而是每一次「就这一次，先这样」的累积：

  • 适配层图快直接 import 另一个适配层的内部实现，双端开始互相耦合。
  • 页面直接依赖底层工具包，绕过分层，底层一改牵动全站。
  • 出现循环依赖：A import B、B 又 import A，初始化顺序与 chunk 变得不可预测。
  • React 端悄悄多出一个契约里没有的 prop，Vue 端没有对应实现，双端 API 分叉。

这些问题单测测不出、人眼 review 易漏，在 AI 批量生成代码时扩散更快。结论：架构约束必须机器化、必须以 error 级别在 CI 中失败——能被绕过的约束等于没有约束。

分层依赖的方向必须单向，越上层越「业务」，只能依赖更下层：

apps（应用 / 文档站）
  ↓ 只能依赖
pages（页面 / 组合层）
  ↓ 只能依赖
shared（纯逻辑 / 契约 / 基础能力）—— 不依赖任何上层

二、dependency-cruiser：把依赖规则变成 CI 红线 ​

dependency-cruiser 解析全仓模块依赖图（支持 TS/JS/.vue/.tsx），用 forbidden 规则对图做断言；规则命中且 severity: 'error' 时进程非零退出，天然成为门禁。

js
// .dependency-cruiser.cjs
module.exports = {
  forbidden: [
    {
      name: 'no-circular',
      severity: 'error',
      comment: '循环依赖会造成初始化顺序不可预测、打包 chunk 错乱',
      from: {},
      to: { circular: true },
    },
    {
      name: 'shared-is-leaf',
      severity: 'error',
      comment: 'shared 是分层最底部，不得反向依赖上层',
      from: { path: '^packages/shared' },
      to: { path: '^(apps|pages)' },
    },
    {
      name: 'no-layer-skip',
      severity: 'error',
      comment: '单向依赖：apps 只能依赖 pages，不得越过 pages 直接依赖 shared',
      from: { path: '^apps' },
      to: { path: '^packages/shared' },
    },
    {
      name: 'adapters-are-isolated',
      severity: 'error',
      comment: 'Vue / React 适配层之间不得互相依赖（跨框架耦合是架构红线）',
      from: { path: '^packages/vue' },
      to: { path: '^packages/react' },
    },
    {
      name: 'no-npm-in-leaf',
      severity: 'error',
      comment: 'shared / core 只允许零运行时依赖，引入 npm 包需显式评审',
      from: { path: '^packages/(shared|core)' },
      to: { dependencyTypes: ['npm', 'npm-optional', 'npm-peer'] },
    },
    {
      name: 'no-deep-import-into-packages',
      severity: 'error',
      comment: '跨包只走包的公开入口，禁止深路径 import 内部文件',
      from: { path: '^(apps|pages)' },
      to: { path: '^packages/[^/]+/src/(?!index\\.ts)', dependencyTypes: ['local', 'localmodule'] },
    },
    {
      name: 'no-orphans',
      severity: 'warn',
      comment: '孤立模块（既无人依赖、也不依赖别人）多半是废弃代码',
      from: { orphan: true, pathNot: ['\\.d\\.ts$', '__tests__', 'scripts/'] },
      to: {},
    },
  ],
  options: {
    doNotFollow: { path: 'node_modules' },
    exclude: { path: '(\\.test\\.(ts|tsx)$|__tests__|/dist/|/coverage/)' },
    tsConfig: { fileName: 'tsconfig.base.json' },
  },
};

要点：

  • 只有 severity: 'error' 拦得住：warn 只是提示、CI 不失败。分层与跨框架耦合这类结构性红线必须 error，no-orphans 等治理型规则可先用 warn 观察再收紧。
  • from / to 双重匹配：from.path 限定「谁」，to.path 限定「依赖谁」；to.dependencyTypes 精确到依赖类型——['npm'] 是第三方包、['local','localmodule'] 是仓库内模块。
  • 必须配 tsConfig：否则 @/x 这类别名路径被判为「无法解析」，规则形同虚设或大量误报。
  • 必须 exclude 测试与产物：否则 dist/coverage/__tests__ 里的依赖会制造海量噪声。
json
// package.json
{
  "scripts": {
    "arch:check": "depcruise --config .dependency-cruiser.cjs apps packages",
    "arch:graph": "depcruise --config .dependency-cruiser.cjs --output-type dot apps packages | dot -T svg > docs/dep-graph.svg"
  }
}

默认输出 err 报告（命中 error 即非零退出）；--output-type dot 导出依赖图，--output-type json 便于脚本统计趋势。

三、反向验证：11 个架构 fixture ​

红线警戒：规则写错/写漏会「全绿通过」，那是最危险的假安全感。必须为规则本身写测试——构造故意违规的 fixture，逐一验证「该违规确实被捕获」。若某 fixture 不再失败，说明规则失效。这是对质量门禁的变异测试（negative testing）。

ts
// scripts/verify-arch-fixtures.ts —— 断言每条规则「反向用例必须失败」
const fixtures = [
  { dir: 'fixtures/01-circular', expectRule: 'no-circular' },
  { dir: 'fixtures/02-shared-to-app', expectRule: 'shared-is-leaf' },
  { dir: 'fixtures/03-app-skip-layer', expectRule: 'no-layer-skip' },
  // ... 其余 8 个
];

let failed = false;
for (const f of fixtures) {
  let output = '';
  let exitCode = 0;
  try {
    output = execFileSync('depcruise', ['--config', '.dependency-cruiser.cjs', f.dir], { encoding: 'utf-8' });
  } catch (err) {
    exitCode = (err as { status?: number }).status ?? 1;   // 非零退出 = 规则命中，正是期望
    output = String((err as { stdout?: string }).stdout ?? '');
  }
  const caught = exitCode !== 0 && output.includes(f.expectRule);
  if (!caught) {
    console.error(`FAIL ${f.dir}: 规则 ${f.expectRule} 未命中，门禁可能已失效`);
    failed = true;
  }
}
process.exit(failed ? 1 : 0);

关键：fixture 是「必须报错」的样本，脚本断言报错发生了。规则被误删/放宽会导致 fixture 假绿、脚本变红——把门禁本身也纳入质量体系。

四、契约对齐：双端 API 机器化比对 ​

跨框架组件库最大风险是双端 API 悄悄分叉（React 多一个 onFocus、Vue 默认值对不上）。靠人眼不可靠，必须机器化。以 @xui-design/core 的运行时 spec（buttonSpec 等）为唯一契约基准：

  • Vue 端（运行时读取）：从已构建的 packages/vue/dist/index.mjs 读取组件的 props（含 default）与 emits；SFC 的 props/emits 只有编译后才有运行时可读元数据。
  • React 端（源码静态解析）：函数组件无运行时 props 元数据，用轻量正则从 .tsx 的 export function X({ ...props }) 解构里提取键与内联默认值。
  • 三方比对：契约 × Vue 运行时 × React 源码。
ts
// scripts/contract-test.ts（核心判定，节选）
const eventToReactProp = (e: string) => `on${e[0].toUpperCase()}${e.slice(1)}`;

// 事件：契约事件 E → Vue emits 必含 E；React props 必含 on+首字母大写(E)
for (const event of Object.keys(spec.events)) {
  if (!vueEmits.includes(event)) fail(`${name}: 事件 ${event} 未在 Vue emits 声明`);
  if (!reactProps.has(eventToReactProp(event))) fail(`${name}: 事件 ${event} 未在 React props 声明`);
}

// 双端不得引入契约之外的 prop / 事件（框架惯用法白名单豁免）
for (const event of vueEmits) {
  if (spec.events[event] || event.startsWith('update:')) continue; // update:* 是 defineModel 语法糖
  fail(`${name}: Vue 存在契约之外的事件 ${event}`);
}

// 默认值：双端交集逐项 Object.is 比对，且各自还要与契约默认值一致
for (const key of corePropKeys) {
  if (isModelGoverned(key)) continue; // v-model 惯例豁免
  if (!Object.is(vueProps.get(key), reactProps.get(key))) fail(`${name}: 默认值 ${key} 双端不一致`);
  if (!Object.is(vueProps.get(key), coreDefaults[key])) fail(`${name}: Vue 默认值偏离契约`);
}

要点：契约是唯一真相，默认值/事件名以 core spec 为准，适配层只是映射；框架惯用法显式豁免（Vue 的 v-model/update:*、React 的 children/ref/render*）不算分叉，用白名单函数（isModelGoverned、isReactIdiomProp）隔离，避免误报；适配层一旦新增契约外 API（人工或 AI 写的）契约测试立刻失败——这是拦住双端长歪的关键；Vue 端读 dist，改完源码必须先 build，CI 里 build 排在契约测试之前。

五、verify 门禁串联 ​

单一门禁各自为战会漏。把「静态检查 → 架构 → 构建 → 审计 → 测试」串成一条 verify：

json
// package.json
{
  "scripts": {
    "verify": "pnpm type-check && pnpm lint && pnpm arch:check && pnpm build && pnpm audit:size && pnpm test:coverage && pnpm exec tsx scripts/contract-test.ts",
    "arch:check": "depcruise --config .dependency-cruiser.cjs apps packages",
    "audit:size": "pnpm exec tsx scripts/check-bundle-size.ts"
  }
}

顺序讲究「先便宜、先快、先能中断」：

yaml
# .github/workflows/ci.yml（节选）
- run: pnpm install --frozen-lockfile
- name: Lint
  run: pnpm lint
- name: Type check
  run: pnpm type-check
- name: Architecture check   # 架构红线，失败即停，别把结构问题带到后面
  run: pnpm arch:check

  run: pnpm test:coverage
- name: Build
  run: pnpm build
- name: Check bundle size    # 构建后审计体积

- name: Contract test        # 依赖 build 产物，必须排在其后
  run: pnpm exec tsx scripts/contract-test.ts

本地/远端两层：husky pre-commit 只对改动文件跑 lint-staged（秒级），完整 verify 交给 CI，兼顾体验与严谨。

六、用门禁拦截 AI 生成代码的架构违规 ​

AI 会快速写出「语法正确、功能可用、结构错误」的代码，常见违规：①跨框架耦合（Vue 适配层 import React 工具）；②越层依赖；③契约外 API（React 加了 onHover、Vue 没有）；④深路径 import 绕过包入口；⑤循环依赖；⑥改完忘 build，契约测试读旧 dist。

机器化门禁正是应对 AI 的正确姿势，因为 AI 无法「说服」CI：no-layer-skip/adapters-are-isolated/no-circular 拦架构违规，contract-test 让契约外 API 出现在任一端即失败，type-check 拦类型破坏，check-bundle-size 拦「偷偷引大依赖」。落地要点是：prompt 里就声明约束（不得跨适配层依赖、不得新增契约外 prop、必须走包入口），让 AI 一次产出就接近合规，而不是靠 CI 反复打回。

一句话：AI 提速只能建立在「约束可被机器校验」之上，否则提的是腐化速度。

七、渐进式治理老项目：先立红线，再逐步清理 ​

老项目一动就是几百条违规，全开 error 会让 CI 永远红、团队直接关掉门禁。正确路径是基线冻结 + 增量红线：

  1. 生成基线：把现存违规固化成快照。
bash
depcruise --config .dependency-cruiser.cjs --output-type baseline apps packages > known-violations.json
  1. CI 只拦新增：与基线相同的违规不报、新增的才失败。
json
{ "scripts": { "arch:check": "depcruise --config .dependency-cruiser.cjs --ignore-known known-violations.json apps packages" } }
  1. 逐步缩小基线：每清理一批就重新生成一次（数字只减不增），并对本次改动的新文件强制全规则通过。
  2. 收口：基线归零后去掉 --ignore-known，全量规则以 error 生效。
  3. 配套：先对新增文件（origin/master 之后的改动）开严格规则，存量文件豁免——让新代码从第一天就干净。

「存量冻结、增量红线、逐步归零」能让老项目在不中断交付的前提下，把架构约束真正落地。

八、常见坑 ​

  1. 规则写了 warn 却以为拦得住：只有 severity: 'error' 会让 CI 非零退出；结构性红线必须 error。
  2. 规则写错/写漏导致假绿：没有 fixture 反向验证，你无法确认规则真的生效——「全绿」可能只是规则没匹配上。
  3. 契约定在源码而非常量：契约若散落在双端各自实现里，就没有唯一基准；必须有框架无关的 core spec 作真相源。
  4. 契约测试静默读旧产物：Vue 端从 dist 读取，忘 build 会拿旧产物比对，出现「改了源码却依旧通过」的假绿。
  5. 别名路径未解析：未配 tsConfig 时 @/x 被判「无法解析」，规则形同虚设或大量误报。
  6. 把测试与产物纳入判定：未 exclude dist/coverage/__tests__ 会制造海量噪声。
  7. 老项目一把梭全开 error：CI 长期红会导致团队弃用门禁；用 --ignore-known 基线 + 增量红线渐进治理。
  8. 体积门禁只在本地跑：体积会缓慢膨胀，必须进 CI 且预算「只增不减地收紧」，每次上调都要走评审。
  9. 豁免白名单越滚越大：isModelGoverned 之类豁免若无边界会退化成「什么都放过」，豁免项要有注释、有评审、能收敛。

面试要点 ​

  1. 为什么架构约束一定要进 CI 且是 error 级？ 答：规范靠自觉、review 靠人眼都会漏；只有会失败的 CI 红线不可绕过，面对 AI 批量产出更是如此。
  2. dependency-cruiser 能拦哪些问题？ 答：循环依赖、分层越级依赖、跨框架耦合、底层引入 npm 依赖、深路径 import 内部文件、孤立模块等，按 error/warn 分级。
  3. 怎么保证「规则本身」没写错？ 答：为每条规则造一个故意违规的 fixture，脚本断言它必须被捕获；规则被放宽会让 fixture 假绿、脚本变红，等于给门禁做反向测试。
  4. 双端契约对齐怎么做？ 答：以 core spec 为唯一基准，Vue 从 dist 读运行时 props/emits、React 从 .tsx 静态解析，比对事件名、prop 集合与默认值，任一越界即失败。
  5. 适配层新增契约外 prop 会怎样？ 答：契约测试直接失败并挂 CI，这是拦住双端分叉的关键；框架惯用法（v-model、children/ref/render*）走白名单豁免。
  6. verify 门禁为什么要固定顺序？ 答：先跑最快最便宜、最能中断的（typecheck/lint/arch），再跑测试与构建；契约测试依赖构建产物，必须排在 build 之后。
  7. 老项目 300 条违规怎么上约束？ 答：--output-type baseline 生成基线 + --ignore-known 只拦新增，配合「新文件严格、存量冻结」，清理到基线归零再全量 error。
  8. 体积预算为什么也要进 CI？ 答：体积会随时间缓慢膨胀，必须进 CI 且只增不减地收紧，预算上调要走评审，否则门禁被逐步稀释。
  9. AI 生成的代码怎么防架构退化？ 答：prompt 里声明约束，再用 dependency-cruiser + 契约测试 + 类型/体积审计把约束机器化，让 AI 无法绕过。
  10. 契约测试为什么读 dist 而不是源码？ 答：SFC 的 props/emits 只有编译后才有运行时可读元数据；代价是必须先 build，忘 build 会静默比对旧产物产生假绿。
