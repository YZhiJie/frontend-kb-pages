单元测试（Vitest） ​

单元测试是质量门禁里成本最低、执行最快的一层。本文按「金字塔 → Vitest 与 Jest 差异 → 配置与环境 → 断言与 mock → 双端组件测试 → 异步与 Teleport → 关键路径 → 覆盖率门禁 → 常见坑」组织。质量模块其他页面见 端到端测试（Playwright） 与 架构约束与依赖治理。

一、测试金字塔与前端测试范围 ​

        ▲  少 / 慢 / 贵 / 信心高
   E2E（Playwright）        真实浏览器 + 真实交互 + 全链路
   集成（Testing Library）  真实组件树 + 真实 DOM，验证协作
   单元（Vitest）           纯函数 / 逻辑层，毫秒级、可大规模并发
        ▼  多 / 快 / 便宜
层级运行环境耗时关注点定位成本
单元（Vitest）node / jsdom< 5ms纯逻辑、分支、边界极低，直指函数
集成（VTU / RTL）jsdom10-100ms渲染、Props 透传、事件低，指向组件
E2E（Playwright）真实浏览器秒级业务链路、视觉回归高，需 trace

对跨框架组件库，金字塔落成四层：shared（框架无关纯逻辑，node 环境，最该高覆盖）→ core（契约 spec 数据）→ vue/react（薄适配层，VTU/RTL 验渲染与事件映射）→ 文档站 E2E 兜底。越靠近纯逻辑越严，适配层只测「Props 透传 + 事件映射 + 渲染结果」。

二、为什么选 Vitest：与 Jest 的差异 ​

维度JestVitest
转换管线babel-jest / ts-jest复用 Vite 的 ESM 管线（esbuild）
原生 ESM需 --experimental-vm-modules原生支持，import 与 vi.mock 一致
并发worker 池tinypool 线程池，默认多线程
配置复用独立转换配置共享 Vite 的 resolver / alias / plugins
.vue / TSX需额外转换装 @vitejs/plugin-vue 即可
API 兼容—兼容 describe/it/expect 及大部分 jest API
覆盖率istanbul（instrument 源码）v8 原生覆盖率（行/分支口径与 istanbul 略不同）

核心收益：组件库源码本就跑在 Vite 生态，Vitest 直接吃同一套插件与 alias，不用维护第二套转换配置。需清醒的局限：jsdom 是 DOM 模拟实现，布局（getBoundingClientRect 恒为 0）、disabled 事件派发、CSS 计算值都与真实浏览器有差异——这些盲区交给 E2E。

三、Vitest 配置与测试环境 ​

3.1 一份可用的根配置 ​

ts
// vitest.config.ts
import { defineConfig } from 'vitest/config';
import vue from '@vitejs/plugin-vue';

export default defineConfig({
  plugins: [vue()],                 // 解析 .vue，跑全仓测试
  test: {
    globals: true,                  // 免 import describe/it/expect
    environment: 'jsdom',           // 适配层需要 DOM
    include: ['packages/**/src/**/__tests__/**/*.test.ts'],
    restoreMocks: true,             // 每个用例后自动还原 spy，防串味
    coverage: {
      provider: 'v8',
      reporter: ['text', 'lcov', 'html'],
      reportsDirectory: './coverage',
      include: ['packages/*/src/**/*.ts'],
      exclude: [
        'packages/*/src/**/__tests__/**',
        'packages/*/src/**/*.d.ts',
        'packages/*/src/**/index.ts', // 纯 re-export，计入会虚高
      ],
      thresholds: { lines: 90, functions: 90, statements: 90, branches: 85 },
    },
  },
});

要点：include 用 __tests__ 目录约定，测试与源码同层；restoreMocks: true 是性价比最高的一行；exclude 剔除 index.ts 与 .d.ts 避免覆盖率虚高；thresholds 写入后 vitest run --coverage 低于阈值即非零退出，天然成为 CI 门禁。

3.2 测试环境：jsdom 还是 node ​

test.environment 是全局默认，逐文件覆盖优先级更高。纯逻辑测试必须在文件首行（任何 import 之前）声明 node 环境：

ts
// packages/shared/src/components/button/__tests__/use-button-logic.test.ts
// @vitest-environment node

import { describe, expect, it, vi } from 'vitest';
import { createButtonLogic } from '../use-button-logic';

describe('createButtonLogic', () => {
  it('disabled 状态下点击不触发回调', () => {
    const onClick = vi.fn();
    createButtonLogic({ disabled: true, onClick }).handleClick({} as MouseEvent);
    expect(onClick).not.toHaveBeenCalled();
  });
});

为什么非要用 node：node 环境没有 document/window 全局。逻辑层一旦误用 DOM，在 jsdom 里会静默跑通、生产里直接炸；在 node 环境下测试立刻报 document is not defined——把「污染框架无关层」变成能即刻发现的错误，且无 jsdom 初始化开销、更快。大型仓库还可用 test.projects（旧版 workspace）按包拆分环境与阈值。

四、断言与 Mock ​

4.1 常用断言与异步断言 ​

ts
expect(value).toBe(x);              // Object.is 严格相等
expect(obj).toEqual({ a: 1 });      // 递归结构相等
expect(fn).toHaveBeenCalledTimes(1);
expect(fn).toHaveBeenCalledWith(expect.objectContaining({ id: 1 }));
await expect(promise).resolves.toBe(1);
await expect(promise).rejects.toThrow('boom');

4.2 vi.fn 与 vi.spyOn ​

ts
const onClick = vi.fn();
const fetchUsers = vi.fn().mockResolvedValue([{ id: 1 }]);
const twice = vi.fn().mockImplementation((n: number) => n * 2);
const spy = vi.spyOn(Math, 'random').mockReturnValue(0.5); // restoreMocks=true 时用例结束自动还原

4.3 vi.mock 的提升与 vi.hoisted ​

vi.mock 会被提升到文件顶部（早于所有 import），因此工厂函数里不能引用文件级变量（尚未初始化），需要共享桩时用 vi.hoisted：

ts
import { vi, describe, it, expect } from 'vitest';
import { fetchList } from '../api';

const mocks = vi.hoisted(() => ({ fetchList: vi.fn() }));
vi.mock('../api', () => ({ fetchList: mocks.fetchList }));

it('加载成功后状态为 success', async () => {
  mocks.fetchList.mockResolvedValue([{ id: 1 }]);
  expect(mocks.fetchList).toHaveBeenCalledOnce();
});

坑：vi.mock 是按路径全量替换，工厂里漏写模块的其它导出，会让它们变成 undefined，报错信息很绕。

4.4 定时器 ​

ts
beforeEach(() => vi.useFakeTimers());
afterEach(() => vi.useRealTimers());

it('debounce 300ms 后只触发一次', () => {
  const fn = vi.fn();
  const debounced = debounce(fn, 300);
  debounced(); debounced(); debounced();
  expect(fn).not.toHaveBeenCalled();
  vi.advanceTimersByTime(300);       // 推进虚拟时钟
  expect(fn).toHaveBeenCalledOnce();
});

vi.setSystemTime(new Date('2026-01-01')) 可固定 Date.now()。坑：fake timers 接管 setTimeout/Date/queueMicrotask，但不推进微任务——被测代码里真实 await 的 Promise 链要用 await vi.advanceTimersByTimeAsync(300) 或 flushPromises。

mock 清理：clearMocks 只清调用记录、mockReset 连实现一起重置、restoreMocks 还原被 spy 替换的原始实现（推荐默认开）、unstubGlobals 还原 vi.stubGlobal。

五、双端组件测试：VTU 与 RTL ​

VTU（@vue/test-utils）与 RTL（@testing-library/react）的 API 对照：

关注点VTU（Vue）RTL（React）
挂载mount / shallowMountrender
查询wrapper.find(selector)screen.getByRole 等
改 Propsawait wrapper.setProps()rerender()
触发事件await wrapper.trigger('click')fireEvent.click() / userEvent.click()
断言事件wrapper.emitted('click')断言 vi.fn() 回调
卸载enableAutoUnmount(afterEach)cleanup()
ts
import { mount, enableAutoUnmount } from '@vue/test-utils';
enableAutoUnmount(afterEach); // Teleport / 全局副作用组件较多时统一卸载

const wrapper = mount(Button, { props: { type: 'primary' }, slots: { default: '确定' } });
expect(wrapper.classes()).toContain('xui-button--primary');
expect(wrapper.find('.xui-button__content').text()).toBe('确定');

await wrapper.setProps({ disabled: true }); // 异步，必须 await
await wrapper.trigger('click');
expect(wrapper.emitted('click')).toBeUndefined();
tsx
import { render, screen, fireEvent } from '@testing-library/react';
import '@testing-library/jest-dom/vitest'; // 引入 toBeDisabled / toHaveClass 等匹配器

it('loading 时禁用点击', () => {
  const onClick = vi.fn();
  render(<Button loading onClick={onClick}>确定</Button>);
  const btn = screen.getByRole('button');
  expect(btn).toBeDisabled();
  fireEvent.click(btn);
  expect(onClick).not.toHaveBeenCalled();
});

要点：VTU 的 trigger/setProps 返回值是 Promise，必须 await，否则断言跑在更新前（假失败或假通过）；mount 渲染真实子树，适配层优先用 mount；RTL 的 screen.* 默认根是 document.body，对 Portal 组件天然友好；userEvent 比 fireEvent 更接近真实交互（含 focus/pointer/keyboard、自动 await），默认优先 userEvent，仅需强制派发时用 fireEvent；对 ref 命令式方法（如 ref.current.focus()）需手动包 act()。

六、异步断言与 microtask 时机 ​

大量组件测试失败源于「断言早于更新」。正确姿势三类：框架更新用 await nextTick() / await wrapper.trigger(...) / waitFor；Promise 链用 flushPromises（VTU 导出）；轮询式断言优先用自动重试的 findByRole / waitFor，而不是 await new Promise(r => setTimeout(r, 100)) 定时等待。

ts
// Vue：触发异步校验后清空微任务
await wrapper.find('form').trigger('submit');
await flushPromises();
expect(wrapper.text()).toContain('用户名已存在');
// React：轮询式断言，默认 1000ms 超时、50ms 间隔
await waitFor(() => expect(screen.queryByRole('alert')).toHaveTextContent('用户名已存在'));

原因：Vue 更新队列与 React act 批处理都在微任务里；若代码是 await api() 后再 setState，一次 await 只推进一档，链式 await（或 flushPromises）才能排空嵌套微任务。断言写错时机 = 本地偶过、CI 偶挂的 flaky。

七、Teleport / Portal 组件测试 ​

弹窗/抽屉/Tooltip 内容渲染到 document.body，在 wrapper/container 内查询查不到，必须直接查 document。

ts
it('teleport 到 body：弹窗不在组件树内', async () => {
  const wrapper = mount(Modal, { props: { visible: true } });
  await nextTick();

  const modal = document.body.querySelector('.xui-modal');
  expect(modal).not.toBeNull();
  expect(wrapper.element.contains(modal)).toBe(false); // 关键：不在组件树内
});

RTL 侧：screen.getByRole('dialog') 默认就查 body。坑：Teleport 内容不在 wrapper 内，wrapper.unmount() 未必清理 body 节点，必须 enableAutoUnmount(afterEach)（Vue）或确保 cleanup()（RTL），否则用例间 DOM 残留，出现「第 2 个用例查到 2 个弹窗」；受控显隐要走完整路径（以 visible: false 挂载再 setProps 打开），才会命中「watch 注册 keydown / 滚动锁」分支，直接以 visible: true 挂载会跳过这段逻辑。

八、关键路径测试：受控、异步校验、虚拟滚动 ​

受控组件：重点是「受控语义」——外部状态不变时组件不得自行改 DOM 值。要同时断言「上报值」与「实际 DOM 值」，才能区分真受控与把 value 当 defaultValue 的伪受控：

ts
it('受控：父级未回写时 DOM 值保持受控值', async () => {
  const wrapper = mount(Input, { props: { modelValue: 'abc' } });
  const input = wrapper.find('input');
  await input.setValue('xyz');
  expect(wrapper.emitted('update:modelValue')?.[0]).toEqual(['xyz']); // 已上报
  expect((input.element as HTMLInputElement).value).toBe('abc');       // 但 DOM 未变
});

异步校验：先断言 pending 态，flushPromises 后再断言最终结果。虚拟滚动：测试重点是窗口计算（给定 scrollTop/视口/行高命中哪些行），属纯逻辑，放 shared 层 node 环境测；组件层只验证「DOM 只渲染可见窗口行数、滚动后区间更新」，不要在 jsdom 断言真实像素位置（getBoundingClientRect 恒 0），那部分交给 E2E。

ts
// @vitest-environment node
it('scrollTop=1000、行高 40、视口 400 → 区间含 overscan', () => {
  const range = computeRange({ scrollTop: 1000, viewport: 400, itemHeight: 40, overscan: 2 });
  expect(range.start).toBe(23); // 25 - overscan 2
});

层级LinesBranches说明

vue / react（适配层）≥ 85%≥ 80%渲染分支多，适度放宽

yaml
# .github/workflows/ci.yml（节选）
- name: Test with coverage
  run: pnpm test:coverage   # 内部即 vitest run --coverage，阈值不达标非零退出

要点：阈值写在配置里而非口头约定，vitest run --coverage 自动 fail，无需 CI 二次判断；lcov 上报 codecov 可做 PR 增量覆盖率，避免「总量够但新代码零覆盖」；覆盖率是下限而非目标——为凑百分比去测无分支 getter 是坏味道，重点保证关键分支、边界与错误路径。

十、常见坑 ​

10.1 disabled 元素不派发事件（双端行为不同步） ​

  • 真实浏览器：点击 disabled 的 <button> 不派发 click 事件（HTML 规范），任何 onClick/@click 都不执行。
  • jsdom 不实现这套阻断：dispatchEvent / VTU trigger('click') / RTL fireEvent.click 都照常派发。
  • 后果：若「禁用不可点」只依赖浏览器原生阻断，测试里事件照样派发——Vue 的 @click 会被命中，React 合成事件系统可能把它丢弃，两端同一用例表现不一致（假通过 / 假失败）。
  • 正确做法：把 disabled 判定下沉到框架无关逻辑层（createButtonLogic 先判 disabled 再调 onClick），双端适配层都调用。测试同时断言两件事：①元素带 disabled 属性（面向浏览器）；②逻辑层拦截（面向一致性与测试）。
ts
it('disabled：逻辑层拦截点击', () => {
  const onClick = vi.fn();
  createButtonLogic({ disabled: true, onClick }).handleClick({} as MouseEvent);
  expect(onClick).not.toHaveBeenCalled();
});

10.2 fireEvent 绕过原生 disabled ​

fireEvent.click 是「硬派发」，不检查 disabled、pointer-events、可见性；userEvent.click 模拟真实交互，遇 pointer-events: none 报错、遇 disabled 跳过。不要用 fireEvent 派发成功来证明功能正常——那只能证明处理器被调用；交互真实性交给 userEvent 或 E2E。

10.3 忘记 await ​

await wrapper.trigger() / await wrapper.setProps() / await userEvent.click() 漏 await 是最常见的 flaky 来源，表现为「断言时 DOM 还没更新」。

10.4 快照测试的取舍 ​

  • 适合：稳定序列化输出——契约 spec、格式化后的配置、错误消息结构。
  • 不适合：整棵组件 DOM 树。UI 一改，toMatchSnapshot 的大文本 diff 无人细看，容易「无脑 -u」把 bug 一起点掉，退化成「记录现状」而非「验证正确」。
  • 替代：用语义断言（toBeInTheDocument/toHaveClass/toHaveTextContent）表达意图；确需快照时用 toMatchInlineSnapshot 写进文件，逼 review 看到变化。

面试要点 ​

  1. 为什么选 Vitest 而不是 Jest？ 答：直接复用 Vite 的 ESM + 插件管线，.vue/TSX 零额外转换配置，原生支持 ESM、多线程并发、watch 只重跑相关用例。
  2. 测试金字塔怎么理解？ 答：越靠下越多越快越便宜、信心越低；单测覆盖逻辑与边界，集成验证协作，E2E 只覆盖关键链路与视觉回归。
  3. 纯逻辑为什么要在 node 环境测？ 答：文件首行 // @vitest-environment node 让 document 不存在，逻辑层误用 DOM 立即报错，保证框架无关层不被污染且更快。
  4. Vue 里为什么必须 await wrapper.trigger()？ 答：trigger/setProps 走 Vue 异步更新队列，不 await 会在 DOM 更新前断言，导致 flaky。
  5. Teleport/Portal 组件怎么测？ 答：内容渲染到组件树外的 document.body，要查 document（Vue）或用 screen（RTL 默认查 body），并统一在 afterEach 卸载防 DOM 残留。
  6. vi.mock 工厂里为什么不能用文件级变量？ 答：vi.mock 提升到 import 之前执行，变量尚未初始化；共享桩要用 vi.hoisted。
  7. fake timers 下 advanceTimersByTime 为何可能不生效？ 答：它只推进定时器不推进微任务；真实 await 的 Promise 链要用 advanceTimersByTimeAsync 或 flushPromises。
  8. disabled 按钮为什么在测试里还能触发处理器？ 答：jsdom 不实现原生 disabled 的事件阻断，trigger/fireEvent 会照常派发；解法是把 disabled 判定下沉到框架无关逻辑层，双端共享。
  9. fireEvent 与 userEvent 区别？ 答：fireEvent 底层硬派发、不检查 disabled/pointer-events；userEvent 模拟真实交互序列且自动 await，默认优先 userEvent。
  10. 覆盖率到 90% 就够了吗？ 答：不够。覆盖率是下限，重点看关键分支、边界与错误路径；凑百分比测无分支 getter 是坏味道。
