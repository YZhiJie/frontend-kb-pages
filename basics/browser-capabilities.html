浏览器能力与高复杂度交互场景 ​

对应 JD：思维巡航 #11 职责第 5 条「音视频、实时交互、富文本、浏览器能力等复杂前端场景」与优先考虑第 3 条（浏览器自动化、富文本编辑器、实时协作、Canvas/WebGL、高复杂度交互产品）。音视频见 WebRTC 与 媒体专项。

一、富文本编辑器 ​

1.1 为什么 contenteditable 不够用 ​

contenteditable 让元素可编辑，但直接基于它做产品会踩平：浏览器在每次按键时的 DOM 修剪行为不可控（样式标签被拆散、空 div 乱生）、跨浏览器行为不一致、无法自定义数据模型。

成熟的编辑器框架都采用同一思路——数据模型与 DOM 分离：

text
用户输入 → 编辑器拦截(beforeinput/自定义) → 更改内部数据模型 → 框架按模型重绘 DOM

1.2 主流框架对比（概念级） ​

框架模型特点
Slate自定义 JSON 树极灵活、React 友好，需自己实现较多细节
ProseMirror严格的 Schema 文档约束最强，协同成熟（y-prosemirror），B 端文档类首选
Lexical元素/文本节点树Meta 出品、性能好、可无 React 使用
QuillDelta(JSON)上手快、生态老牌，深度定制较难

面试三句话：「编辑器核心是数据模型与 DOM 解耦；选型看 schema 约束强度与协同方案；协同走 CRDT（如 Yjs）或 OT。」

1.3 选区（Selection / Range） ​

富文本的「加粗选中文字」「@提及」「划词评论」都依赖选区 API：

ts
const sel = window.getSelection(); // 当前选区
if (sel && sel.rangeCount > 0) {
  const range = sel.getRangeAt(0); // Range 含起止容器与偏移
  const rect = range.getBoundingClientRect(); // 弹出工具条的定位依据
}

坑：编辑器重绘 DOM 后选区会丢，框架层需在 render 前保存选区、渲染后恢复——这是所有编辑器框架的内部核心逻辑。

二、浏览器自动化（前端视角） ​

2.1 原理 ​

Playwright / Puppeteer 通过 CDP（Chrome DevTools Protocol） 驱动浏览器：页面导航、DOM 查询、输入模拟、截图、网络拦截全部走协议指令。Playwright 额外支持 Firefox/WebKit 内核。

ts
// 自动化的基本骨架（与 e2e 测试同源）
const page = await browser.newPage();
await page.goto("https://example.com");
await page.getByRole("button", { name: "登录" }).click();

2.2 AI Agent 时代的浏览器自动化 ​

浏览器操作型 Agent（AI 帮用户操作网页）的链路：截图/DOM 快照 → 多模态模型理解页面 → 输出动作（点击/输入/滚动）→ 执行 → 循环。前端侧的贡献点：

  • 可访问性树是 Agent 读页面的主要方式——写好语义化标签/aria 属性，既是 a11y 又是「Agent 可操作性」；
  • 给 Agent 的页面稳定锚点：data-testid、稳定的 role/name；
  • 用 Playwright 做执行层（已有 E2E 实战经验可直接迁移）。

面试话术：「浏览器自动化的执行层我用 Playwright 做过完整 E2E（含拖拽、tab 切换、视觉回归）；AI Agent 化的差异只在决策层换成多模态模型，执行与断言基建是同一套。」

三、实时协作（概念级） ​

多人同时编辑同一文档（腾讯文档/Figma 类）的两个经典算法：

方案思路代表
OT（Operational Transformation）服务器对并发操作做变换后再应用Google Docs
CRDT数据结构本身保证无冲突合并，可去中心化Yjs、Automerge、Figma

前端要点：操作广播走 WebSocket；协同光标是每个用户的选区位置实时同步（节流上报 + 远端光标渲染）；离线编辑靠本地缓存 + 回线合并（CRDT 天然支持）。

一句话：「实时协作 = 数据模型支持合并（CRDT/OT）+ 实时通道（WebSocket）+ 光标与在线状态同步。」

四、Canvas 与 WebGL ​

维度Canvas 2DWebGL
渲染方式CPU 绘制 2D 命令GPU 着色器渲染
适合白板/标注/图表/海报编辑器三维、大量图元、滤镜特效
上层库Fabric.js（简历实战）、KonvaThree.js（协作接触）、Cesium

Canvas 2D 性能三板斧（简历 fabric.js/大屏可佐证）：分层 canvas（静态背景与动态前景分离，动层只重绘小画布）、脏矩形（只重绘变化区域）、离屏 canvas 预渲染复杂图形。

选型一句话：「静态图多、交互以点击拖拽为主 → Canvas 2D + Fabric；三维/海量图元/着色需求 → WebGL + Three.js；图表直接上 ECharts 不手写。」

五、高复杂度交互产品的通用思路 ​

  1. 状态先行：复杂交互先设计状态机（如播放器的 idle/playing/seeking），再写 UI，避免布尔变量地狱；
  2. 数据模型与视图解耦：编辑器/画布类产品必须自建数据模型，DOM/Canvas 只是投影；
  3. 命令模式：用户操作封装成命令对象，撤销/重做（undo/redo）= 命令栈，编辑器与画布类几乎必备；
  4. 性能预算：交互类页面按「输入到响应 < 100ms」约束，重计算挪 Web Worker，重渲染走分层/虚拟化。

六、常见坑 ​

  1. contenteditable 直接上产品：浏览器差异大、模型失控，产品级一律用框架；
  2. 编辑器中文输入法（IME）干扰：composition 事件期间不能重绘/恢复选区，否则拼音被吞；
  3. 自动化脚本依赖 CSS 类名选择器：样式重构即失效，用 role/text/testid 等语义锚点；
  4. Canvas 高 DPI 模糊：canvas 物理尺寸需乘 devicePixelRatio，再用 CSS 尺寸缩放回去；
  5. 协同场景只同步内容不同步选区：多人编辑会互相「看不到对方在改哪」，光标同步是体验刚需。

面试要点 ​

  1. 富文本编辑器为什么难？ 数据模型与 DOM 必须解耦，浏览器 contenteditable 行为不可控；成熟方案是拦截输入 → 改模型 → 重绘。
  2. ProseMirror/Slate 差异？ ProseMirror schema 约束强、协同生态成熟；Slate 更自由、React 友好但细节自己实现。
  3. 浏览器自动化原理？ CDP 协议驱动浏览器；AI Agent 化后决策层交给多模态模型，执行层与 Playwright E2E 同一套基建。
  4. OT 与 CRDT？ OT 靠服务器变换并发操作（Google Docs）；CRDT 数据结构天然无冲突合并（Yjs/Figma），可离线。
  5. Canvas 2D 性能优化？ 分层、脏矩形、离屏预渲染；高 DPI 乘 devicePixelRatio。
  6. 撤销重做怎么设计？ 命令模式：操作封装为命令对象进栈，undo 出栈逆执行，redo 回栈。
