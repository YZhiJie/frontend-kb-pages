工程化与场景题 ​

本页覆盖二面最深的两类题：工程化问答（考察工具链与工程规范）与场景设计题（考察架构与系统思维）。每题给"答题框架 + 要点"。对应 JD 要求 A4（工程化工具）+ A5（组件库/SDK 建设）+ B2（测试）。

深入阅读：构建工具 Vite/Webpack、Monorepo、CI/CD、组件库建设、单元测试、E2E 测试。

一、工程化问答 ​

Q1. Vite 与 Webpack 的区别？ ​

要点：Webpack 是"先打包再启动"（bundle-based），启动需构建整个依赖图；Vite 开发环境基于原生 ESM，不打包、按需编译（esbuild 预构建依赖），启动极快；生产环境 Vite 用 Rollup 打包。

深度补充：Vite 的 HMR 精确到模块、随包体增大不明显变慢；Webpack 的 HMR 需重新构建受影响 chunk，大项目会变慢。Vite 生态兼容性曾有 gap（如某些 CJS 插件），现已有 vite-plugin 体系补齐。对应 A4 级要求（9 份 JD）。

Q2. Vite 的核心配置与优化有哪些？ ​

要点：resolve.alias（路径别名）、server.proxy（开发代理跨域）、build.rollupOptions.manualChunks（分包）、build.target、optimizeDeps.include/exclude（预构建）、插件（@vitejs/plugin-react、unplugin-auto-import）。

深度补充：manualChunks 把 react/vue/echarts 拆成独立 chunk 提升缓存命中；build.chunkSizeWarningLimit 观察包体；vite-plugin-inspect 排查插件问题。生产用 rollup-plugin-visualizer 分析依赖构成。

Q3. Webpack 的核心概念与优化手段？ ​

要点：核心是 entry/output/loader/plugin/mode。优化：splitChunks 分包、treeShaking、cache（持久化缓存）、externals（CDN 外置）、thread-loader/esbuild-loader 提速、DllPlugin（历史方案）。

深度补充：splitChunks 的 chunks: 'all' 会把异步与同步共享模块提取为公共 chunk；runtimeChunk: 'single' 稳定长期缓存。resolve.extensions 精简、module.noParse 可减少解析。

Q4. pnpm 与 npm/yarn 的区别？为什么要用 pnpm？ ​

要点：pnpm 用内容寻址存储 + 硬链接，全局只存一份，项目通过硬链接引用；配合符号链接构建严格 node_modules 结构，避免幽灵依赖。npm/yarn 是"打平"或多次拷贝。

深度补充：pnpm 的严格结构让"未在 package.json 声明的依赖无法被直接 import"（杜绝幽灵依赖），但某些老库会因找不到打平的依赖而报错，可用 shamefully-hoist 兼容。速度与磁盘占用优势明显。

Q5. pnpm workspace 与 Monorepo 的组织方式？ ​

要点：pnpm-workspace.yaml 声明 packages/*；各包通过 workspace:* 协议互相引用（本地软链，免发布）；根 package.json 统一脚本；用 filter 只跑某包的脚本（pnpm --filter pkg build）。

深度补充：Monorepo 的价值是"统一依赖与配置、原子提交、跨包复用"。代价是需要处理构建顺序与版本一致性。组件库场景（命中 7 份 JD）常把 packages/components、packages/tokens、apps/docs 放在同一仓库。

Q6. Turborepo 与 Changesets 分别解决什么？ ​

要点：Turborepo 做任务编排与缓存——按依赖图并行/串行跑 build/lint/test，命中缓存则跳过；Changesets 做版本与发布管理——记录变更、自动升版本号、生成 CHANGELOG、发布 npm。

深度补充：Turborepo 的 pipeline 声明任务依赖（如 build 依赖 ^build），支持远程缓存（CI 提速）。Changesets 在 PR 中让作者写一个变更文件，合并后由 CI 统一版本与发布——是组件库（多包）发布的标准组合。

Q7. ESLint 与 Prettier、Stylelint 如何分工与协作？ ​

要点：ESLint 管代码质量与潜在错误（含 TS、React/Vue 规则）；Prettier 管格式（缩进/引号/换行），不管质量；Stylelint 管样式代码规范。三者职责分离，用 eslint-config-prettier 关闭与 Prettier 冲突的规则。

深度补充：用 lint-staged + husky 在提交前只检查改动文件（快）；eslint-plugin-import 约束依赖方向，配合 架构约束 守住分层。Vue/React 各自有官方 eslint 插件。

Q8. CI/CD 在前端项目里通常做什么？ ​

要点：CI——装依赖、lint、类型检查、单测、构建、E2E；CD——产物上传 CDN、灰度/蓝绿发布、通知。常用 GitHub Actions / GitLab CI。质量门禁是核心：不通过不允许合并。

深度补充：缓存 node_modules/.turbo 提速；--filter 只跑受影响包（Monorepo）；发布 npm 用 Changesets + npm publish（含 provenance）。对应 C 级"Docker/K8s/DevOps"（3 份 JD）。

Q9. 组件库如何打包与发布？ ​

要点：产物要多格式——ESM（es）、CJS（lib）、类型声明（types，vite-plugin-dts）；package.json 的 exports 字段暴露入口；按需加载靠 ESM + tree-shaking 或 unplugin-vue-components/babel-plugin-import 自动导入。

深度补充：样式产物单独输出（dist/style.css）或按组件拆分；peerDependencies 声明 React/Vue（避免用户重复引入）；版本遵循 semver；发布前用 npm pack 校验产物。这是 A5 级核心能力（7 份 JD）。

Q10. 前端测试体系怎么搭？ ​

要点：单元——Vitest/Jest 测工具函数与组件逻辑（@testing-library 测行为不测实现）；组件——测试渲染与交互；E2E——Playwright 跑真实浏览器关键路径；覆盖率做门禁。分层金字塔：单测多、E2E 精。

深度补充：@testing-library 的哲学是"像用户一样测试"（查 role/text 而非 class）；Playwright 支持多浏览器、自动等待、录制生成脚本。对应 B2 级（5 份 JD）。AI 提效场景下可作为质量门禁卡住 AI 产出。

二、场景设计题 ​

场景题的答题骨架：澄清需求 → 拆解模块 → 技术选型 → 关键难点 → 边界与权衡 → 效果度量。先问清约束（规模、兼容、团队），再给方案。

Q11. 如何设计一个组件库？ ​

框架：需求（给谁用、覆盖哪些端）→ 分层（tokens → 基础组件 → 业务组件）→ 技术（TS、多格式打包、文档站）→ 质量（单测、a11y、视觉回归）→ 交付（semver、按需加载、主题）。

要点：

  1. 设计令牌层：颜色/字号/间距 token 化，支持主题切换（CSS 变量）。
  2. 组件层：受控 + 非受控双模式；命名与 API 一致（如统一 onChange 签名）。
  3. 样式方案：CSS Modules / CSS-in-JS / 原子化，权衡可维护性与运行时成本。
  4. 文档与示例：用 Storybook/VitePress 做文档站（4 份 JD 要求技术文档能力）。
  5. 发布：多格式产物 + exports + 按需加载 + Changesets 版本管理。

深度补充：你做过双栈同构组件库——同一套设计 token 与交互契约在 React/Vue 落地，这正是 7 份 JD 要的"组件库/SDK 交付"。讲清"同构"如何降低维护成本、API 如何对齐。

Q12. 如何设计一个前端请求层？ ​

框架：实例封装 → 拦截器 → 错误模型 → 取消/重试 → 并发与缓存 → 类型安全。

要点：

  1. 实例：baseURL、超时、默认头，支持多实例（不同网关）。
  2. 拦截器：请求注入 token/追踪 ID；响应统一处理业务码与非 2xx。
  3. 错误模型：区分网络错误、超时、HTTP 错误、业务错误，暴露结构化错误。
  4. 取消：AbortController（组件卸载取消）；重试：指数退避 + 幂等方法白名单。
  5. 并发：Promise.allSettled、并发池；缓存：GET 合理缓存（可配 SWR）。

深度补充：401 刷新 token 的并发排队是关键难点——刷新期间挂起其他请求，刷新完成统一重放，失败则登出并跳转。详见 HTTP 与请求层设计。

Q13. 如何设计 RBAC 权限系统与动态路由？ ​

框架：角色模型 → 权限粒度 → 路由/菜单生成 → 按钮级控制 → 数据权限。

要点：

  1. 模型：用户 → 角色（Role）→ 权限码（Permission），后端返回权限码列表。
  2. 粒度：菜单级、按钮级（v-permission / <Can>）、接口级（后端校验）。
  3. 动态路由：登录后拉权限，前端按权限过滤/追加路由表（router.addRoute），并处理 404 兜底。
  4. 按钮控制：用指令/组件包裹按权限码显隐（前端控制是体验，安全必须后端兜底）。

深度补充：B 端中后台（6 份 JD）高频。要强调"前端权限只为体验，真正安全由后端强制"。动态路由需处理首次刷新时权限还未加载的路由守卫等待。

Q14. 如何实现虚拟滚动？ ​

框架：只渲染可视区 → 容器高度撑起 → 滚动偏移定位。

要点：

  1. 固定高度：总高 = 项数 × 项高；渲染 [start, end] 区间项，用 translateY 偏移。
  2. 动态高度：需预估 + 实测修正（测量已渲染项高、维护偏移表），复杂度高。
  3. 缓冲：可视区上下各多渲染几项，减少滚动白屏。
  4. 优化：will-change、避免滚动中重排、requestAnimationFrame 节流。

深度补充：大屏/日志/大表格场景必备（命中 #7 大屏、#1 监控列表）。可用 vue-virtual-scroller、@tanstack/virtual。对比"虚拟列表 vs 分页"的适用边界。

Q15. 如何设计大屏适配方案？ ​

框架：设计稿基准 → 缩放策略 → 图表自适应 → 性能。

要点：

  1. 缩放：以固定设计稿宽（如 1920）为基准，用 transform: scale 或 vw/vh 等比缩放；rem + flexible 是移动端方案（大屏一般用 scale）。
  2. 图表自适应：ECharts 监听 resize；容器尺寸变化用 ResizeObserver 而非 window.resize。
  3. 性能：大数据量图表降采样、关闭动画、虚拟化表格、Web Worker 计算。
  4. 层级：背景图/装饰图/数据层分组，避免重排。

深度补充：transform: scale 会有模糊与点击坐标偏移问题，需按缩放比换算；ResizeObserver 是容器级自适应的正解。对应 B3 级可视化（5 份）。详见 大屏性能。

Q16. 如何治理组件 re-render（React/Vue）？ ​

框架：定位 → 分层优化 → 度量。

要点：

  1. 定位：先用 Profiler（React DevTools）/ Vue Devtools 找热点，不要盲目 memo。
  2. React：memo + useMemo/useCallback 稳定 props；状态下移/拆分；children 透传；Context 拆分或换可订阅状态库；列表虚拟化。
  3. Vue：v-once、v-memo、shallowRef、computed 缓存、稳定 key。
  4. 度量：渲染次数统计、why-did-you-render、火焰图。

深度补充：强调"先测量再优化"，否则 memo 的比较成本可能反噬。层级化的思路（组件级 → 值级 → 结构级）能体现系统性。

Q17. 如何做离线消息补偿（IM）？ ​

框架：本地存储 → 序号同步 → 增量拉取 → 去重与合并。

要点：

  1. 本地存储：会话与消息存 IndexedDB（异步、大容量）。
  2. 序号：每条消息有唯一 ID 与全局/会话内递增序号（seq）。
  3. 补偿：重连成功后带 lastSeq 请求 sync，服务端返回缺失消息；实时消息与补偿消息按 seq 去重 + 排序合并。
  4. 兜底：断线指数退避重连、心跳保活、乐观发送失败回滚。

深度补充：这是 #8 鹏开信息 IM 岗的核心（见 IM 前端）。要点是"消息不重不漏"——靠单调序号 + 客户端幂等去重实现。

Q18. 如何搭建前端监控（可观测）体系？ ​

框架：采集 → 上报 → 存储 → 分析告警。

要点：

  1. 采集：onerror/unhandledrejection（异常）、资源错误、接口错误、性能指标（PerformanceObserver）、白屏检测、用户行为埋点。
  2. 上报：sendBeacon 可靠上报；采样降量；去重合并；携带用户/设备/版本上下文；sourcemap 还原堆栈。
  3. 存储与分析：聚合看板（错误率、P95 耗时）、告警规则（阈值/突增）。
  4. SDK 设计：可插拔插件、体积控制、错误隔离（try/catch 包裹，不影响宿主）。

深度补充：这是 #3 腾讯外包"监控 SDK/可观测体系"核心考点。要讲清"SDK 自身不能拖垮业务"——异步上报、异常隔离、体积预算。也呼应 A5 级 SDK 交付能力。

面试要点 ​

  1. Vite vs Webpack？ 开发基于原生 ESM（无打包、极快 HMR），生产 Rollup 打包；Webpack 先打包再启动。
  2. pnpm 优势？ 内容寻址 + 硬链接省空间，严格 node_modules 杜绝幽灵依赖。
  3. Monorepo 工具链？ pnpm workspace 组织 + Turborepo 任务编排缓存 + Changesets 版本发布。
  4. 组件库交付？ 多格式产物（ESM/CJS/types）+ exports/peerDeps + 按需加载 + semver + 文档站。
  5. 场景题骨架？ 澄清需求 → 拆模块 → 选型 → 难点 → 权衡 → 度量，先问清约束再给方案。
  6. RBAC 要点？ 角色-权限码模型 + 动态路由过滤 + 按钮级控制；前端只为体验，安全靠后端。
  7. 虚拟滚动本质？ 只渲染可视区 + 容器撑高 + 偏移定位；动态高度需实测修正。
  8. 监控 SDK 关键？ 可靠上报（sendBeacon）+ 异常隔离 + 采样 + sourcemap 还原。
