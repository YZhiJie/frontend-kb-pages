浏览器与网络高频题 ​

本页覆盖浏览器原理与网络层的高频题，采用 [问法] → [要点] → [深度补充] 结构。对应 JD 要求 A2（浏览器原理）+ B5（HTTP 请求层）+ B8（前端安全，4 份 JD）。

深入阅读：HTTP 与请求层设计、浏览器跨域机制、实时通信 WebSocket/SSE、前端 Web 安全。

一、渲染原理 ​

Q1. 从输入 URL 到页面渲染发生了什么？ ​

要点：分阶段——① URL 解析与 DNS 查询；② TCP 三次握手（HTTPS 再加 TLS 握手）；③ 发送 HTTP 请求；④ 服务器响应；⑤ 浏览器解析 HTML 构建 DOM、解析 CSS 构建 CSSOM，合成渲染树；⑥ 布局（layout）计算几何；⑦ 绘制（paint）与合成（composite）；⑧ 执行 JS、加载子资源。

深度补充：DNS 有缓存层级（浏览器 → 系统 → 路由器 → ISP）；HTML 解析遇 <script> 会阻塞解析（无 defer/async 时），遇 <link> CSS 会阻塞渲染。现代浏览器还会做预加载扫描（preload scanner）提前发现子资源。

Q2. 浏览器渲染流程与重排、重绘？ ​

要点：渲染流水线——DOM + CSSOM → Render Tree → Layout（重排）→ Paint（重绘）→ Composite（合成）。重排改变几何（位置/尺寸），代价最大且会连锁重绘；重绘只改外观（颜色/背景），代价较小；合成只改 transform/opacity，可由 GPU 独立线程处理、不触发重排重绘。

深度补充：优化原则——动画优先用 transform/opacity；用 will-change/translateZ 提升为独立图层；批量读写 DOM 避免布局抖动（强制同步布局）；用 DocumentFragment 或离线节点批量更新。display: none 会触发重排，visibility: hidden 只重绘。

Q3. 什么会触发强制同步布局（布局抖动）？ ​

要点：在同一帧里"写 DOM → 立即读布局属性（offsetHeight/getComputedStyle）→ 再写"会强制浏览器提前同步计算布局，反复触发重排。

深度补充：修复方法是先集中读、再集中写（read-then-write）。requestAnimationFrame 里做视觉更新、requestIdleCallback 做非紧急任务，能避免抖动。使用 FastDOM 之类的批处理库也是常见方案。

二、HTTP 缓存 ​

Q4. 强缓存与协商缓存？ ​

要点：强缓存由 Cache-Control（max-age）或 Expires 控制，命中后不发请求直接用本地缓存；协商缓存在强缓存失效后，带 If-None-Match（配 ETag）或 If-Modified-Since（配 Last-Modified）询问服务器，未变则返回 304。

深度补充：Cache-Control 优先级高于 Expires（后者是绝对时间、受本地时钟影响）。ETag 比 Last-Modified 更精确（内容哈希，能识别秒内修改），但计算有成本。no-cache 是"要协商"（仍存缓存），no-store 是完全不缓存，别混淆。

Q5. 前端资源缓存策略怎么设计？ ​

要点：HTML 用 no-cache（每次都协商，保证入口最新）；带哈希的静态资源（app.1a2b3c.js）用 max-age=31536000, immutable（内容变则文件名变，可长期强缓存）。

深度补充：immutable 告诉浏览器"过期前不要再发验证请求"。改用文件名哈希而非查询参数（?v=1）——有些 CDN/浏览器对带查询串的资源缓存策略不一致。配合 Service Worker 可做更细粒度的离线缓存。

三、跨域与安全 ​

Q6. 什么是同源策略？如何跨域？ ​

要点：同源 = 协议 + 域名 + 端口三者相同。跨域方案：CORS（服务端设 Access-Control-Allow-*，主流）、JSONP（只支持 GET，已过时）、代理（开发用 Vite/Webpack devServer proxy、生产用 Nginx 反代）、postMessage（页面间通信）、WebSocket（不受同源策略限制）。

深度补充：跨域限制的是读取响应（XHR/fetch），不是"发送请求"——简单请求会真的发出，只是响应被拦。document.domain（已废弃）、window.name、iframe 跳转是历史方案。

Q7. CORS 的简单请求与预检请求？ ​

要点：简单请求（GET/HEAD/POST + 特定 Content-Type + 无自定义头）直接发送，响应带 Access-Control-Allow-Origin 即可；非简单请求先发 OPTIONS 预检，服务器返回允许的方法/头后（Access-Control-Allow-Methods/-Headers）才发真实请求。

深度补充：带凭证（Cookie）的跨域请求要求 Access-Control-Allow-Credentials: true 且 Access-Control-Allow-Origin 不能是 *（必须是具体来源）。预检结果可用 Access-Control-Max-Age 缓存，减少 OPTIONS 次数。

Q8. 跨域下 Cookie 为什么带不上？如何解决？ ​

要点：现代浏览器默认 SameSite=Lax，跨站请求不带 Cookie；跨域携带 Cookie 还需 withCredentials: true（前端）+ Access-Control-Allow-Credentials: true（后端）+ Cookie 设 SameSite=None; Secure。

深度补充：SameSite 三值——Strict（完全禁止跨站）、Lax（默认，顶层导航 GET 携带）、None（允许，但必须 Secure）。SSO/嵌入第三方页面时常用 SameSite=None; Secure。

Q9. XSS 是什么？怎么防？ ​

要点：XSS 是攻击者注入并执行恶意脚本。分三类——存储型（存入数据库，危害最大）、反射型（URL 参数回显）、DOM 型（前端 JS 直接插入）。防御：输出转义、输入校验、Content-Security-Policy（CSP）、HttpOnly Cookie。

深度补充：HttpOnly 让 JS 无法读取 Cookie（防 cookie 窃取）；CSP 用 script-src 'self' 白名单限制脚本来源。React 默认转义 JSX 插值，但 dangerouslySetInnerHTML、v-html 会绕过，必须对富文本做白名单过滤（如 DOMPurify）。

Q10. CSRF 是什么？怎么防？ ​

要点：CSRF 利用浏览器自动携带 Cookie 的特性，诱导用户已登录的站点发起恶意请求。防御：CSRF Token（服务端下发、提交时校验）、SameSite Cookie、校验 Origin/Referer、关键操作二次验证。

深度补充：XSS 与 CSRF 区别——XSS 是"信任了用户输入"，CSRF 是"信任了用户浏览器"。用了 SameSite=Lax/Strict 后，多数 CSRF 场景已被浏览器默认抵挡，但同站点的 CSRF 仍需 Token。

四、HTTP 协议与实时通信 ​

Q11. HTTP/1.1、HTTP/2、HTTP/3 的区别？ ​

要点：HTTP/1.1 明文文本、队头阻塞、同域连接数受限（浏览器约 6 个）；HTTP/2 二进制分帧、多路复用（一个 TCP 连接并发多请求）、头部压缩（HPACK）、服务端推送，但仍有 TCP 层队头阻塞；HTTP/3 基于 QUIC（UDP），消除 TCP 队头阻塞、0-RTT 建连、连接迁移。

深度补充：HTTP/2 的多路复用解决了应用层队头阻塞，但丢包会让同一 TCP 连接的所有流等待（TCP 队头阻塞）；QUIC 把流独立，丢包只影响单流。HTTP/2 需 HTTPS（浏览器实现要求）。

Q12. WebSocket 与 SSE 的区别？ ​

要点：WebSocket 基于 ws://，全双工、双向通信，适合 IM/协同编辑；SSE 基于 HTTP，单向（服务器 → 客户端）、自动重连、文本流，适合推送通知/进度；两者都不受同源策略的读取限制（WebSocket 需服务端校验 Origin）。

深度补充：SSE 相比 WebSocket 更轻（无需协议升级），但只能服务端推、只支持文本。AI 产品（#10）的流式输出常用 SSE 或 fetch + ReadableStream 实现。

Q13. 如何做实时通信的断线重连与消息补偿？ ​

要点：心跳保活（定时 ping/pong 检测死连接）；断线用指数退避重连（避免风暴）；重连成功后按最后一条消息 ID/序号拉取离线消息，实现补偿。

深度补充：消息要有唯一 ID 与单调递增序号，服务端保留一段历史；客户端记录 lastSeq，重连后 sync(lastSeq)。这正是 #8 鹏开信息 IM 岗的核心考点（见 IM 前端）。

深度补充：Cookie 会自动附加到同源请求，是它最大的"负担"；localStorage 同步，存大 JSON 会阻塞主线程（大屏/IM 大量数据改用 IndexedDB）。跨标签页同步可用 storage 事件或 BroadcastChannel。

Q15. localStorage 的性能坑？ ​

要点：localStorage 是同步 API，读写大对象会阻塞主线程，导致卡顿/掉帧。

深度补充：大数据（历史消息、图表缓存）用 IndexedDB（异步）；需要更快的会话级缓存可放在内存 + sessionStorage。敏感数据不要放 localStorage（XSS 可读），应放 HttpOnly Cookie。

六、性能与监控 ​

Q16. Core Web Vitals 是哪三个指标？ ​

要点：LCP（最大内容绘制，加载性能）、INP（Interaction to Next Paint，交互响应性，2024 起替代 FID）、CLS（累积布局偏移，视觉稳定性）。目标：LCP < 2.5s、INP < 200ms、CLS < 0.1。

深度补充：LCP 优化——压缩/预加载首屏大图、fetchpriority="high"、CDN、服务端渲染；CLS 优化——给图片/广告位预留尺寸、字体 font-display: optional、避免动态插入内容顶掉布局；INP 优化——减少长任务、拆包、用 requestIdleCallback。

Q17. 首屏加载怎么优化？ ​

要点：资源层面——代码分割（路由懒加载）、Tree-shaking、压缩（gzip/brotli）、CDN、HTTP/2；渲染层面——SSR/预渲染、骨架屏、关键 CSS 内联、图片懒加载/WebP、preload/prefetch。

深度补充：用 performance API 或 Lighthouse 量化——TTFB（网络/服务端）、FCP、LCP 分别定位瓶颈。命中 A3 级"性能优化（首屏/懒加载/渲染）"（9 份 JD）。

Q18. 前端如何做异常监控与上报？ ​

要点：三类异常——JS 运行时错误（window.onerror / error 事件）、资源加载错误（error 事件捕获阶段）、未处理的 Promise 拒绝（unhandledrejection）。上报要点：采样、navigator.sendBeacon（不阻塞卸载）、错误去重、携带 sourcemap 还原堆栈。

深度补充：还要补——接口错误（拦截 fetch/XHR）、白屏检测、性能指标上报（PerformanceObserver）。上报队列可做合并与批量，失败重试。这是 #3 腾讯外包"监控 SDK/可观测体系"的核心考点。

Q19. sendBeacon 与 fetch(keepalive) 为什么适合埋点上报？ ​

要点：它们能在页面卸载时可靠地把数据发出去且不阻塞跳转。navigator.sendBeacon(url, data) 适合小数据；fetch(url, { keepalive: true }) 支持更大负载与自定义头。

深度补充：普通 XHR 在卸载时可能被中断；sendBeacon 由浏览器排队保证送达。埋点 SDK 常用 visibilitychange/pagehide 触发上报。

Q20. HTTP 请求层的常见设计？ ​

要点：统一封装（baseURL、超时、鉴权头注入）、拦截器（请求加 token、响应统一错误处理/刷新 token）、错误分类（网络/超时/业务码）、取消（AbortController）、重试与并发控制。

深度补充：401 自动刷新 token 需并发排队（刷新期间挂起其他请求，刷新后重放），并用队列防止 token 刷新风暴。详见 HTTP 与请求层设计。

Q21. 浏览器事件循环中渲染发生在哪一步？ ​

要点：每个宏任务执行完、微任务清空后，浏览器才会决定是否渲染（requestAnimationFrame 回调在这一步之前执行）。若主线程被长任务占满，渲染会被推迟，造成掉帧。

深度补充：requestAnimationFrame 在下一次重绘前执行（约 60fps / 16.7ms 一次）。动画用 rAF 而非 setTimeout 才能对齐刷新；requestIdleCallback 在帧空闲时执行低优先级任务。

面试要点 ​

  1. 输入 URL 到渲染？ DNS → TCP/TLS → HTTP → 解析构建 DOM/CSSOM → 布局 → 绘制 → 合成；<script> 阻塞解析。
  2. 重排 vs 重绘？ 重排改几何、代价最大；重绘只改外观；transform/opacity 只走合成、不触发两者。
  3. 强缓存 vs 协商缓存？ 强缓存不发请求（Cache-Control）；协商缓存发请求问是否更新，未变返回 304（ETag）。
  4. 跨域怎么答？ 同源策略限制读取响应；CORS（含预检与凭证）、代理、postMessage、WebSocket 是主要方案。
  5. XSS vs CSRF？ XSS 是"信任了输入"（注入脚本），CSRF 是"信任了浏览器"（诱导已登录请求）；分别用转义/CSP 与 Token/SameSite。
  6. HTTP/2 与 HTTP/3？ HTTP/2 多路复用仍受 TCP 队头阻塞；HTTP/3 用 QUIC（UDP）消除之，支持 0-RTT。
  7. 核心指标？ LCP（加载）、INP（交互）、CLS（稳定）。
  8. 异常监控三类？ onerror、资源错误、unhandledrejection；用 sendBeacon 可靠上报 + sourcemap 还原。
