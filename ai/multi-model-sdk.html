多模型接入与前端 SDK ​

从「接一家写一套」到「面向接口编程」——Provider 抽象层是 AI 前端架构能力的最佳体现，也是面试设计题的高频区。本文按「为什么多模型 → 抽象层 → 统一 SDK → 交付要点 → 直连 vs BFF → 降级与并发 → 常见坑」组织。协议细节见 流式渲染与 AI 交互界面，对外交付与发布见 组件库建设与发布。

覆盖 JD 对应点：#10 欣农互联「AI 产品前端」需对接多家模型服务、#3 腾讯外包「AI Agent 界面」需 SDK 化的模型接入层、#9 今天国际「组件库 / 公共能力建设 + SDK 交付」（A5 要求 + AI 协作硬性条款）。

一、多模型接入的动机 ​

直接在业务代码里写 openai.chat.completions.create(...) 会付出三重代价：厂商锁定（换模型等于全业务改造，做效果对比也得侵入业务代码）、重复造轮子（流式解析 / 重试 / 降级 / 错误处理在 N 处各写一遍且不一致）、成本不可控（没有统一入口，无法集中限流、计量、降级）。目标：业务只依赖抽象接口，模型切换是配置问题而非代码问题。

二、模型无关抽象层设计 ​

2.1 统一请求/响应与错误模型 ​

ts
export type Role = 'system' | 'user' | 'assistant' | 'tool'
export interface ToolCall {
  id: string
  type: 'function'
  function: { name: string; arguments: string } // arguments 是 JSON 字符串
}
export interface ChatMessage {
  role: Role
  content: string
  reasoning_content?: string      // DeepSeek-R1 / QwQ 的思考内容
  tool_calls?: ToolCall[]
  tool_call_id?: string           // role:'tool' 时对应哪个调用
}

export interface ChatRequest {
  model: string
  messages: ChatMessage[]
  temperature?: number
  maxTokens?: number
  tools?: { type: 'function'; function: { name: string; description: string; parameters: unknown } }[]
}

export interface StreamChunk {
  content?: string
  reasoning?: string
  toolCalls?: ToolCall[]
  finishReason?: 'stop' | 'length' | 'tool_calls' | 'content_filter' | null
  usage?: { promptTokens: number; completionTokens: number }
}

export type SDKErrorCode =
  | 'NETWORK' | 'TIMEOUT' | 'AUTH' | 'RATE_LIMIT'
  | 'QUOTA' | 'CONTENT_FILTER' | 'BAD_REQUEST' | 'SERVER' | 'ABORTED'

export class SDKError extends Error {
  constructor(
    public code: SDKErrorCode,
    message: string,
    public provider?: string,
    public retryable: boolean = false,
    public status?: number,
  ) {
    super(message)
    this.name = 'SDKError'
  }
}

// Provider 抽象接口（核心）：业务只依赖它
export interface ModelProvider {
  readonly name: string
  chat(req: ChatRequest, signal?: AbortSignal): Promise<ChatMessage>
  streamChat(req: ChatRequest, signal?: AbortSignal): AsyncGenerator<StreamChunk>
}

2.2 适配器模式与 OpenAI 兼容协议 ​

OpenAI 兼容协议已是事实标准——DeepSeek、通义（DashScope 兼容模式）、Kimi、智谱、豆包都提供同构端点：相同路径 /chat/completions、相同 body、相同 SSE 报文（data: {chunk} + [DONE]）。所以一个适配器吃遍大部分厂商，差异只在 baseURL / apiKey / model 名。

ts
export class OpenAICompatibleProvider implements ModelProvider {
  constructor(
    public readonly name: string,
    private baseURL: string,
    private apiKey: string,
    private extraHeaders: Record<string, string> = {},
  ) {}

  async chat(req: ChatRequest, signal?: AbortSignal): Promise<ChatMessage> {
    const msg = (await (await this.request(req, signal, false)).json()).choices?.[0]?.message
    return { role: 'assistant', content: msg?.content ?? '', tool_calls: msg?.tool_calls }
  }

  async *streamChat(req: ChatRequest, signal?: AbortSignal): AsyncGenerator<StreamChunk> {
    const res = await this.request(req, signal, true)
    if (!res.body) throw new SDKError('NETWORK', 'no body', this.name)
    yield* parseOpenAISSE(res.body, this.name, signal) // 复用统一 SSE 解析器
  }

  private async request(req: ChatRequest, signal: AbortSignal | undefined, stream: boolean) {
    let res: Response
    try {
      res = await fetch(`${this.baseURL}/chat/completions`, {
        method: 'POST',
        headers: { 'Content-Type': 'application/json', Authorization: `Bearer ${this.apiKey}`, ...this.extraHeaders },
        body: JSON.stringify({
          model: req.model, messages: req.messages, temperature: req.temperature,
          max_tokens: req.maxTokens, tools: req.tools,
          stream,
          stream_options: stream ? { include_usage: true } : undefined, // 流式要显式开 usage
        }),
        signal,
      })
    } catch (e) {
      throw new SDKError('NETWORK', String(e), this.name, true) // 网络层错误可重试
    }
    if (!res.ok) throw this.mapError(res.status)
    return res
  }

  private mapError(status: number): SDKError {
    const code: SDKErrorCode = status === 401 || status === 403 ? 'AUTH' : status === 429 ? 'RATE_LIMIT'
      : status === 402 ? 'QUOTA' : status === 400 ? 'BAD_REQUEST' : 'SERVER'
    return new SDKError(code, `HTTP ${status}`, this.name, status === 429 || status >= 500, status)
  }
}

异构协议（Claude / 文心）需要单独适配，且是双向映射：

统一模型Claude (messages API)
role:'system' 在 messages 内抽出为顶层 system 字段
Authorization: Bearerx-api-key + anthropic-version
choices[0].delta.content事件 content_block_delta.delta.text
tool_callstool_use / tool_result
usage.prompt_tokensusage.input_tokens / output_tokens
finish_reasonstop_reason（end_turn / max_tokens / tool_use）

注意：Claude 的 SSE 事件类型多（message_start / content_block_delta / message_stop 等），必须按 event: 分流，不能像 OpenAI 那样只读 data:。

三、统一 SDK 设计 ​

3.1 客户端封装与双范式流式 API ​

底层用 Async Generator，上层包一层回调，两种消费风格兼供：

ts
export interface StreamCallbacks {
  onDelta: (text: string) => void
  onReasoning?: (text: string) => void
  onDone: (usage?: StreamChunk['usage']) => void
  onError: (err: SDKError) => void
}

export class AIClient {
  constructor(private providers: Record<string, ModelProvider>) {}

  // 范式 A：Async Iterator（现代 async 风格）
  streamChat(req: ChatRequest, signal?: AbortSignal): AsyncGenerator<StreamChunk> {
    const key = req.model.split(':')[0] // 约定 "provider:model"
    const p = this.providers[key]
    if (!p) throw new SDKError('BAD_REQUEST', `未知 provider: ${key}`)
    return p.streamChat(req, signal)
  }
}

// 范式 B：在客户端之上包一层回调适配（框架无关，便于集成老代码 / 小程序）
export function streamWithCallback(client: AIClient, req: ChatRequest, cb: StreamCallbacks, signal?: AbortSignal) {
  void (async () => {
    let usage: StreamChunk['usage']
    try {
      for await (const c of client.streamChat(req, signal)) {
        if (c.content) cb.onDelta(c.content)
        if (c.reasoning) cb.onReasoning?.(c.reasoning)
        if (c.usage) usage = c.usage
      }
      cb.onDone(usage)
    } catch (e) {
      cb.onError(e instanceof SDKError ? e : new SDKError('SERVER', String(e)))
    }
  })()
}

3.2 超时、重试、降级与可测试性 ​

超时要分两段：连接/首字节超时（短，如 10s）与整体流上限（长，如 300s）。只设一个总超时会误杀正常长回答，只设连接超时又防不住「连上了但一直不吐字」。实现上连接阶段用短 setTimeout + 独立 AbortController，超时即 abort(new DOMException('timeout','TimeoutError'))，并把外部 signal 的 abort 事件转发进去。

ts
// 重试：仅对可重试错误，指数退避 + 抖动
export async function retry<T>(
  fn: () => Promise<T>, { retries = 2, base = 500, signal }: { retries?: number; base?: number; signal?: AbortSignal } = {},
): Promise<T> {
  let lastErr: unknown
  for (let attempt = 0; attempt <= retries; attempt++) {
    try { return await fn() } catch (e) {
      lastErr = e
      if (e instanceof SDKError && !e.retryable) throw e    // AUTH/QUOTA 等直接抛
      if (attempt === retries) break
      if (signal?.aborted) throw new SDKError('ABORTED', 'cancelled')
      await new Promise((r) => setTimeout(r, base * 2 ** attempt + Math.random() * 300))
    }
  }
  throw lastErr
}
ts
// 降级：主 → 备 → 兜底，按序尝试
export async function chatWithFallback(client: AIClient, chain: ChatRequest[], signal?: AbortSignal): Promise<ChatMessage> {
  let lastErr: SDKError | undefined
  for (const req of chain) {
    try {
      const result = await client.chat(req, signal)
      if (req !== chain[0]) reportFallback(chain[0].model, req.model) // 上报降级，UI 提示「备用线路」
      return result
    } catch (e) {
      lastErr = e as SDKError
      if (!lastErr.retryable) throw lastErr // 不可重试错误不浪费备用配额
    }
  }
  throw lastErr
}

降级的三条边界：流式中途失败不自动降级（已吐一半，换模型更糟）；业务依赖特定能力（如 Function Calling 格式）时不降级，除非确认备模型兼容；降级必须上报监控，主模型故障率超阈值告警，恢复后静默切回。

Mock Provider 是可测试性的关键：内置一个返回预设流式 / CoT / 工具调用 / 引用序列的 Mock，可支撑无网开发、零成本单测与现场演示。

四、前端 SDK 交付要点 ​

作为「公共能力 / SDK 交付」的一部分（对应 A5），前端 SDK 的交付标准与 UI 组件库相当：

维度要求
类型完整 .d.ts，请求/响应/错误全类型化，strict 编译通过
产物同时出 ESM 与 UMD/CJS；exports 用 { types, import, require } 映射，sideEffects: false
错误模型统一 SDKError + 错误码枚举，不用裸 Error / any
可配置baseURL / apiKey / timeout / headers / retries 全可注入，不硬编码
无框架绑定核心 SDK 不依赖 React/Vue，UI 适配层单独出包（见 双栈对比与同构组件库）
可观测事件钩子 + 每请求 requestId，便于排查与计费

五、前端直连 vs BFF 代理 ​

风险直连厂商的后果
Key 打包进 JS任何人查看产物即拿到，被盗刷
Key 出现在请求头抓包 / 浏览器扩展可见
无法轮换泄露后要发版才能换
CORS多数厂商不支持浏览器直连
无审计无法按用户/部门计量成本

结论：生产必须走 BFF——前端持会话凭证访问自家 BFF，BFF 负责鉴权、限流（按租户配额）、Key 注入（KMS / 环境变量）、用量审计、合规过滤、SSE 透传与心跳保活、主备降级。前端的「API Key 输入框」只存在于开发/演示模式，生产构建必须关掉。

六、并发控制与长任务轮询 ​

Promise.all(100) 会触发厂商 QPS 限流（429），并占满浏览器同域连接（HTTP/1.1 上限 6）。用固定并发度的池，完成一个补一个：

ts
export async function promisePool<T, R>(items: T[], concurrency: number, worker: (item: T, i: number) => Promise<R>): Promise<R[]> {
  const results = new Array<R>(items.length)
  let cursor = 0
  const run = async () => {
    while (cursor < items.length) {
      const i = cursor++
      results[i] = await worker(items[i], i)
    }
  }
  await Promise.all(Array.from({ length: concurrency }, run))
  return results
}

文档解析等长任务：提交拿 taskId 后轮询状态。能推送（SSE/WebSocket）就别轮询，轮询是兜底：

ts
export async function pollTask<T>(
  fetcher: () => Promise<{ status: 'pending' | 'done' | 'failed'; result?: T }>,
  { interval = 1000, timeout = 300_000, signal }: { interval?: number; timeout?: number; signal?: AbortSignal } = {},
): Promise<T> {
  const start = Date.now()
  let delay = interval
  while (Date.now() - start < timeout) {
    if (signal?.aborted) throw new SDKError('ABORTED', 'poll cancelled')
    const { status, result } = await fetcher()
    if (status === 'done') return result as T
    if (status === 'failed') throw new SDKError('SERVER', 'task failed')
    await new Promise((r) => setTimeout(r, delay + Math.random() * 300)) // 抖动防惊群
    delay = Math.min(delay * 2, 10_000)                                 // 1s → 2s → 4s，封顶 10s
  }
  throw new SDKError('TIMEOUT', 'poll timeout', undefined, true)
}

坑：页面隐藏时浏览器会节流 setTimeout（最小 1s 甚至暂停），重要任务考虑 Web Worker / Service Worker。

七、常见坑与实战要点 ​

  1. 拿一个分词器估算所有厂商 Token：分词器不同，中文差异明显，跨厂商预算要按各家口径。
  2. arguments 直接当对象用：Function Calling 返回 JSON 字符串要先 JSON.parse；流式下 args 还是分片累积的。
  3. 不设连接超时：首字节挂起时整个请求卡死，必须分开设「连接超时 + 总时长上限」。
  4. 忘了 include_usage：OpenAI 系流式默认不返回 usage，计费统计全为 0。
  5. 降级吞掉可修的错误：AUTH / QUOTA 是配置问题，降级只是把错误掩盖成「备模型也失败」。
  6. 流式中断后想断点续传：伪命题，服务端推理上下文已丢，只能重新发起并说明会重新计费。
  7. 忽略 CORS 与网关缓冲：自研 BFF 要正确响应 OPTIONS；SSE 要禁网关缓冲（X-Accel-Buffering: no）。
  8. SDK 硬编码 baseURL/Key：交付型 SDK 必须全可配置，否则接入方无法对接自有网关。
  9. 并发度拍脑袋：按厂商 QPS 与 Token 速率留 buffer（如 QPS 20 时并发设 15）；没有 Mock Provider 则无法单测流式路径。

面试要点 ​

  1. 如何设计一个多模型 SDK？ 抽象层定义 ModelProvider（chat / streamChat + 统一消息与错误模型），适配层每厂商一实现（OpenAI 兼容协议复用一套），能力层做重试/并发/降级/中断，业务只依赖抽象接口。
  2. OpenAI 兼容协议的意义？ 同构端点与 SSE 报文，一个适配器加上不同 baseURL/apiKey/model 就能接入大部分厂商，避免锁定、降低迁移成本。
  3. API Key 放前端有什么问题？ 打包泄露、抓包可见、无法快速轮换、无审计、CORS 受限；应走 BFF，前端只持会话凭证。
  4. 如何实现模型降级？ 主备链按序尝试，仅对可重试错误降级；流式中途失败与能力依赖场景不降级；要上报监控并 UI 提示。
  5. 并发请求怎么控？ Promise Pool 固定并发度，避免 QPS 限流与同域连接打满，失败任务单独重试。
  6. 长任务为什么用指数退避轮询？ 降请求压力、避免任务堆积打爆服务端；间隔翻倍封顶 + 抖动；能推送就优选推送。
  7. SDK 流式 API 怎么设计才好用？ 双范式：底层 Async Generator，上层回调包装（onDelta/onDone/onError），兼容不同消费风格。
  8. Token 用量怎么统计？ 解析流式最后一个 chunk 的 usage（OpenAI 系需 include_usage），本地按会话/用户累加，BFF 另存一份对账。
  9. SDK 交付（对外）要注意什么？ 完整类型、ESM+UMD 双产物、统一错误模型、全可配置、无框架绑定、可观测、带 Mock 便于测试。
  10. 流式请求超时怎么设？ 拆成连接/首字节超时（短）+ 整体时长上限（长），配 AbortController，既不误杀长回答又防挂起。
