流式渲染与 AI 交互界面 ​

AI 交互界面的「血液系统」是流式传输，它决定首字延迟、渲染节奏与中断体验；「骨架」则是会话状态机、消息渲染与滚动跟随。本文按「为什么流式 → 三种传输方案 → SSE 前端处理 → 打字机 → Markdown 渲染 → 会话管理 → CoT/工具/引用 → 三态与性能 → 可访问性 → 常见坑」组织。协议层背景见 实时通信：WebSocket / SSE，多模型封装见 多模型接入与前端 SDK。

覆盖 JD 对应点：#10 欣农互联「AI 产品前端（问答/Agent/RAG）」、#3 腾讯外包「AI Agent 界面」、#9 今天国际「AI 协作能力」；本页是「AI 产品界面（流式/Agent/RAG）」这一类 C 级加分的核心证据页。

一、为什么 AI 交互必须流式 ​

一次完整生成可能要 10–60 秒。非流式请求下用户全程面对 loading，感知是「卡死了」；流式则让第一个字几百毫秒内出现，感知是「它在想、它在写」。

指标含义前端可做的优化
TTFT（Time To First Token）首 Token 延迟，决定「快不快」缩短出请求路径、预热连接、先展示骨架
TPOT（Time Per Output Token）Token 间隔，决定「顺不顺」rAF 批量渲染、虚拟化长文本
中断响应点「停止」到真正停下AbortController 贯穿全链路

关键点：流式不缩短总时长，但把「感知等待」从 30 秒压到 0.3 秒。

二、三种流式传输方案对比 ​

维度SSE (EventSource)WebSocketFetch Stream
方向单向（服务端 → 客户端）全双工单向（请求/响应各一流）
请求方法仅 GET任意任意，POST 友好
自定义 Header不支持握手阶段支持完全支持
数据格式纯文本（UTF-8）文本 + 二进制任意字节流
自动重连原生支持需自实现需自实现
中断close()close()AbortController
浏览器 APIEventSourceWebSocketfetch + ReadableStream

LLM 场景结论：对话是「问一次、推一串」的半双工，不需要 WebSocket；请求要带 JSON body 与鉴权头，EventSource 的「仅 GET + 无自定义 Header」不可接受；Fetch Stream 是 OpenAI / Claude / DeepSeek 等的主流事实标准。EventSource 只适合无鉴权的公共事件流。

三、SSE 前端处理 ​

3.1 报文与 OpenAI 分片字段 ​

响应头 Content-Type: text/event-stream，事件块之间用**空行（\n\n）**分隔；以 : 开头的行是注释（常用作心跳）；同一事件可有多行 data:，客户端用 \n 拼接：

: 心跳注释（冒号开头，保活用）

event: message
data: {"choices":[{"delta":{"content":"今天"},"finish_reason":null}]}
id: 1

OpenAI 流式分片的关键字段：

字段含义前端关注
choices[0].delta.content本次增量文本累加拼接
choices[0].delta.role首个 chunk 标记角色初始化消息对象
choices[0].finish_reason结束原因stop/length/tool_calls/content_filter
usageToken 用量通常最后一个 chunk 才有
data: [DONE]流结束标记非 JSON，必须特判

3.2 fetch + ReadableStream 手写解析（面试手写题核心） ​

ts
export interface StreamDelta {
  content?: string
  reasoning?: string
  finishReason?: string | null
  usage?: { prompt_tokens: number; completion_tokens: number }
}

export async function* streamChat(url: string, body: unknown, signal?: AbortSignal): AsyncGenerator<StreamDelta> {
  const res = await fetch(url, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ ...body, stream: true }),
    signal, // 与 AbortController 关联，支持「停止生成」
  })
  if (!res.ok || !res.body) throw new Error(`HTTP ${res.status}`)

  const reader = res.body.getReader()
  const decoder = new TextDecoder('utf-8')
  let buffer = '' // 跨 TCP 包的不完整数据先攒着

  try {
    while (true) {
      const { done, value } = await reader.read()
      if (done) break
      // stream:true 让解码器保留被截断的多字节字符（一个汉字 3 字节，可能跨包）
      buffer += decoder.decode(value, { stream: true })

      const events = buffer.split('\n\n') // 按事件分隔符切分
      buffer = events.pop() ?? ''         // 尾部可能不完整，留到下一轮

      for (const evt of events) {
        for (const line of evt.split('\n')) {
          if (!line.startsWith('data:')) continue
          const payload = line.slice(5).trim()
          if (payload === '[DONE]') return // 特判，不做 JSON.parse
          try {
            const json = JSON.parse(payload)
            const choice = json.choices?.[0]
            if (choice || json.usage) {
              yield {
                content: choice?.delta?.content,
                reasoning: choice?.delta?.reasoning_content,
                finishReason: choice?.finish_reason ?? null,
                usage: json.usage,
              }
            }
          } catch {
            // 坏行忽略，不中断整条流
          }
        }
      }
    }
  } finally {
    reader.releaseLock()
  }
}

评分点：TextDecoder 用 { stream: true }；缓冲区 split('\n\n') 后 pop() 保留残段；[DONE] 特判；try/finally 释放 reader 锁；AbortSignal 贯穿；Async Generator 让消费侧清爽。

3.3 增量拼接与中断 ​

ts
const ctrl = new AbortController()
let acc = ''
try {
  for await (const d of streamChat('/api/chat', payload, ctrl.signal)) {
    if (d.content) acc += d.content
    flush(acc) // 交给渲染层
  }
} catch (e) {
  if (e instanceof DOMException && e.name === 'AbortError') {
    markAsAborted(acc) // 用户主动停止：保留已生成内容并标记「已中断」
  } else {
    markAsFailed(e)
  }
}

注意：abort() 只中断浏览器侧连接，服务端仍在烧推理成本——BFF 必须监听客户端连接关闭并同步 abort 上游请求。

四、打字机效果：rAF 节流 ​

不要「每个 chunk 都 setState」——模型每秒可能推 20–50 个 chunk，逐次渲染会让低端机掉帧。正确做法是攒到 ref，按 rAF 每帧批量 flush 一次：

ts
export class TypewriterQueue {
  private pending = ''
  private displayed = ''
  private raf = 0
  constructor(private onFlush: (text: string) => void, private charsPerFrame = 3) {}

  push(delta: string) {
    this.pending += delta
    if (!this.raf) this.raf = requestAnimationFrame(this.tick)
  }

  private tick = () => {
    this.raf = 0
    if (!this.pending) return
    this.displayed += this.pending.slice(0, this.charsPerFrame)
    this.pending = this.pending.slice(this.charsPerFrame)
    this.onFlush(this.displayed)
    if (this.pending) this.raf = requestAnimationFrame(this.tick)
  }

  stop() {
    if (this.raf) cancelAnimationFrame(this.raf)
    this.raf = 0
    this.pending = ''
  }
}

要点：不要用 setInterval（后台标签页被节流到 ≥1s，切回来会「憋一大批」）；流已结束但队列没排空时不能解锁输入框；低端机调低 charsPerFrame。

五、Markdown 与代码块渲染（增量） ​

流式 Markdown 的难点是未闭合语法（半个代码围栏、半截表格、未闭合行内代码）。策略是每帧重解析整段文本，但未闭合块降级为纯文本；代码高亮只在围栏闭合或流结束后执行，过程态先渲染纯文本。

tsx
import { marked } from 'marked'
import DOMPurify from 'dompurify'
import { useMemo } from 'react'

export function MarkdownView({ text }: { text: string }) {
  const safe = useMemo(() => {
    // 按 code fence 切段，未闭合的 "$" 兜底能匹配到行尾
    const parts = text.split(/(^```[\s\S]*?(?:```|$))/m)
    const html = parts
      .map((p) => (p.startsWith('```') ? `<pre class="code-block">${escapeHtml(p)}</pre>` : (marked.parse(p) as string)))
      .join('')
    // 模型输出不可信（可能被 Prompt 注入污染），必须 sanitize 防 XSS
    return DOMPurify.sanitize(html)
  }, [text])
  return <div className="markdown" dangerouslySetInnerHTML={{ __html: safe }} />
}

注意：卡片化渲染（React 组件树）比 innerHTML 更安全可控，适合对引用角标做交互；但无论哪种，sanitize 都不能省。

六、多轮会话管理 ​

会话的核心是消息状态机，每条 assistant 消息有明确阶段：pending → streaming → (done | aborted | failed)。

ts
type MsgStatus = 'pending' | 'streaming' | 'done' | 'aborted' | 'failed'
interface ChatMessage { id: string; role: 'user' | 'assistant'; content: string; status?: MsgStatus }

function reducer(state: ChatMessage[], action: Action): ChatMessage[] {
  switch (action.type) {
    case 'add':
      return [...state, action.msg]
    case 'append': // 只更新目标消息，其余引用不变 —— 配合 memo 精准重渲染
      return state.map((m) => (m.id === action.id ? { ...m, content: m.content + action.delta } : m))
    case 'setStatus':
      return state.map((m) => (m.id === action.id ? { ...m, status: action.status } : m))
    case 'truncateAfter': // 编辑重发：截断该消息之后的所有轮次
      return state.slice(0, state.findIndex((m) => m.id === action.id) + 1)
    default:
      return state
  }
}

三个易被追问的工程点：

  1. 滚动跟随：用户没手动上滑时自动吸底；一旦上滑阅读历史，停止自动跟随并显示「回到底部」按钮（依据 scrollTop + clientHeight >= scrollHeight - threshold）。
  2. 取消生成：每个会话独立 AbortController，连接挂在 store 而非组件，切换会话不中断其他流。
  3. 截断重发：编辑用户消息后必须 truncateAfter 丢掉旧回答，否则历史里会留下与当前上下文不一致的孤儿 assistant 消息。

七、CoT、工具调用与引用溯源 ​

  • CoT 思维链：支持推理的模型（DeepSeek-R1、QwQ 等）通过 delta.reasoning_content 单独推送思考过程。用折叠面板（<details>）独立分层，默认收起显示「已思考 N 秒」，content 出现后收起；折叠不等于删除，展开要能看到完整推理。
  • 工具调用可视化：用步骤卡展示 工具名 → 参数 → 状态 → 结果。arguments 是 JSON 字符串要先 parse；流式下 tool_call 可能分片到达，需按 index/callId 累积；写操作（发邮件、下单、删除）必须 Human-in-the-loop 确认。
  • 引用溯源：回答正文 [1][2] 角标与底部来源卡双向联动（详见 Agent 编排与 RAG 界面）。流式下最大难点是时序不一致：角标先渲染占位态（不可点击/置灰），citation 到齐后激活；解析 [n] 用增量识别，未闭合的 [1 保持原文。

type ToolStep = {

  status: 'running' | 'success' | 'failed' | 'awaiting_confirm'

function ToolCallSteps({ steps, onConfirm }: { steps: ToolStep[]; onConfirm: (id: string) => void }) {

八、三态与长会话性能 ​

状态表现关键点
加载态首字节前显示打字光标或骨架别显示转圈，用户会以为卡死
生成中断保留已生成内容 + 「生成中断，点击重试」不能清空已产出
限流/超时明确文案 + 重试按钮区分「限流（稍后重试）」与「超时（可重试）」
空态引导示例问题降低首次使用门槛
无引用顶部黄条「该回答未基于知识库」提示可信度

历史消息上千条时，虚拟列表（如 @tanstack/react-virtual）只渲染视口内消息；难点是流式消息高度动态变化，需要「测量 + 缓存高度 + 吸底补偿」。另外：离屏的历史消息降级为纯文本、进入视口再渲染 Markdown；流式增量只更新当前那条消息的订阅者，历史消息用 memo 隔离。

九、可访问性 ​

流式输出容器用 aria-live="polite"，避免屏幕阅读器每个 chunk 都打断朗读；「停止生成」用语义化 <button> 且键盘可达；代码块与引用角标提供可聚焦的 aria-label；尊重 prefers-reduced-motion，减弱打字机动画与呼吸灯。

十、常见坑与实战要点 ​

  1. 每个 chunk 都 setState：20–50 次/秒渲染抖动，改用 rAF 批量 flush。
  2. TextDecoder 没用 { stream: true }：中文字符跨 TCP 包被截断，出现乱码。
  3. 忘了缓冲区残段：直接 split('\n\n') 不 pop()，会把半截事件当完整事件解析失败。
  4. 把 [DONE] 也 JSON.parse：抛异常导致流提前中断。
  5. abort 只管前端：BFF 不联动会持续烧钱推理。
  6. Markdown 不 sanitize：Prompt 注入可造成 XSS。
  7. 代码高亮逐帧跑：性能杀手，改为闭合或流结束后高亮。
  8. 自动滚动不设边界：用户翻历史时被强行拽回底部，体验灾难。
  9. 后台标签页用 setInterval 打字：被节流，切回来一大坨内容突然喷出，改用 rAF。
  10. 中断后清空内容：用户可能想保留半截答案，应保留并标记。

面试要点 ​

  1. 为什么 AI 对话要用流式？ 自回归逐 Token 生成，非流式要等几十秒；流式把 TTFT 从数十秒降到几百毫秒，感知质变。
  2. SSE / WebSocket / Fetch Stream 怎么选？ 单向推送 SSE，双向实时 WebSocket，LLM 场景要 POST + 自定义 Header 用 Fetch Stream。
  3. 手写 Fetch Stream 解析 SSE 的关键点？ TextDecoder {stream:true} 处理多字节截断、缓冲区按 \n\n 切分并保留残段、[DONE] 特判、AbortSignal、finally 释放 reader。
  4. 为什么不用 EventSource？ 仅支持 GET、不能自定义 Header（Key 只能进 URL）、无法带复杂 JSON body。
  5. 流式渲染为什么不能每个 chunk 都 setState？ 每秒 20–50 次渲染导致掉帧，用 rAF 把增量攒到 ref 每帧批量 flush。
  6. 如何实现「停止生成」？ 前端 AbortController.abort() 中断 fetch，保留已生成内容并标记中断；BFF 需同步 abort 上游，避免浪费推理成本。
  7. 流式中断能重连续写吗？ 伪命题——服务端推理上下文已丢，只能重新发起完整请求；工程上引导用户重试并告知会重新计费。
  8. 流式 Markdown 的难点是什么？ 未闭合语法（半截围栏/表格），需降级渲染 + 增量识别；且必须 sanitize 防 XSS，高亮不能逐帧跑。
  9. CoT 思考过程怎么展示？ 用折叠面板独立分层，默认收起显示「已思考 N 秒」，与正式回答分区渲染，内容可展开不可丢。
  10. 长会话列表怎么优化？ 虚拟列表 + 高度测量缓存 + 吸底补偿；流式消息只更新自身订阅者，历史消息降级为纯文本并用 memo 隔离。
