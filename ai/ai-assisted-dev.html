AI 辅助研发与质量门禁 ​

把 Cursor / Copilot / Claude Code / Trae 从「个人玩具」变成「团队生产力」，核心不是买工具，而是建立**「契约定义 → AI 生成 → 迭代修复 → 质量验收」四阶段工作流，以及一套不依赖人眼自觉的 CI 门禁**。本文按「工具生态 → 四阶段方法论 → 如何识别 AI 代码问题 → 门禁机器化 → AI 生成测试 → Prompt 技巧 → 审查清单 → 风险 → 度量 → 常见坑」组织。门禁背后的测试与架构约束原理见 单元测试（Vitest）、端到端测试（Playwright）、架构约束与依赖治理、代码规范与静态检查、CI/CD 与自动化发布。

覆盖 JD 对应点：#9 今天国际把「AI 协作能力」列为硬性第 2 条并要求「对 AI 产出严谨 Review」、#3 腾讯外包「AI 研发提效」、#1 星河视控 / #8 鹏开信息等 3 份 JD 提及「AI 编程助手 + 对 AI 产出严谨 Review」。这是本知识库最强的差异化证据页。

一、AI 编码工具生态 ​

典型场景日常编码加速中型特性、跨文件修改完整任务交付、重构、脚手架完整任务、跨文件中文注释/单测补全补全 + 任务

分层认知（不止「谁更聪明」，而是交互粒度与上下文组织方式不同）：

  • 补全级（Copilot / 灵码）：预测下一行，人始终握方向盘，随用随走。
  • IDE 级（Cursor / Trae）：文件级 / 多文件编辑，需要会组织上下文。
  • Agent 级（Claude Code / Trae Agent）：交付完整任务，能自主读仓库、执行命令、自我修正，人的角色变成定契约 + 做验收。

一个常被低估的因果链：补全工具的接受率取决于代码本身模式是否统一、命名是否规范；Agent 工具的产出质量则与规则文件（CLAUDE.md / .cursor/rules）质量强相关。所以「先把工程规范做好，AI 才能用好」是前置条件，不是口号。

二、AI 辅助研发四阶段方法论 ​

阶段人的职责AI 的职责产出物
1 契约定义定接口/类型/验收标准，拆任务参与方案讨论、提建议类型定义、接口注释、任务清单
2 AI 生成提供上下文、把控方向按契约生成实现可运行代码
3 迭代修复指出偏差、补充边界 case按反馈定向修复修正后代码
4 质量验收跑门禁、review 关键路径可辅助生成测试用例通过门禁的 MR

关键认知：人的价值在前移——从「写代码」转到「定契约」和「做验收」。契约越清晰，AI 生成越少跑偏，迭代轮次越少。

契约先行的实操：先手写类型定义（如 src/sdk/types.ts 的 Provider 接口与消息类型），再让 AI 按接口生成实现（流式解析），最后用 Mock 数据验证边界——这就是一次完整循环。

ts
// 步骤 1：人写契约（类型即规格）
export interface ModelProvider {
  readonly name: string
  chat(req: ChatRequest, signal?: AbortSignal): Promise<ChatMessage>
  streamChat(req: ChatRequest, signal?: AbortSignal): AsyncGenerator<StreamChunk>
}
// 步骤 2：把契约 + 验收标准交给 AI，生成 openaiCompatible.ts 的实现
// 步骤 3：跑 tsc + 单测，把失败信息回喂给 AI 修复

常见翻车模式：跳过契约直接生成（「先让 AI 写写看」），然后花三倍时间改 AI 的代码。宁可在契约阶段多花 20 分钟，也不在修复阶段多花 2 小时。

迭代修复的反馈技巧：指问题不指方案——说清「行为应该是 X 而实际是 Y」，让 AI 自己修正，保持上下文连贯；连续两轮修不对同一个问题，说明上下文已被带偏，开新会话重述契约比继续纠缠高效。

三、如何识别 AI 代码的问题（不盲目采纳） ​

AI 生成的是「看起来合理」的代码，不一定是「正确」的代码。三类高频问题要专项审查：

3.1 安全漏洞 ​

模式表现检查点
XSSinnerHTML / dangerouslySetInnerHTML 直接塞未净化内容是否经 DOMPurify 等净化
敏感信息把 Key/token 拼进 URL、写进日志是否走环境变量、是否打印
权限绕过前端仅凭 role 字段隐藏按钮，未做接口鉴权后端是否二次校验
反序列化/依赖引入不明来源的 npm 包、eval依赖来源与许可

3.2 性能隐患 ​

  • N+1 请求：循环里 await 逐个发请求，未用并发池。
  • 每 chunk setState：流式场景高频渲染（见 流式渲染与 AI 交互界面）。
  • 无节流/防抖：搜索框、滚动、resize 未做控制。
  • 全量渲染大列表：不虚拟化。
  • 重渲染失控：内联对象/函数 props 导致子组件频繁重渲。

3.3 架构问题 ​

  • 分层破坏：页面直接依赖底层工具包，绕过分层。
  • 循环依赖：A import B、B import A。
  • 过度抽象：AI 偏爱「看起来专业」的配置层/工厂层，多余的抽象要砍掉。
  • 依赖方向反了：shared 反向依赖上层。

核心原则：这些问题单测测不出、人眼 review 易漏，而且在 AI 批量产出时扩散更快。所以必须把它们翻译成能自动失败的机器规则，而不是靠 reviewer 每篇代码逐行盯。

四、CI 门禁：把「审查」机器化 ​

门禁顺序按快 → 慢排，前面的失败就不跑后面。这条链路与 架构约束与依赖治理 的 verify 脚本一致：

阶段命令拦截的问题级别
1 typechecktsc --noEmit类型糊弄、as any、契约漂移error
2 linteslint .风格漂移、禁用 API、可疑模式error
3 架构检查depcruise --config .dependency-cruiser.cjs分层破坏、循环依赖、跨框架耦合error
4 构建审计vite build + 体积预算意外依赖引入、包体膨胀error
5 全量测试vitest run --coverage逻辑错误、覆盖率不达标error
6 契约对齐测试tsx scripts/contract-test.ts双端 API 分叉、生成代码偏离契约error
json
// package.json：一条命令串起全部门禁
{
  "scripts": {
    "type-check": "tsc --noEmit",
    "lint": "eslint . --max-warnings 0",
    "arch:check": "depcruise --config .dependency-cruiser.cjs apps packages",
    "audit:size": "tsx scripts/check-bundle-size.ts",
    "test:coverage": "vitest run --coverage",
    "contract-test": "tsx scripts/contract-test.ts",
    "verify": "pnpm type-check && pnpm lint && pnpm arch:check && pnpm build && pnpm audit:size && pnpm test:coverage && pnpm contract-test"
  }
}

架构规则示例（dependency-cruiser 的关键几条）：

js
// .dependency-cruiser.cjs（节选）
module.exports = {
  forbidden: [
    { name: 'no-circular', severity: 'error', from: {}, to: { circular: true } },
    { name: 'shared-is-leaf', severity: 'error', from: { path: '^packages/shared' }, to: { path: '^(apps|pages)' } },
    { name: 'no-layer-skip', severity: 'error', from: { path: '^apps' }, to: { path: '^packages/shared' } },
    { name: 'adapters-are-isolated', severity: 'error', from: { path: '^packages/vue' }, to: { path: '^packages/react' } },
  ],
}

契约对齐测试是把「AI 实现是否符合契约」机器化的关键一环：对统一接口/双端组件，用同一组用例断言双端行为一致，AI 生成越界即失败。

ts
// scripts/contract-test.ts（思路示意）
import { providers } from '../src/sdk'
import { assertStreamContract } from './contract-helpers'

// 每个 Provider 都必须满足同一份流式契约
for (const [name, p] of Object.entries(providers)) {
  await assertStreamContract(p, {
    // 契约断言：首个 chunk 之后必有 content、结束必有 finishReason、usage 字段类型正确
    expectFirstChunkRole: true,
    expectFinishReason: true,
  }, `provider:${name}`)
}

门禁的底线：AI 生成代码过和人工代码一样甚至更严的 CI 门禁，没有豁免。能被绕过的约束等于没有约束。

五、AI 批量生成测试与覆盖率阈值 ​

5.1 分工与「镜像实现」陷阱 ​

AI 擅长铺开用例矩阵（正常 / 边界 / 异常）和写测试骨架，能显著提升覆盖率；但最大的坑是镜像实现——照抄被测代码的逻辑推算期望值，实现对测试就对，实现错测试也错，失去检验意义。

正确分工：

  • 关键断言（输入 → 期望输出）由人依据业务语义给出。
  • AI 负责展开与组织 case 矩阵。
  • review 测试时重点看期望值来源，不只看覆盖率数字。
ts
// 错误：期望值由实现逻辑推导（镜像实现）
// const expected = fn(input)   ← 用实现对测试，无检验力

// 正确：期望值来自人的业务判断
import { describe, it, expect } from 'vitest'
import { trimByBudget } from '../src/chat/trim'

describe('trimByBudget', () => {
  it('预算不足时优先保留最近的消息', () => {
    const counter = (s: string) => s.length
    const msgs = [
      { role: 'system', content: 'S' },      // 1
      { role: 'user', content: 'AAAA' },     // 4
      { role: 'user', content: 'BBBB' },     // 4
    ]
    // 人给的期望：budget=6 → 保留 system(1) + 最近一条(4) = 5，丢弃最早那条
    expect(trimByBudget(msgs, 6, counter)).toEqual([
      { role: 'system', content: 'S' },
      { role: 'user', content: 'BBBB' },
    ])
  })
})

5.2 覆盖率阈值写进配置而非口头约定 ​

ts
// vitest.config.ts
export default defineConfig({
  test: {
    coverage: {
      provider: 'v8',
      reporter: ['text', 'lcov'],
      include: ['src/**/*.{ts,tsx}'],
      exclude: ['src/**/index.ts', 'src/**/*.d.ts'],
      thresholds: { lines: 80, branches: 75, functions: 80, statements: 80 },
    },
  },
})

机制：阈值写在配置里，vitest run --coverage 不达标即非零退出，天然成为 CI 门禁，无需 CI 二次判断。再上报 lcov 到 codecov 可做 PR 增量覆盖率，防止「总量够但新代码零覆盖」。覆盖率是下限而非目标——为凑百分比测无分支 getter 是坏味道，重点是关键分支、边界与错误路径。

六、Prompt 编写技巧 ​

把「一句话需求」升级为「带契约的工单」，四个要素缺一不可：

  1. 提供上下文：要改的文件/函数、相关约定、技术栈版本。
  2. 给定约束：边界（不做什么）、禁止项（不引入依赖、不改公共 API）、风格。
  3. 明确验收标准：什么算完成（tsc 通过、测试通过、行为符合描述）。
  4. 给示例：贴 1–2 个符合规范的现有实现作参照。
错误（开盲盒）：
帮我写一个文件上传组件。

正确（带契约的工单）：
在 src/shared/components/ 下新增 UploadList 组件。
- Props：files: UploadFile[]（含 name/size/status/progress）、onRetry(id)、onRemove(id)
- 状态：uploading / success / failed 三态展示，failed 行显示「重试」按钮
- 约束：遵循 CLAUDE.md 组件规范；样式用 CSS Modules；不引入新依赖
- 验收：tsc 无报错；补 Vitest 单测覆盖三态渲染；不改变现有 UploadButton 的对外 API

规则文件（CLAUDE.md / .cursor/rules） 是团队规范的沉淀载体，随仓库提交，让 AI 每次都「带着团队规范工作」：

markdown
# 项目约定
- 技术栈：React 19 + TypeScript 严格模式 + Vite，样式用 CSS Modules
- 组件规范：函数组件；Props 必须显式声明 interface；禁止 default export
- 状态管理：局部用 useState，跨组件用 Zustand；禁止修改 props
- 目录约定：apps → pages → shared 单向依赖，禁止跨层反向引用
- 测试：hooks 与工具函数必须配 Vitest 单测
- 提交信息：遵循 Conventional Commits

规则文件要少而硬：只写 AI 容易违反或团队强约束的规则，几十行以内；写模糊规则（「写出高质量代码」）不如不写——AI 无法执行还稀释其他规则权重。维护方式：每轮 review 里反复出现的错误，翻译成下一条规则补进去。

七、AI 产出审查清单 ​

Review AI 代码时逐条过：

  • 类型是否诚实：没有 as any 糊弄、没有为过编译乱放宽类型。
  • 边界是否处理：空数组、空字符串、超时、重复提交、并发、异常路径。
  • 安全是否达标：无未净化 HTML 注入、无硬编码密钥、无日志泄露、前端隐藏不等于鉴权。
  • 架构是否合规：依赖方向、分层约定、命名是否与现有代码一致（过 arch:check）。
  • 是否过度设计：AI 偏爱的多余配置层/工厂/抽象类，砍掉。
  • 测试是否有效：断言来自业务语义而非镜像实现。
  • 依赖是否必要：新增依赖的理由、体积影响、许可证、维护活跃度。

八、风险与边界 ​

风险说明应对
幻觉代码调用不存在的 API、编造配置项类型检查 + 单测 + 运行验证，不靠「看起来对」
过度抽象引入无谓的配置层/工厂review 清单专项核查
依赖引入为一个函数引入一个大包体积预算门禁 + 依赖审查
许可证生成片段与开源代码高度相似关键算法人工确认原创性；CI 加 license 扫描
密钥泄露敏感信息进上下文企业版/私有化部署，.cursorignore 排除敏感目录，密钥只放环境变量
责任外包不理解就提交提交者对质量负全责，review 标准不降
上下文污染长会话忘记早期约束定期开新会话重述契约

底线：无论谁生成，谁提交谁负责；合规与安全责任不因「AI 写的」而转移。

九、团队落地与提效度量 ​

落地路径：

个人提效验证 → 规范沉淀（规则文件 + Prompt 模板库）→ 流程嵌入（PR 模板 + CI 门禁）→ 度量闭环

人力不可复制的技巧要资产化才能抬升团队均值：

指标采集方式健康信号
交付周期（需求 → 上线）项目管理工具中等特性周期下降
AI 生成代码占比PR 模板标注上升但缺陷率不升
缺陷归因中「AI 生成」占比线上复盘标记稳定或下降
PR review 轮次代码平台统计接近人工水平
物理指标—不要用「生成多少行代码」当成果，代码行数是成本不是产出

推广阻力应对：抵触多来自「生成代码不可信」——用「有门禁 + 小任务试点 + 数据对比」逐步建立信任，不搞强制全员切换。

十、常见坑与实战要点 ​

  1. 跳过契约直接生成：没有契约约束的代码，每处修改都可能引入新不一致。
  2. AI 代码豁免 CI 门禁：一次豁免就毁掉整套约束，必须一视同仁。
  3. 只看覆盖率不看期望值来源：镜像实现的测试越多越危险。
  4. dangerouslySetInnerHTML 未净化：AI 常这么写渲染逻辑，安全专项必查。
  5. 无体积预算门禁：AI 顺手引入的依赖会悄悄把包体翻倍。
  6. 规则文件写太虚：模糊规则无法执行，还稀释有效规则。
  7. 长会话无限续聊：上下文被带偏后越修越错，及时开新会话。
  8. 用「生成行数」证明提效：不可信且方向错，应看交付周期与缺陷率。
  9. 密钥进上下文：任何进了上下文的内容都当作已离开本机。
  10. 不做契约对齐测试：AI 生成易与既有接口分叉（如双端组件 API 不一致），需机器断言。

面试要点 ​

  1. AI 生成代码你怎么保证质量？ 四层：契约先行（定类型/接口/验收标准）→ 任务拆小 → CI 门禁（typecheck/lint/架构/构建/测试/契约对齐）→ 人工 review 关键路径。
  2. 怎么识别 AI 代码的安全漏洞？ 重点查未净化的 HTML 注入、硬编码密钥、日志泄露、伪鉴权（前端隐藏按钮不等于后端鉴权），并让安全扫描门禁兜底。
  3. AI 代码的性能隐患有哪些？ N+1 请求、流式每 chunk setState、无节流防抖、大列表不虚拟化、内联 props 导致重渲染。
  4. 架构问题怎么发现？ 靠 dependency-cruiser 等把分层/循环依赖/跨框架耦合成 CI 红线；人眼 review 漏的部分机器兜。
  5. 为什么门禁要机器化？ 这些问题单测测不出、人眼易漏，且在 AI 批量产出时扩散更快；能被绕过的约束等于没有约束。
  6. 四阶段方法论是什么？ 契约定义（人）→ AI 生成 → 迭代修复（指问题不指方案）→ 质量验收（门禁 + review）。
  7. AI 生成测试靠谱吗？覆盖率阈值怎么落地？ 部分靠谱——AI 铺用例矩阵与骨架，关键断言由人按业务语义给出，提防「镜像实现」；阈值写进 vitest 配置，vitest run --coverage 不达标非零退出，直接成为 CI 门禁。
  8. Prompt 怎么写才有效？ 提供上下文（文件/约定）、约束（边界/禁止项）、验收标准、示例；规则文件沉淀团队规范并少而硬。
  9. 怎么证明 AI 辅助研发的收益？ 用交付周期与缺陷率这对矛盾指标 + 具体案例，不用「生成行数」或「提效 10 倍」这类不可验证的说法。
  10. AI 代码的许可证风险怎么控？ 关键算法确认原创性、CI 加 license 扫描、企业工具开相似代码过滤；底线是合规责任不转移，谁提交谁负责。
