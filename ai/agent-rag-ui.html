Agent 编排与 RAG 界面 ​

AI 产品前端的「后台重器」有两类界面：Agent 编排画布（把 Agent 能力拆成可拖拽的节点-边流程）与 RAG 知识库界面（文档上传、解析、检索、引用的全链路管理）。本文按「Agent 概念 → 工作流画布 → 编排实现要点 → RAG 知识库界面 → 知识库管理 → RAG 交互范式 → 运行监控 → 常见坑」组织。流式渲染细节见 流式渲染与 AI 交互界面，图形生态见 AntV 生态（G2/G6/X6）。

覆盖 JD 对应点：#10 欣农互联「AI 产品前端（问答 / Agent / RAG）+ React Native 跨端」、#3 腾讯外包「AI Agent 界面」、#1 星河视控 / #7 润信智能「监控 + 大屏 + 数字孪生」（Agent 运行监控与编排画布可复用大屏与图形能力）。

一、AI Agent 概念 ​

Agent 与普通对话的本质区别：普通对话是「文本进、文本出」，Agent 是**「感知 → 规划 → 执行 → 观察 → 反思」的循环**，模型能主动调用工具、记住中间状态、根据结果调整下一步。

能力含义前端可见形态
规划（Planning）把任务拆成有序子步骤步骤列表 / 待办清单
工具（Tools）Function Calling 调用外部 API工具调用卡片 + 参数
记忆（Memory）长期（向量库）+ 短期（会话）历史消息、知识库引用
反思（Reflection）自我检查、修正、重试重试节点 / 反思文本

两种主流编排形态：ReAct 式（隐式循环，模型逐步输出 Thought/Action/Observation，前端展示增长的步骤流）与画布式（显式编排，用户串起「LLM → 条件分支 → 工具 → 知识库检索 → 结束」的 DAG，由后端执行引擎跑）。

2.2 节点-边-连接桩数据模型 ​

tsx
import { Handle, Position, type NodeProps, type Node, type Edge } from '@xyflow/react'

export interface WorkflowNode extends Node {
  id: string
  type: 'start' | 'llm' | 'tool' | 'retrieval' | 'condition' | 'end' // 决定渲染哪个组件
  position: { x: number; y: number }
  data: { label: string; model?: string; prompt?: string; status?: 'idle' | 'running' | 'success' | 'failed' }
}

export interface WorkflowEdge extends Edge {
  id: string
  source: string // 起点节点 id
  sourceHandle?: string // 出参桩：一对多出参时区分走哪条边
  target: string
  targetHandle?: string // 入参桩
  label?: string        // 条件分支的「是 / 否」
}

连接桩（Handle / Port） 是 AI 编排的关键：一个条件分支节点有多个 source handle，每条出边用 sourceHandle 记录走哪个分支。

tsx
function ConditionNode({ data, selected }: NodeProps<WorkflowNode>) {
  return (
    <div className={`node node--${data.status ?? 'idle'} ${selected ? 'is-selected' : ''}`}>
      <Handle type="target" position={Position.Left} />
      <div className="node__title">{data.label}</div>
      {/* 两个输出桩，id 与出边 sourceHandle 一一对应 */}
      <Handle type="source" id="true" position={Position.Right} style={{ top: '30%' }} />
      <Handle type="source" id="false" position={Position.Right} style={{ top: '70%' }} />
    </div>
  )
}

2.4 连线校验与环检测 ​

DAG 必须无环，否则执行会死循环。校验分三层，失败一定要有视觉反馈（红色虚线标记非法目标），否则用户以为「拖不动是 bug」。

ts
export function isValidConnection(conn: Connection, nodes: Node[], edges: Edge[]): boolean {
  if (conn.source === conn.target) return false                 // 1. 结构：禁止自连
  if (wouldCreateCycle(conn, edges)) return false               // 2. 拓扑：禁止成环
  const src = nodes.find((n) => n.id === conn.source)?.type
  const tgt = nodes.find((n) => n.id === conn.target)?.type
  return !(tgt === 'start' || src === 'end')                    // 3. 业务：开始无入边/结束无出边
}

// 从 target 出发能否回到 source：能则说明新增这条边成环
function wouldCreateCycle(conn: Connection, edges: Edge[]): boolean {
  const adj = new Map<string, string[]>()
  for (const e of edges) adj.set(e.source, [...(adj.get(e.source) ?? []), e.target])
  const stack = [conn.target!], seen = new Set<string>()
  while (stack.length) {
    const cur = stack.pop()!
    if (cur === conn.source) return true
    if (seen.has(cur)) continue
    seen.add(cur)
    stack.push(...(adj.get(cur) ?? []))
  }
  return false
}

2.5 属性面板 ​

选中节点后右侧编辑其配置。要点是表单随节点类型切换，且改配置只更新该节点的 data，不重建整个 nodes 数组（否则性能与撤销栈都会爆炸）：

tsx
function PropertyPanel({ node, onChange }: { node: WorkflowNode; onChange: (id: string, data: Partial<WorkflowNode['data']>) => void }) {
  const patch = (p: Partial<WorkflowNode['data']>) => onChange(node.id, p)
  if (node.type === 'llm') {
    return <>
      <select value={node.data.model} onChange={(e) => patch({ model: e.target.value })}>
        <option value="deepseek-chat">DeepSeek</option>
        <option value="qwen-plus">通义千问</option>
      </select>
      <textarea value={node.data.prompt} onChange={(e) => patch({ prompt: e.target.value })} />
    </>
  }
  return null // tool / retrieval 节点各自一套表单
}

三、Agent 编排的前端实现要点 ​

  1. 画布状态与执行状态分离：nodes/edges 是编辑态；执行时通过 SSE 推送的 nodeId → status 覆写 data.status，节点按状态渲染（running 呼吸灯 / success 绿框 + 耗时 / failed 红框 + 「重试此节点」）。
  2. 序列化为后端可执行 DSL：只保留拓扑与配置（不含 position/样式），变量引用用 {{nodeId.field}}，带 version 便于演进。
  3. 撤销重做先上快照法：history: [{nodes, edges}] 快照栈 + 限制栈深（如 50）；协作场景再考虑命令模式。
  4. 运行前做校验：schema 校验 + 拓扑校验（无环、开始/结束节点唯一、必有出边/入边），不过则禁止运行并高亮问题节点。
  5. 拓扑排序（Kahn） 决定执行顺序，有环即报错——调试模式要能展示执行路径。

四、RAG 知识库界面 ​

4.1 三级数据模型与文档状态机 ​

知识库（Dataset）→ 文档（Document）→ 分段（Chunk）。文档状态：待解析 → 解析中 → 解析成功 →（可禁用，退出检索），失败可重试。每个状态对应不同操作：失败给「重试 + 失败原因」，成功给「分段预览 / 禁用 / 删除」，解析中只给「查看进度」。

分段策略是创建知识库时最影响效果的选项：

策略原理优点缺点
固定长度按字符/Token 切，可设重叠窗口简单稳定、成本低易截断表格/段落语义
语义分段按标题层级 / 段落 / 句子边界切语义完整、召回质量高chunk 大小不均、实现复杂

4.2 大文件上传与解析进度 ​

大文件（扫描版 PDF 上百 MB）单次 POST 易超时、失败全废，方案是分片上传：

ts
export async function uploadFile(file: File, chunkSize = 4 * 1024 * 1024) {
  const chunks: Blob[] = []
  for (let i = 0; i < file.size; i += chunkSize) chunks.push(file.slice(i, i + chunkSize))
  const hash = await computeHash(file) // 内容 hash → 秒传 / 断点续传标识
  const uploaded = await fetch(`/api/upload/status?hash=${hash}`).then((r) => r.json())
  const todo = chunks.map((c, i) => ({ c, i })).filter(({ i }) => !uploaded.indices.includes(i))

  await promisePool(todo, 3, async ({ c, i }) => {
    await uploadChunk(hash, i, c).catch(() => uploadChunk(hash, i, c)) // 分片级重试
  })
  return fetch('/api/upload/merge', { method: 'POST', body: JSON.stringify({ hash, name: file.name }) })
}

上传与解析是两个独立阶段：解析失败重试是重新触发解析任务，不是重新上传。并发度取 3–6，服务端已有完整文件直接「秒传」。

进度用指数退避轮询（能推送则优先 SSE/WebSocket 推送）：

ts
export async function pollParse(taskId: string, onProgress: (p: number) => void) {
  let delay = 1000
  while (true) {
    if (document.visibilityState !== 'visible') { await sleep(5000); continue } // 页面隐藏降频
    const t = await fetch(`/api/tasks/${taskId}`).then((r) => r.json())
    onProgress(t.progress)
    if (t.status === 'success' || t.status === 'failed') return t
    await sleep(delay)
    delay = Math.min(delay * 2, 10_000) // 1s → 2s → 4s，封顶 10s
  }
}

注意：组件卸载必须取消轮询（AbortController 或标志位），否则内存泄漏 + 无效请求。

4.3 检索结果高亮 ​

tsx
export function Highlight({ text, keyword }: { text: string; keyword: string }) {
  if (!keyword.trim()) return <>{text}</>
  const escaped = keyword.replace(/[.*+?^${}()|[\]\\]/g, '\\$&') // 转义正则特殊字符
  const parts = text.split(new RegExp(`(${escaped})`, 'gi'))
  return <>{parts.map((p, i) => (p.toLowerCase() === keyword.toLowerCase() ? <mark key={i}>{p}</mark> : <span key={i}>{p}</span>))}</>
}
  • 不要用字符串替换 + dangerouslySetInnerHTML 高亮：XSS 风险 + 脱离框架渲染管理，切分渲染是正解。
  • 长 chunk 折叠：默认只显示命中位置前后 N 个字符窗口，点击展开，避免单条撑爆列表。
  • 优先用后端返回的 highlight 字段（分词位置更准），前端关键词匹配只做兜底。

4.4 引用来源（Citation） ​

ts
export interface Citation {
  id: number       // 角标序号，对应正文 [1] [2]
  docId: string
  docName: string
  chunkId: string
  content: string  // 引用原文分段
  score?: number   // 相似度分数
}

联动四步：渲染（把正文 [n] 渲染为可点击上标）→ 来源区（回答下方渲染来源卡片：文档名 + 原文摘要 + 分数色阶）→ 双向联动（点角标 scrollIntoView 到对应卡片并短暂高亮；hover 角标 Tooltip 预览原文）→ 流式兼容（citation 可能先于或后于正文到达，角标支持「未到占位、到了补全」，绝不阻塞正文渲染）。

五、知识库管理 ​

  • 列表：服务端分页 + 状态筛选（不要前端全量拉）。解析中文档单独轮询、行级增量更新，不整表刷新。
  • 权限：知识库级 RBAC（查看 / 编辑 / 使用），检索时按权限过滤可见知识库。
  • 文档状态：除解析状态机，还要有「启用 / 禁用」——禁用文档保留但退出检索。
  • 召回测试（Hit Testing）：输入问题只走检索链路（Embedding → 向量召回 → 重排），返回 Top-K chunk 与分数，不经模型生成。这是把检索黑盒变可视化调试工具的核心界面，让运营/算法自助调参。
  • 分段预览：展示 chunk 列表（内容、Token 数、命中次数），帮助运营诊断「为什么召回不准」。

六、RAG 交互范式 ​

  • 引用卡片：回答内角标 + 底部来源卡，是可信度的载体（时序处理见 流式渲染与 AI 交互界面）。
  • 可信度可视化：相似度分数用进度条 / 色阶；低于阈值时顶部黄条提示「该回答未基于知识库，请谨慎参考」。
  • 追问（Follow-up）：基于当前回答推荐 2–3 个追问，降低提问门槛。
  • 无引用降级：检索不到时明确告知「知识库中没有相关内容」，而非让模型编造。
  • 反馈闭环：点赞/点踩 + 问题归因（引用错 / 答案错 / 无引用），沉淀 badcase 反哺知识与分段策略。

七、Agent 运行监控（大屏式） ​

  • 拓扑运行图：复用编排画布，节点按执行状态实时高亮，边显示数据流（传输中脉冲动画）。
  • 指标面板：QPS、成功率、P95 延迟、Token 消耗、失败节点 Top N。
  • 单次运行追踪（Trace）：时间轴展示每个节点的输入 / 输出 / 耗时，失败节点可单独重跑。
  • 告警：失败率或延迟超阈值时大屏告警。大屏渲染性能沿用 大屏与大数据可视化性能 的策略：动画走 Canvas/WebGL、状态更新合并降频。

八、常见坑与实战要点 ​

  1. 画布连线不校验成环：执行时拓扑排序失败或死循环，必须在 isValidConnection 里做 DFS 环检测。
  2. 手算屏幕 → 画布坐标：忽略缩放/平移导致落点漂移，用 screenToFlowPosition。
  3. 属性面板改动重建整棵 nodes：性能与撤销栈爆炸，要精确更新目标节点。
  4. 画布序列化带 position：后端执行引擎不需要 UI 坐标，DSL 要与 UI 解耦。
  5. 上传与解析耦合：解析失败要重新上传整包文件，应拆成两阶段。
  6. 轮询不取消 / 页面隐藏不停：内存泄漏与无效请求，卸载时清理、隐藏时降频。
  7. 高亮用 innerHTML：XSS 风险，改为切分渲染。
  8. 引用未到就阻塞正文：角标必须先占位，citation 到达再激活。
  9. 文档量大整表刷新：「解析中」文档行级增量更新，静态行不动。
  10. 监控大屏逐帧更新 React 状态：高频状态更新要合并降频，动画交给 Canvas/WebGL。

面试要点 ​

  1. Agent 与普通对话的区别？ Agent 是「感知-规划-执行-观察-反思」循环，能调用工具、保留记忆、自我修正；普通对话只有文本进出。
  2. 画布为什么选 React Flow？ React 生态契合、节点即组件心智极简、MIT 协议、内置拖拽/连线/小地图；复杂图编辑或 Vue 栈才考虑 X6。
  3. 连线校验要做哪些层？ 结构（自连/重复边）、拓扑（DFS 环检测，DAG 必须无环）、业务（开始无入边/结束无出边、类型匹配），失败要有视觉反馈。
  4. 连接桩（Handle）在 AI 编排里的作用？ 让条件分支等多出参节点精确区分走哪条边，边的 sourceHandle 记录分支走向，执行时只跑命中的分支。
  5. 画布怎么和后端执行引擎对接？ 序列化为版本化 JSON DSL，拓扑与配置和 UI 坐标分离，变量用 {{nodeId.field}} 引用，运行前做 schema + 拓扑校验。
  6. 大文件上传要注意什么？ Blob.slice 分片 + 内容 hash（秒传/断点续传）+ 并发 3–6 + 分片级重试；上传与解析拆成两阶段。
  7. 解析进度用什么方案推送？ 先轮询（指数退避、封顶、终态停止），任务量大或实时性高再上 SSE/WebSocket 推送，并处理页面隐藏降频与卸载取消。
  8. 检索高亮为什么不用 innerHTML？ XSS 风险 + 脱离框架渲染管理；正确做法是按关键词切分渲染 <mark>。
  9. RAG 引用与正文时序不一致怎么处理？ 角标先渲染占位态，citation 到达后激活联动；解析 [n] 用增量识别，未闭合标记保持原文。
  10. Agent 运行监控怎么落地？ 复用编排画布做节点状态实时高亮 + 指标面板 + 单次 Trace（节点输入输出耗时、可单节点重跑），大屏性能按大数据可视化策略优化。
