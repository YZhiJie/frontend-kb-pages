Generative UI 与 AI Native 交互 ​

对应 JD：思维巡航 #11 职责第 1 条（围绕 AI Native 产品体验，探索 Generative UI、智能交互能力落地）。同时命中 #10 欣农互联的 AI 产品交互要求。

一、什么是 Generative UI ​

传统前端是「接口返回数据 → 固定模板渲染」；Generative UI 是「AI 输出结构化 UI 描述 → 前端动态映射为组件树渲染」。界面的形态本身由模型在运行时决定，而不是开发期写死。

text
传统：API 返回 JSON ──> 写死的模板 ──> 固定 UI
GenUI：LLM 输出 { component: "WeatherCard", props: {...} } ──> 组件注册表查表 ──> 动态渲染对应组件

核心价值：AI 的回答从「一段文字」升级为「可交互的应用片段」——查天气直接出天气卡片、订机票直接出日期选择器、改数据直接出图表。

二、三种实现形态（由浅入深） ​

形态 1：组件槽位映射（主流，生产可用） ​

LLM 通过 Function Calling / 结构化输出返回白名单内的组件名 + props，前端查表渲染：

tsx
// 1. 组件注册表：只暴露安全、受控的组件
const registry = {
  WeatherCard: lazy(() => import("./gen/WeatherCard")),
  ChartBlock: lazy(() => import("./gen/ChartBlock")),
  FormPanel: lazy(() => import("./gen/FormPanel")),
} as const;

type GenSpec = { component: keyof typeof registry; props: Record<string, unknown> };

// 2. 渲染器：白名单校验 + 兜底
function GenRenderer({ spec }: { spec: GenSpec | null }) {
  if (!spec || !(spec.component in registry)) {
    return <FallbackText />; // 未知组件降级为普通文本，不渲染
  }
  const Comp = registry[spec.component];
  return <Comp {...sanitizeProps(spec.props)} />;
}

要点：模型只能选、不能造组件；props 必须过 schema 校验（zod）后再传入。

形态 2：Schema 驱动动态表单/页面 ​

AI 输出一份 JSON Schema（或类 JSON Schema），前端用通用渲染器（如 react-jsonschema-form、自研 Schema 渲染引擎）生成整块表单或页面。适合「AI 动态生成配置界面」「审批流动态表单」场景。与形态 1 的区别：粒度从「组件」变成「页面片段」。

形态 3：AI 直接生成代码（前沿，风险高） ​

模型生成 JSX/HTML 代码，前端在沙箱（iframe + postMessage、Web Worker、受控 eval）中渲染。Vercel v0 是代表。风险：XSS、不可控样式、性能不可预估——生产环境必须隔离执行 + 白名单依赖。

三、与流式渲染的配合 ​

GenUI 通常跑在 SSE 流式输出之上，难点是JSON 没接收完就要开始渲染：

ts
// 流式 JSON 的容错解析：累积缓冲 + 尝试补全闭合再 parse
function tryParsePartial(buffer: string): object | null {
  for (const suffix of ["}", "}]}", '"}]', "}])")) {
    try {
      return JSON.parse(buffer + suffix);
    } catch {
      /* 继续尝试 */
    }
  }
  return null; // 尚不完整，等待下一个 chunk
}

常见策略：文本部分先打字机上屏；检测到 component 字段完整即提前渲染卡片骨架；props 流完再做二次渲染（骨架屏 → 真实数据）。

四、安全边界（面试必问） ​

风险防御
模型幻觉出不存在的组件白名单注册表，未知组件降级为文本
恶意/越权 propszod schema 校验 + 字段过滤，禁止传 dangerouslySetInnerHTML、href="javascript:"
生成代码注入形态 3 必须 iframe 沙箱隔离，禁同源、禁 Cookie 携带
提示词注入改变 UI 行为组件层无副作用设计：GenUI 组件只展示，写操作必须走用户显式确认

五、AI Voice / Speech 交互范式 ​

思维巡航的音视频清单里专门列了「实时语音交互 / AI Voice / Speech 产品前端」，语音型 AI 产品的前端核心链路：

text
麦克风采集(getUserMedia + AudioWorklet)
  → VAD 静音检测(判断说完没)
  → ASR 实时转写(WebSocket 流式上行)
  → LLM 处理
  → 流式 TTS(音频分片下行)
  → 播放队列(顺序播放 + 可打断)

前端关键机制：

  • VAD（Voice Activity Detection）：本地能量/模型检测用户是否说完，避免每句话都等超时；
  • 打断（barge-in）：用户开口说话时立即停止 TTS 播放并清空播放队列，是语音助手体验的分水岭；
  • 播放队列：TTS 音频分片到达后按序 decodeAudioData 入队，播放指针推进，支持随时 stop() 清队；
  • 实时字幕：ASR 中间结果（不稳定文本）与最终结果（稳定文本）分色渲染，类似直播字幕。

六、常见坑 ​

  1. 把 GenUI 做成 eval HTML：脱离沙箱直接插入模型生成的 HTML 是 XSS 重灾区，坚持白名单组件映射。
  2. 流式 JSON 用 JSON.parse 硬解：必然报错，必须缓冲 + 部分解析策略。
  3. 打断逻辑只清 UI 不清音频：语音场景停止播放必须同时取消未消费的 TTS 分片请求（AbortController）。
  4. 骨架屏到真实数据二次渲染闪烁：骨架与真实组件保持同尺寸布局（min-height 预留），用 transition 平滑。
  5. 组件粒度过细：注册表暴露 50 个原子组件会显著提高模型选错率；暴露 8-15 个业务级复合组件成功率最高。

面试要点 ​

  1. 什么是 Generative UI？ AI 输出结构化 UI 描述（组件名+props 或 Schema），前端白名单映射动态渲染，界面形态由模型运行时决定。
  2. 三种实现形态？ 组件槽位映射（生产主流）、Schema 驱动渲染（动态表单/页面）、AI 生成代码沙箱渲染（v0，风险高）。
  3. 流式 JSON 怎么渲染？ 缓冲累积 + 尝试补全闭合部分解析；文本先上屏、组件骨架提前渲染、props 流完二次渲染。
  4. 安全怎么兜？ 白名单注册表 + zod props 校验 + 沙箱隔离（形态 3）+ GenUI 组件只读无副作用。
  5. 语音 AI 产品前端链路？ 采集 → VAD → 流式 ASR → LLM → 流式 TTS → 播放队列，关键在 VAD 与 barge-in 打断。
  6. 和传统渲染的本质区别？ 传统是数据变化模板不变；GenUI 是模板本身由 AI 生成，前端职责从「写页面」转向「设计组件词汇表 + 安全渲染器」。
