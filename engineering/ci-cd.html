CI/CD 与自动化发布 ​

CI/CD 把「人肉执行」的构建、测试、发布流水线化。本文覆盖流水线阶段设计、GitHub Actions 核心、npm 自动发布、GitHub Pages 部署、Docker/K8s 概念与灰度发布。仓库组织见 pnpm workspace 与 Monorepo，发布物设计见 组件库建设与发布。

一、CI/CD 概念与流水线阶段 ​

  • CI（持续集成）：每次提交自动构建 + 测试 + 静态检查，尽早暴露集成问题。
  • CD：可持续交付（Continuous Delivery，可一键上生产）或持续部署（Continuous Deployment，自动上生产）。

一条典型的门禁流水线（从快到慢，失败即止）：

阶段动作工具目标时长
1 lintESLint/Prettier/Stylelint见 代码规范与静态检查< 1 min
2 typechecktsc --noEmitTypeScript< 1 min
3 testVitest 单测（含覆盖率）Vitest1-3 min
4 build产物构建 + 体积预算Vite/Turbo1-3 min
5 e2ePlaywright 关键路径Playwright3-10 min
6 deploy/publish部署 Pages / 发布 npmActions + CLI1-2 min

设计原则：阶段按「快 → 慢」排序，前面的失败就不必跑后面；能并行就并行（lint 与 typecheck 可同 job）；重型任务（e2e）只在 PR 与主分支触发。

二、GitHub Actions 核心 ​

2.1 概念模型 ​

  • workflow：.github/workflows/*.yml 一个文件。
  • trigger（on）：push、pull_request、release、schedule、workflow_dispatch（手动）、workflow_call（被复用）。
  • job：一组 step，默认并行；用 needs 表达依赖。
  • step：run（shell）或 uses（复用 action）。
  • runner：执行环境（ubuntu-latest 等）。
  • secrets / vars：加密的环境配置。
yaml
name: CI
on:
  push:
    branches: [main]
  pull_request:
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true      # 同一分支新推送自动取消旧运行，省额度
jobs:
  quality:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4     # 用 pnpm
        with: { version: 9 }
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: pnpm }
      - run: pnpm install --frozen-lockfile
      - run: pnpm lint
      - run: pnpm typecheck
      - run: pnpm test -- --coverage

2.2 matrix 多版本矩阵 ​

yaml
strategy:
  fail-fast: false
  matrix:
    node: [18, 20, 22]
    os: [ubuntu-latest, macos-latest]
runs-on: ${{ matrix.os }}
steps:
  - uses: actions/setup-node@v4
    with: { node-version: ${{ matrix.node }}, cache: pnpm }

fail-fast: false 让某个组合失败时其余继续跑完，便于一次看全问题。

2.3 缓存 ​

  • setup-node 的 cache: pnpm 自动缓存 pnpm store。
  • 也可手动用 actions/cache 精确控制 key：
yaml
- uses: actions/cache@v4
  with:
    path: |
      ~/.pnpm-store
      node_modules/.cache/turbo
    key: ${{ runner.os }}-pnpm-${{ hashFiles('pnpm-lock.yaml') }}
    restore-keys: ${{ runner.os }}-pnpm-
  • 缓存 key 要包含 lockfile 的哈希，否则依赖变更后仍命中旧缓存。
  • Turbo 远程缓存用 TURBO_TOKEN/TURBO_TEAM 注入，让 CI 与本地共享构建结果（见 pnpm workspace 与 Monorepo）。

2.4 secrets、权限与 token 安全 ​

  • 敏感值放 Repository/Environment secrets，引用 ${{ secrets.NPM_TOKEN }}，绝不写进 YAML 明文。
  • GITHUB_TOKEN 是 Actions 自动注入的临时令牌。最小权限原则：在 workflow 顶层声明
yaml
permissions:
  contents: read         # 默认收紧
  id-token: write        # 需要 OIDC 时按 job 收敛
  pages: write
  • OIDC 免密发布（npm Trusted Publishing）优于长期 token：npm 侧配置信任 GitHub，Actions 用 id-token: write 换取短期凭据，无需保存 NPM_TOKEN 密钥。
  • 第三方 action 用 pin 到 SHA 或可信大版本，避免 upstream 被投毒（uses: actions/checkout@v4 之外，安全敏感场景用完整 SHA）。

三、自动化发布链路 ​

组件库 + 文档站的一条完整链路：

yaml
name: Release
on:
  push:
    branches: [main]
permissions:
  contents: write        # 让 Changesets 能推 tag / 建 release
  pull-requests: write   # 开 version PR
  id-token: write        # npm OIDC 免密
jobs:
  release:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }        # Changesets 需要完整历史
      - uses: pnpm/action-setup@v4
        with: { version: 9 }
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: pnpm, registry-url: 'https://registry.npmjs.org' }
      - run: pnpm install --frozen-lockfile
      - run: pnpm build
      - run: pnpm test
      - name: Create version PR or publish
        uses: changesets/action@v1
        with:
          publish: pnpm changeset publish
          version: pnpm changeset version
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
          NPM_TOKEN: ${{ secrets.NPM_TOKEN }}

工作方式：有未消费的 changeset 时，Changesets 开一个 version PR（自动升版本、改 CHANGELOG）；该 PR 合并后，再次运行即执行 publish 推到 npm 并打 tag。发布是「合并 version PR」的自然结果，无需手动改版本号。

四、npm 发布要点 ​

4.1 granular token 与 2FA ​

  • 用 Granular Access Token（细粒度、可限定包与权限）替代旧的 Automation token。
  • 账号开了 2FA 时，CI 用 token 发布需要在 token 上勾选 bypass 2FA（或走 OIDC Trusted Publishing，则不需要 token）。
  • token 只在 npm 后台可见一次，立即存进 GitHub Secrets。

4.2 publishConfig 与作用域包 ​

json
// packages/ui/package.json
{
  "name": "@your-org/ui",
  "version": "1.2.0",
  "publishConfig": {
    "access": "public",           // 作用域包默认私有，必须显式 public
    "registry": "https://registry.npmjs.org"
  },
  "files": ["dist", "README.md"],  // 白名单，避免把 src/测试一起发出去
  "main": "./dist/index.cjs",
  "module": "./dist/index.mjs",
  "types": "./dist/index.d.ts",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs"
    },
    "./styles.css": "./dist/styles.css"
  },
  "sideEffects": ["**/*.css"]
}

坑：

  • 作用域包（@scope/name）不加 publishConfig.access: public 会被当私有包，需付费 org 才能推。
  • 作用域包首次发布后，索引（registry search）有延迟（分钟级），不是发布失败。
  • files 白名单外的一切都不会进包；忘记包含 dist 或 types 会导致下游类型报错。
  • exports 的 types 必须放最前、import/require 顺序正确，否则 TS/Node 解析走错分支。

五、GitHub Pages 部署 ​

5.1 base 前缀注入与校验 ​

VitePress/SPA 部署到 https://<user>.github.io/<repo>/ 时，资源路径必须带仓库名前缀，否则 404。

yaml
jobs:
  deploy:
    permissions: { contents: read, pages: write, id-token: write }
    environment:
      name: github-pages
      url: ${{ steps.deploy.outputs.page_url }}
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: pnpm }
      - run: pnpm install --frozen-lockfile
      - name: Build docs with base prefix
        env:
          DOCS_BASE: /${{ github.event.repository.name }}/
        run: pnpm build
      - uses: actions/configure-pages@v5
      - uses: actions/upload-pages-artifact@v3
        with: { path: docs/.vitepress/dist }
      - id: deploy
        uses: actions/deploy-pages@v4

校验：构建产物里的 index.html 是否把 DOCS_BASE 注入到 base（config.mts 里 base: process.env.DOCS_BASE || '/'）；若用了自定义域名（base: '/'），要配套 docs/public/CNAME。

5.2 .nojekyll ​

GitHub Pages 默认用 Jekyll 处理，会忽略以 _ 开头的文件/目录（如 _assets、_next）。静态站必须在产物根放空文件 .nojekyll（VitePress 未必自动生成），否则资源 404。

yaml
- run: touch docs/.vitepress/dist/.nojekyll   # 或放进 docs/public/.nojekyll

六、Docker 基础与 K8s 概念 ​

6.1 镜像分层 ​

Dockerfile 每条指令生成一个只读层，层可被缓存复用。优化核心是把变化频率低的指令放前面：

dockerfile
# 多阶段构建：builder 编译，runner 只带产物
FROM node:20-alpine AS builder
WORKDIR /app
COPY package.json pnpm-lock.yaml ./
RUN corepack enable && pnpm install --frozen-lockfile   # 依赖层，package.json 变才重建
COPY . .
RUN pnpm build

FROM nginx:alpine AS runner
COPY --from=builder /app/dist /usr/share/nginx/html
EXPOSE 80
  • 多阶段构建：最终镜像不含 node_modules/源码/构建工具，体积从数百 MB 降到几十 MB。
  • .dockerignore 排除 node_modules、.git、dist，避免把宿主垃圾拷进去。
  • 前端静态站常用 nginx 作为 runner，注意 SPA 的 try_files $uri /index.html 回退。

6.2 K8s 三个最核心概念 ​

  • Pod：最小调度单元，一个或多个共享网络的容器；前端静态站通常一 Pod 一 nginx 容器。
  • Service：给一组 Pod 提供稳定的虚拟 IP 与 DNS 名，做负载均衡；前端的 ClusterIP/NodePort/LoadBalancer。
  • Ingress：七层入口，按 host/path 路由到 Service，负责 TLS 终止；前端域名 + 静态资源路径就挂在这里。
yaml
# 概念示意（Ingress 路由一个前端站点）
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata: { name: web }
spec:
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend: { service: { name: web-svc, port: { number: 80 } } }

前端面试对 K8s 的要求通常是「知道 Pod/Service/Ingress 各是什么、静态站怎么被暴露」，不必写 Operator。

七、多环境与灰度发布 ​

  • 多环境：dev / staging / prod 各自独立的配置、域名、密钥。用 Environment secrets（GitHub Environments）隔离，并加**人工审批（required reviewers）**保护 prod。
  • 灰度发布策略：
    1. 蓝绿（blue-green）：新旧两套环境，切流量即回滚，资源占用翻倍。
    2. 金丝雀（canary）：按 1% → 10% → 100% 逐步放量，观察错误率/性能指标再扩大。
    3. 功能开关（feature flag）：代码已上、功能按开关放量，粒度最细、回滚最快，是 Trunk Based 的标配（见 Git 工作流）。
  • 回滚：产物用不可变版本号（1.2.3）+ 保留最近 N 个版本，回滚=切回上一版本引用，而非重新构建。

八、常见坑与实战要点 ​

  1. pnpm install 在 CI 里用了非 frozen 模式：必须 --frozen-lockfile，否则 lockfile 与 package.json 不一致会被静默「修好」，掩盖问题。
  2. 缓存污染：手动 cache 的 key 没带 lockfile 哈希，旧依赖被复用导致装错版本。
  3. secrets 泄漏到日志：echo $SECRET、set -x、把 token 拼进 URL 都会打印。用 ::add-mask:: 或避免打印。
  4. 权限过宽：默认 GITHUB_TOKEN 权限很大，务必声明 permissions 收敛。
  5. 发布脚本无 fetch-depth: 0：Changesets 依赖完整 Git 历史，浅克隆会算错/失败。
  6. Pages 部署 404：八成是 base 前缀没注入，或缺 .nojekyll。
  7. npm 首次发布「搜不到」：作用域包索引有延迟，用 npm view @scope/pkg versions 确认已发布即可，别重复发。
  8. e2e 在 CI 上不稳定：等待改为断言可观测状态（元素可见/接口响应），而非固定 sleep；配置失败重试与 trace 上传。
  9. 发布与构建耦合：先 build 再 publish 的顺序要写死在同一 job，跨 job 需 actions/upload-artifact 传递产物。

面试要点 ​

  1. CI 与 CD 的区别？ CI 是持续集成（自动构建测试），CD 是持续交付/部署（自动上生产或一键上生产）。
  2. 流水线阶段为什么要按快慢排序？ 快速失败节省资源与反馈时间，lint/typecheck 秒级、e2e 分钟级放后面。
  3. GITHUB_TOKEN 权限如何收敛？ 在 workflow 顶层写 permissions 最小集合，敏感操作按 job 单独放开。
  4. npm 自动发布为什么推荐 OIDC？ Trusted Publishing 用短期凭据替代长期 token，无需存储密钥，安全性更高。
  5. 作用域包发布要注意什么？ 必须 publishConfig.access: public，否则被当作私有包拒推；首次发布后索引有延迟。
  6. GitHub Pages 部署 404 的两大原因？ base 前缀未按仓库名注入、缺 .nojekyll 导致下划线目录被 Jekyll 忽略。
  7. Docker 多阶段构建的好处？ 最终镜像只带产物，剥离源码与构建工具，体积大幅减小、攻击面更小。
  8. Pod / Service / Ingress 各是什么？ Pod 是最小调度单元，Service 提供稳定访问入口与负载均衡，Ingress 做七层路由与 TLS。
  9. 灰度发布的三种方式？ 蓝绿（环境切换）、金丝雀（按比例放量）、功能开关（代码已上按 flag 放量）。
  10. 为什么 CI 必须 --frozen-lockfile？ 保证依赖可复现、lockfile 与声明一致，避免静默漂移掩盖问题。
