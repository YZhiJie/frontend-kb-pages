Git 工作流 ​

Git 是工程化协作的底座。本文先讲清 Git 的数据模型（理解模型，命令才有意义），再落到分支模型、rebase/merge 选择、误操作恢复与提交规范。与 CI 的衔接见 CI/CD 与自动化发布，提交门禁见 代码规范与静态检查。

一、Git 内部模型：对象、引用、HEAD ​

理解这三样，大部分「为什么会这样」都能自解。

1.1 四类对象 ​

Git 是一个内容寻址的键值存储，key 是内容的 SHA-1/SHA-256 哈希：

对象作用
blob文件内容快照（不含文件名）
tree目录结构：路径名 → blob/tree 的映射
commit指向一棵 tree + 父 commit(s) + 作者/时间 + message
tag（annotated）指向某个对象的带签名/说明的引用对象
  • commit 里记录的是 tree 的哈希，而不是差异（diff 是计算出来的）。
  • 相同内容的文件在不同 commit 中共享同一个 blob，所以 Git 存储非常省。
  • 改一个文件会产生新 blob、新 tree 链、新 commit，旧对象不会消失（这正是 reflog 能救命的根本）。
bash
git cat-file -p HEAD        # 查看当前 commit 对象内容
git cat-file -t <hash>      # 查看对象类型
git rev-parse HEAD          # 把引用解析成哈希
git hash-object -w file.txt # 手动把文件写入对象库（少用）

1.2 引用与 HEAD ​

  • 分支就是一个指向 commit 的可变指针（存在 .git/refs/heads/）。
  • HEAD 是指向「当前分支（或某个 commit，即 detached HEAD）」的引用。
  • git switch/checkout 改变 HEAD 指向；提交会移动当前分支指针到新 commit。
git switch -c feature/x     # 新建并切换分支
git switch --detach v1.2.0  # 切到某 tag（进入 detached HEAD）

switch 是较新的、语义更清晰的命令（git restore 负责文件层面），建议新项目用 switch/restore 替代易混淆的 checkout。

二、分支模型 ​

2.1 Git Flow（重流程） ​

长期分支：main（生产）+ develop（集成），辅以 feature/*、release/*、hotfix/*。

  • 适合有明确发版周期、需要并行维护多个版本的产品。
  • 缺点：分支多、合并频繁、历史较乱，对持续交付不友好。

2.2 Trunk Based（主干开发 + 短分支） ​

  • 只有 main 一条主干，特性用存活数小时的短分支合入，靠功能开关（feature flag）控制灰度。
  • 是持续交付（CD）的主流选择，CI 反馈快、冲突少。
  • 前提：自动化测试与门禁足够强，团队规模适中。

2.3 GitHub Flow（折中） ​

  • main 常驻 + feature/* 短分支 + Pull Request 评审，合并即部署。
  • 中小团队最常见，本文默认按此模型展开。

三、rebase vs merge ​

维度mergerebase
历史保留分叉，产生 merge commit线性、整洁
真实性忠实反映分支时间线重写历史（新 commit 新哈希）
冲突处理一次性提交级，可能反复解
适用合入共享分支（保留 PR 上下文）本地整理、把特性分支对齐上游
bash
# 特性分支保持与主干同步（本地、未 push 时）
git fetch origin
git rebase origin/main

# 合并进主干（保留一条合并记录，PR 可追溯）
git switch main && git pull --ff-only
git merge --no-ff feature/login

# 更干净的三方合并（避免 merge 后还带回一堆上游提交）
git rebase origin/main feature/login
git switch main && git merge --ff-only feature/login

黄金法则：永远不要 rebase 已经推送到共享分支、且别人可能基于它工作的提交。会改写哈希，导致他人历史分叉。个人已合入的 PR 若必须变基，需 git push --force-with-lease（比 --force 安全，会在远端被别人改动时拒绝）。

四、常见操作与适用场景 ​

4.1 cherry-pick ​

把某个提交「复制」到当前分支（生成新哈希），用于：

  • 从主干挑选某个 bugfix 到 release 分支；
  • 不小心提交到了错误分支，想搬运。
bash
git cherry-pick <commit-hash>            # 单个
git cherry-pick <A>..<B>                 # 一段（不含 A）
git cherry-pick -x <hash>                # 记录来源 (cherry picked from ...)
git cherry-pick --continue / --abort     # 冲突后继续/放弃

坑：cherry-pick 会产生内容相同但哈希不同的提交，长期大量 use 会让历史难以追踪。能用 merge/rebase 就别 cherry-pick。

4.2 revert vs reset ​

命令语义历史适用
revert生成一个反向提交抵消某提交追加，不删已推送的共享分支
reset移动分支指针，丢弃后续提交变更/删除仅本地未推送
bash
git revert <hash>                        # 安全撤销已发布的提交
git revert -m 1 <merge-commit>           # 撤销一个 merge，保留第一父线
git reset --soft HEAD~1                  # 撤销 commit、保留改动在暂存区
git reset --mixed HEAD~1                 # 撤销 commit、改动回到工作区（默认）
git reset --hard HEAD~1                  # 丢弃 commit 与改动（危险）

准则：已推送 → 用 revert；未推送且只是「提交早了」→ 用 reset --soft。

4.3 stash ​

临时保存工作区以便切换分支：

bash
git stash push -m "wip: 表单校验"        # 带说明
git stash push -u                        # 连未跟踪文件一起存
git stash list
git stash apply stash@{1}                # 恢复但保留 stash
git stash pop                            # 恢复并删除该 stash
git stash drop stash@{0}

坑：stash 冲突可能丢失（pop 冲突失败后 stash 不自动删，注意别 drop）。长期未清理的 stash 容易遗忘，应尽量及时 pop。

4.4 交互式 rebase 与 squash ​

bash
git rebase -i HEAD~4
# 编辑器里对每个 commit 选择：
#   pick   保留
#   reword 改 message
#   squash 合并进上一个 commit（保留 message 供合并编辑）
#   fixup  合并进上一个 commit（丢弃本条 message）
#   drop   删除
  • 合并 PR 时常用 squash merge：把一堆「fix typo」压成一个有意义的提交。
  • 编辑器（VS Code）保存关闭即生效；中途出错用 git rebase --abort 全撤，或 --continue/--skip 续跑。

4.5 冲突解决策略 ​

  1. 先 git status 看清冲突文件，理解双方意图再动手，不要机械取一边。
  2. 冲突标记 <<<<<<< / ======= / >>>>>>> 三部分分别是 current（ours/HEAD）与 incoming（theirs）。
  3. 冲突多时优先减小变更面：git rebase 逐提交解（定位更准），或 git merge --no-commit 一次看全。
  4. git checkout --ours <file> / --theirs <file> 可整文件取一边（rebase 中 ours/theirs 语义与 merge 相反，注意）。
  5. 解完 git add <file> 标记已解决，再 --continue。

五、提交规范与版本 ​

5.1 Conventional Commits ​

格式：<type>(<scope>): <subject>，正文与 footer 空行分隔。

type含义
feat新功能（对应 minor）
fix修 bug（对应 patch）
docs / style / refactor / perf / test / build / ci / chore其他类别
feat! / fix! 或 footer BREAKING CHANGE:破坏性变更（对应 major）
feat(ui): 支持 DatePicker 受控 value/onValueChange 双模式

BREAKING CHANGE: 移除已废弃的 onChange 回调
Closes #123

语义化版本（SemVer）：MAJOR.MINOR.PATCH，由 commit type 推导（feat→MINOR，fix→PATCH，BREAKING→MAJOR）。这正是 Changesets / semantic-release 自动发版的依据。

5.2 tag ​

bash
git tag -a v1.3.0 -m "release 1.3.0"    # 附注 tag（推荐，可签名）
git push origin v1.3.0                  # 推送单个 tag
git push origin --tags                  # 推送所有 tag
git tag -d v1.3.0                       # 删本地 tag
git push origin :refs/tags/v1.3.0       # 删远端 tag

坑：轻量 tag（git tag v1.0）就是没有说明的指针，发布请用 -a。删远端 tag 要用 :refs/tags/... 语法。

六、reflog：误操作的后悔药 ​

reflog 记录 HEAD 与分支指针的每次移动，是找回「reset --hard 后丢失的提交」「误删分支」的关键：

bash
git reflog                                # 查看最近 HEAD 移动历史
git reset --hard HEAD@{3}                 # 回到 3 步之前
git branch recovered HEAD@{5}             # 从某个旧位置救回分支
git checkout -b hotfix-lost <orphan-hash> # 救回悬空提交

要点：未推送的提交被 reset --hard 丢弃后，对象仍在对象库里，reflog 能定位；但 reflog 会过期（默认 90 天），且 git gc 可能回收。救回要及时。

七、子模块与 subtree ​

  • submodule：在父仓记录子仓的一个具体 commit，需显式 git submodule update --init --recursive。缺点是易踩「忘记 init」「detached HEAD」坑。
  • subtree：把子仓内容合并进父仓（真实文件），对使用者透明，无需额外初始化，但同步需 git subtree pull/push。
bash
git submodule add <url> libs/foo
git submodule update --init --recursive
git submodule foreach 'git pull origin main'

git subtree add --prefix=libs/bar <url> main --squash
git subtree pull --prefix=libs/bar <url> main --squash

选型：需要独立发布/权限隔离 → submodule；想让使用者无感、单仓构建 → subtree（或干脆 monorepo，见 pnpm workspace 与 Monorepo）。

八、常见踩坑与安全操作准则 ​

  1. git push --force 覆盖同事工作：默认用 --force-with-lease，它会在远端被他人更新时拒绝，避免误覆盖。
  2. 在共享分支 rebase/reset：改写公共历史会伤害所有人，改推个人分支或走 PR。
  3. 误提交敏感信息：一旦推送就很难彻底清除（要 filter-repo 重写全历史 + 强制推送 + 轮换密钥）。预防优于补救：.gitignore + pre-commit 密钥扫描（见 CI/CD 与自动化发布）。
  4. 大文件入库：二进制/大文件应走 Git LFS，否则仓库体积不可逆膨胀。
  5. detached HEAD 下提交：提交后不挂分支，切走就成悬空提交，记得 git switch -c 建分支。
  6. 合并冲突后提交混乱：merge --abort / rebase --abort 能回到干净状态，别硬提交半成品。
  7. CRLF/LF 跨平台：统一 .gitattributes 的 * text=auto eol=lf，避免整文件「看起来全改了」。
  8. 安全准则总结：共享分支只增不改（revert 而非 reset）；个人分支可自由变基；写操作前先 git status + git fetch。

面试要点 ​

  1. Git 的四种对象是什么？ blob（内容）、tree（目录）、commit（快照+父指针）、tag；均为内容寻址。
  2. commit 存的是 diff 还是快照？ 快照（tree 哈希），diff 是实时计算的。
  3. rebase 与 merge 的本质区别？ rebase 重写历史得到线性结构，merge 保留分叉；共享分支不要 rebase。
  4. 已推送的提交要撤销怎么办？ 用 git revert 生成反向提交，绝不 reset 已共享的历史。
  5. reflog 能解决什么？ 找回被 reset/误删分支丢弃的提交，前提是对象未被 gc 回收。
  6. --force 与 --force-with-lease 的区别？ 后者在远端被别人更新时会拒绝推送，避免覆盖他人提交。
  7. cherry-pick 的代价？ 生成内容相同但哈希不同的重复提交，滥用会让历史难以追踪。
  8. Conventional Commits 有什么用？ 结构化提交类型可自动推导 SemVer 与生成 CHANGELOG，驱动自动发版。
  9. git submodule 与 subtree 怎么选？ 需独立发布/隔离用 submodule，想让使用者无感用 subtree。
