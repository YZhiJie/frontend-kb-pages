构建工具：Vite / Webpack ​

构建工具是工程化的地基。本文按「Vite 原理 → Vite 实战 → Webpack5 核心 → 选型对比 → 常见坑」组织，重点讲清两者的运行机制差异，而不是罗列配置项。工程化模块的其他页面见 pnpm workspace 与 Monorepo 与 组件库建设与发布。

一、构建工具解决什么问题 ​

现代前端构建本质是三件事：

  1. 模块解析与打包：把 import/require 的依赖图（dependency graph）展开，合并成浏览器可执行的产物。
  2. 语法与资源转换：TS → JS、JSX → JS、SCSS → CSS、图片/字体处理、CSS 后处理（PostCSS）。
  3. 产物优化：tree shaking、code splitting、压缩、hash 命名、兼容性降级（target/browserslist）。

差异在于「什么时候做」：Webpack 是先打包再交给浏览器（bundle-based），Vite 开发期是浏览器直接执行原生 ESM、按需编译（bundleless dev），生产期仍走 Rollup 打包。

二、Vite 原理与机制 ​

2.1 开发期：ESM + esbuild 预构建 ​

  • 启动 dev server 时，Vite 不打包源码，只启动一个静态服务器。浏览器请求 /src/main.ts 时，Vite 拦截该请求做按需编译，把 TS/JSX/Vue SFC 即时转成 ESM 返回。
  • 第三方依赖（node_modules）走依赖预构建（pre-bundling）：用 esbuild 把 CJS/UMD 依赖转成 ESM，并把大量内部模块（如 lodash 的数百个文件）合并成单个文件，缓存到 node_modules/.vite/deps。
  • 为什么需要预构建：
    1. CJS/UMD 依赖不能直接在浏览器跑 ESM；
    2. 一个 import { debounce } from 'lodash-es' 会触发几十上百个 HTTP 请求，预构建后只剩 1 个；
    3. 请求数决定 dev server 冷启动表现。
# 依赖预构建缓存目录
node_modules/.vite/deps/lodash-es.js
node_modules/.vite/deps/_metadata.json

2.2 HMR 机制 ​

Vite 的 HMR 建立在 原生 ESM + WebSocket 上，而不是 Webpack 的「重新打包后推送整个 chunk」：

  1. server 用 chokidar 监听文件变化，构建模块图（ModuleGraph）。
  2. 变化后沿 import 链向上查找「接受该模块更新的边界（HMR boundary）」，即声明了 import.meta.hot.accept 的模块。
  3. 通过 WebSocket 只推送该模块的更新，浏览器用动态 import() 拉取新模块并替换。
ts
// 手写一个 HMR 边界：接受自身更新，保留状态
if (import.meta.hot) {
  import.meta.hot.accept((newModule) => {
    // newModule 是更新后的模块，可做局部替换而不是整页刷新
    render(newModule.default);
  });
  import.meta.hot.dispose(() => {
    // 清理旧模块的副作用：定时器、事件监听、WebSocket
    clearInterval(timer);
  });
}

框架层（@vitejs/plugin-vue、@vitejs/plugin-react）已内置 HMR 边界，业务代码通常不用手写；但自研插件或全局副作用模块必须实现 dispose，否则会出现内存泄漏与「刷新无效」。

2.3 生产构建：Rollup ​

vite build 使用 Rollup（Rollup 4 起用 Rust 写的解析器，配合 esbuild 做 minify）产出可部署产物。Vite 在 Rollup 之上做了一层「默认配置包装」：

  • 默认 target: 'modules'（支持原生 ESM 的浏览器），可用 build.target 覆盖。
  • 默认按动态 import() 做 code splitting，并做 CSS 与资源的 hash 命名。
  • build.rollupOptions 可直接透传原生 Rollup 配置（external、output.manualChunks、多入口等）。

三、Vite 实战配置 ​

3.1 一份典型配置 ​

ts
// vite.config.ts
import { defineConfig, loadEnv } from 'vite';
import react from '@vitejs/plugin-react';
import path from 'node:path';

export default defineConfig(({ mode, command }) => {
  const env = loadEnv(mode, process.cwd(), ''); // 第三个参数 '' 表示不过滤 VITE_ 前缀
  const isBuild = command === 'build';

  return {
    base: env.DOCS_BASE || '/', // 子路径部署时必须显式设置
    resolve: {
      alias: { '@': path.resolve(__dirname, 'src'), '~': path.resolve(__dirname, 'src/styles') },
      // 强制所有包共用同一份 react，避免 hooks 报 Invalid hook call
      dedupe: ['react', 'react-dom'],
    },
    server: {
      port: 5173,
      proxy: {
        '/api': { target: env.API_TARGET || 'http://localhost:3000', changeOrigin: true, rewrite: (p) => p.replace(/^\/api/, '') },
      },
    },
    optimizeDeps: {
      include: ['echarts', 'lodash-es'], // 预构建白名单，避免运行时才发现
      exclude: ['@your-org/internal-cjs-pkg'], // 已知不兼容预构建的包
    },
    build: {
      target: 'es2020', sourcemap: !isBuild ? true : 'hidden', cssCodeSplit: true, chunkSizeWarningLimit: 800,
      rollupOptions: {
        output: {
          manualChunks(id) { // 按依赖来源手动分包，避免单个 vendor.js 过大
            if (id.includes('node_modules')) {
              if (id.includes('echarts')) return 'vendor-echarts';
              if (id.includes('@antv')) return 'vendor-antv';
              return 'vendor';
            }
          },
        },
      },
    },
  };
});

3.2 环境变量与多环境 ​

  • 只有以 VITE_ 开头的变量才会被注入客户端（import.meta.env.VITE_API_BASE），这是防止密钥泄漏的硬性约定。
  • 通过 .env、.env.development、.env.production、.env.local（.local 应加入 .gitignore）分层。
  • import.meta.env.MODE / DEV / PROD / SSR 是内建变量。
  • 坑：.env 在构建时被静态替换，不是运行时读取；构建产物换环境必须重新构建。
# .env.production
VITE_API_BASE=https://api.example.com
DOCS_BASE=/frontend-kb-pages/   # 非 VITE_ 前缀不会注入客户端，仅构建脚本可用

3.3 库模式构建（library mode） ​

组件库产物用 build.lib，关键是把外部依赖 external 出去，否则会把 react/vue 打进产物，导致宿主应用出现两份运行时。

ts
// packages/ui/vite.config.ts
import { defineConfig } from 'vite';
import { resolve } from 'node:path';
import dts from 'vite-plugin-dts';

export default defineConfig({
  build: {
    lib: {
      entry: resolve(__dirname, 'src/index.ts'),
      formats: ['es', 'cjs'],
      fileName: (format) => `index.${format === 'es' ? 'mjs' : 'cjs'}`,
    },
    rollupOptions: {
      // 只把 peer 依赖与宿主框架排除，其余不 external
      external: ['react', 'react-dom', 'react/jsx-runtime', 'vue'],
      output: { globals: { react: 'React', vue: 'Vue' } },
    },
  },
  plugins: [dts({ rollupTypes: true })], // 生成 .d.ts，类型入口要写进 package.json exports
});

3.4 SSR 构建 ​

vite build --ssr 产出 Node 侧 bundle，默认 external 掉所有依赖（依赖宿主 node_modules），入口通过 ssr 字段或 CLI 指定。SSR 场景注意：import.meta.env.SSR 分支、CSS 只提取不注入、水合（hydration）一致性（详见 React 18/19 深入）。

四、Webpack5 核心 ​

4.1 四大概念与配置骨架 ​

Webpack 的一切围绕 entry / output / loader / plugin 展开：loader 处理「单个文件级别的转换」，plugin 处理「编译生命周期级别的扩展」。

js
// webpack.config.js
const path = require('node:path');
const HtmlWebpackPlugin = require('html-webpack-plugin');
const { BundleAnalyzerPlugin } = require('webpack-bundle-analyzer');

module.exports = (env, argv) => {
  const isProd = argv.mode === 'production';
  return {
    entry: { app: './src/main.ts' },
    output: {
      path: path.resolve(__dirname, 'dist'),
      filename: isProd ? 'js/[name].[contenthash:8].js' : 'js/[name].js',
      chunkFilename: isProd ? 'js/[name].[contenthash:8].chunk.js' : 'js/[name].chunk.js',
      publicPath: '/', clean: true,
    },
    resolve: { extensions: ['.tsx', '.ts', '.jsx', '.js'], alias: { '@': path.resolve(__dirname, 'src') } },
    module: {
      rules: [
        {
          test: /\.tsx?$/,
          include: path.resolve(__dirname, 'src'), // 只 loader 源码，node_modules 跳过 babel，显著提速
          use: [{
            loader: 'babel-loader',
            options: { cacheDirectory: true, presets: [['@babel/preset-env', { targets: 'defaults' }], '@babel/preset-react', '@babel/preset-typescript'] },
          }],
        },
        { test: /\.css$/, use: ['style-loader', 'css-loader', 'postcss-loader'] },
        { test: /\.(png|svg|woff2?)$/, type: 'asset', parser: { dataUrlCondition: { maxSize: 8 * 1024 } } },
      ],
    },
    plugins: [new HtmlWebpackPlugin({ template: './public/index.html' })].concat(
      isProd ? [new BundleAnalyzerPlugin({ analyzerMode: 'static', openAnalyzer: false })] : []
    ),
    optimization: {
      splitChunks: { chunks: 'all' },
      runtimeChunk: 'single',
    },
    cache: { type: 'filesystem' }, // Webpack5 持久化缓存
    devtool: isProd ? 'source-map' : 'eval-cheap-module-source-map',
  };
};

4.2 Tree shaking ​

生效条件（三者缺一不可）：

  1. 使用 ESM（import/export），CJS 的 module.exports 无法静态分析；
  2. mode: 'production'（开启 usedExports + sideEffects 优化）；
  3. package.json 里正确声明 "sideEffects": false 或列出有副作用的文件（如 "sideEffects": ["*.css"]）。
json
// 包的 package.json：声明无副作用才能被安全摇树
{
  "name": "@your-org/ui",
  "sideEffects": ["**/*.css", "./src/polyfill.ts"]
}

4.3 Code splitting 三种手段 ​

  • 动态 import：import('./Chart') 生成独立 chunk，是最主要的手段。
  • splitChunks：抽取公共依赖，chunks: 'all' 可覆盖同步/异步 chunk。
  • entry 多入口：多页应用场景。

配合 runtimeChunk: 'single' 把 webpack runtime 单独抽出，避免业务 chunk 变化导致 runtime hash 变化，从而让长期缓存命中率更高。

4.4 Module Federation（微前端） ​

Webpack5 内建的运行时模块共享机制：容器（container）暴露 remote，宿主用 remotes 消费，运行时通过 share 声明共享依赖版本。

js
// 远端 A：暴露一个微应用
new ModuleFederationPlugin({
  name: 'remoteA', filename: 'remoteEntry.js',
  exposes: { './Widget': './src/Widget.tsx' },
  shared: { react: { singleton: true, requiredVersion: '^18.0.0' }, 'react-dom': { singleton: true } },
});
// 宿主 B：消费
new ModuleFederationPlugin({
  name: 'host',
  remotes: { remoteA: 'remoteA@https://a.com/remoteEntry.js' },
  shared: { react: { singleton: true }, 'react-dom': { singleton: true } },
});

要点：shared.singleton: true 是正确性要求（React 单实例），不是优化项；版本不一致时会产生 Unsatisfied version 告警并可能加载重复 React。

4.5 持久化缓存与构建性能 ​

js
cache: {
  type: 'filesystem',
  buildDependencies: { config: [__filename] }, // 配置文件变化使缓存失效
}

常见提速手段与量级参考：

手段说明收益
cache: { type: 'filesystem' }增量编译缓存二次构建常降 50%-80%

五、bundle 分析 ​

  • Vite：rollup-plugin-visualizer 生成 stats.html 体积报告；Webpack：webpack-bundle-analyzer 分析 chunk 组成。
  • 关注点：入口 JS 体积、重复依赖（同一库多版本）、未摇掉的死代码、过大的单 chunk（> 200KB gzip 需警惕）。
ts
import { visualizer } from 'rollup-plugin-visualizer';
plugins: [visualizer({ filename: 'stats.html', gzipSize: true, brotliSize: true })];

六、Vite 与 Webpack 选型对比 ​

维度ViteWebpack5
开发启动按需编译 + esbuild 预构建，秒级全量打包，随项目线性变慢
HMR原生 ESM 精准更新，通常 < 50mschunk 级更新，大项目常数百 ms 至数秒
生产打包Rollup自研（含 MF）
生态/插件与 Rollup 生态共享，兼容性已基本齐平最成熟，历史插件最多
微前端需借助模块联邦变体或 wujie/qiankun内建 Module Federation
老项目/Less 深度定制部分 loader 需适配兼容性最强
适用新项目、组件库、VitePress 文档站存量大项目、需要 MF、深度定制构建

一句话结论：新项目默认 Vite；维护老项目、需要 Module Federation 或历史 loader 定制时用 Webpack5。

七、实战要点与常见坑 ​

  1. 依赖预构建失败：报 Failed to resolve dependency 或改依赖后 dev 未更新。解决：删除 node_modules/.vite 重启，或在 optimizeDeps.include 中显式声明。
  2. 路径别名：TS 里配了 paths 但构建报找不到，需同时在 vite.config/webpack.resolve.alias 与 tsconfig.json 的 compilerOptions.paths 配置，两套系统互不感知。
  3. external 用法：组件库必须 external react/vue；但 react/jsx-runtime（自动 JSX runtime）也常被漏掉，导致宿主多一份 runtime。
  4. CSS 处理：Vite 默认用 PostCSS，Sass 需装 sass（不是 node-sass）；@import 深度嵌套会重复输出，建议 @use。Webpack 侧注意 css-loader 的 modules 与 style-loader 的注入顺序。
  5. 子路径部署：base 只影响产物引用路径；路由（router basename）与 VitePress 的 base 是两回事，需分别设置。
  6. hash 与长期缓存：contenthash 才是内容哈希（hash 是编译级，全项目共享），Webpack 里用错会导致缓存全失效。
  7. monorepo 下源码引用：alias 指向别的包的 src 会让 Vite 把它当源码处理，需在 optimizeDeps.include 里登记，否则出现「开发正常、构建后重复实例」。

面试要点 ​

  1. Vite 为什么开发快？ 开发期用原生 ESM 按需编译 + esbuild 预构建依赖，省去了全量打包；生产期才用 Rollup。
  2. 依赖预构建的目的是什么？ 把 CJS/UMD 转 ESM 并合并零散模块，把上百个请求降为 1 个，同时对 ESM 依赖做缓存与优化。
  3. Vite 的 HMR 和 Webpack 的 HMR 有何不同？ Vite 基于原生 ESM 精准定位 HMR 边界、只更新单模块；Webpack 是打包体系内、以 chunk 为单位推送更新。
  4. tree shaking 生效的三个前提？ ESM 语法、生产模式、sideEffects 正确声明。
  5. webpack 的 hash/contenthash/chunkhash 区别？ hash 为编译级、chunkhash 为 chunk 级、contenthash 为内容级（长期缓存应优先 contenthash）。
  6. Module Federation 的 shared.singleton 为什么重要？ React 等必须单实例，否则 hooks/上下文会错乱，singleton 保证运行时共用同一份。
  7. import.meta.env.VITE_ 前缀的意义？ 只有带前缀变量注入客户端，避免把密钥等敏感配置打进前端产物。
  8. library mode 为什么必须 external 掉框架？ 否则产物自带一份 react/vue，宿主加载两份运行时会导致 hooks 报错与体积翻倍。
