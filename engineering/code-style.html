代码规范与静态检查 ​

静态检查是「把编码约定固化成工具」，让风格问题在提交前就被机器拦掉，人只专注逻辑与设计。本文覆盖 ESLint 9 flat config、Prettier、Stylelint、Husky/lint-staged、commitlint 与评审清单。与 CI 的接线见 CI/CD 与自动化发布。

一、分层：谁负责什么 ​

工具职责不做
ESLint逻辑/潜在 bug/规范（可自动修复）格式化（交给 Prettier）
Prettier纯格式化（缩进、引号、换行）语义分析
StylelintCSS/Less/SCSS 规范与可维护性逻辑
TypeScript类型正确性（tsc --noEmit）格式
Husky + lint-staged提交前只检查改动文件全量检查（交给 CI）

核心原则：格式交给 Prettier（不与其冲突），语义与规范交给 ESLint，类型交给 tsc，提交前只查增量、CI 查全量。

二、ESLint 9 flat config 与迁移 ​

2.1 为什么是 flat config ​

ESLint 9 默认使用 eslint.config.js（flat config），取代 .eslintrc.* + extends 的层叠机制：

  • 配置是普通 JS 数组，可自由编程组合，不再有隐式层叠规则。
  • 插件从「字符串名 + plugins 数组」改为直接导入对象，依赖显式、无魔法解析。
  • 匹配用 files glob（不再需要 overrides）。
js
// eslint.config.js（ESM）
import js from '@eslint/js';
import tseslint from 'typescript-eslint';
import react from 'eslint-plugin-react';
import reactHooks from 'eslint-plugin-react-hooks';
import prettier from 'eslint-config-prettier';

export default tseslint.config(
  { ignores: ['dist/**', 'coverage/**', '**/*.d.ts'] },
  js.configs.recommended,
  ...tseslint.configs.recommendedTypeChecked,
  {
    files: ['**/*.{ts,tsx}'],
    languageOptions: {
      parserOptions: {
        project: ['./tsconfig.json'],      // 类型感知规则必须配 project
        tsconfigRootDir: import.meta.dirname,
      },
    },
    plugins: { react, 'react-hooks': reactHooks },
    rules: {
      'react-hooks/rules-of-hooks': 'error',
      'react-hooks/exhaustive-deps': 'warn',
      '@typescript-eslint/no-unused-vars': ['error', { argsIgnorePattern: '^_' }],
      '@typescript-eslint/consistent-type-imports': ['error', { prefer: 'type-imports' }],
      'no-console': ['warn', { allow: ['warn', 'error'] }],
    },
  },
  prettier, // 必须放最后，关闭与 Prettier 冲突的格式规则
);

2.2 迁移要点（.eslintrc → flat） ​

  1. extends: ['plugin:react/recommended'] → 导入插件对象并展开其 configs.recommended。
  2. env: { browser: true } → languageOptions.globals（如 globals.browser）与 languageOptions.ecmaVersion/sourceType。
  3. overrides → 拆成多个带 files 的配置对象。
  4. .eslintignore → 顶层配置的 ignores。
  5. --ext 不再需要；直接用 glob（ESLint 9 默认匹配 **/*.js，需显式声明 ts/tsx）。
  6. 用官方迁移工具：npx @eslint/migrate-config .eslintrc.json。

2.3 自定义规则 ​

团队特化需求（如「禁止直接 import lodash，必须走 utils」）用 no-restricted-imports 或自研规则：

js
rules: {
  'no-restricted-imports': ['error', {
    paths: [
      { name: 'lodash', message: '请使用 @your-org/utils 的封装，避免全量引入。' },
      { name: 'moment', message: '请改用 dayjs。' },
    ],
    patterns: [{ group: ['@your-org/ui/dist/*'], message: '请从包入口导入，勿深链 dist。' }],
  }],
  'no-restricted-syntax': [
    'error',
    { selector: 'ExportDefaultDeclaration', message: '库内统一用命名导出，避免默认导出影响 tree shaking。' },
  ],
}

no-restricted-syntax 用 AST selector，是不写插件也能做架构约束的利器（配合 架构约束与依赖治理）。

三、eslint-plugin-react-hooks 与 ESLint 9 的兼容坑 ​

这块是近年最常见的踩坑点：

  1. peer 依赖冲突：早期 eslint-plugin-react-hooks@4.x 的 peer 只声明到 ESLint 8，装 ESLint 9 会报 peer eslint@^8 冲突。解决：升级到支持 ESLint 9 的版本，或用 pnpm overrides 放宽；不要 --force 硬装。
  2. flat config 接入方式不同：旧写法的 extends: ['plugin:react-hooks/recommended'] 在 flat 里要改成导入 reactHooks.configs['recommended-latest'] 或手动注册插件对象。
  3. react-hooks/exhaustive-deps 误报：把「稳定的 ref/dispatch」判为缺失依赖。可在具体行用 // eslint-disable-next-line react-hooks/exhaustive-deps 加说明注释，或抽出稳定引用。不要整文件全局关规则。
  4. React Compiler 时代：新版 react-hooks 插件加入编译器相关规则，若暂时不启用 React Compiler，需确认规则不会误伤（可在配置里选择性关闭）。
  5. Vue 侧对应物：eslint-plugin-vue 的 vue/no-mutating-props、vue/require-explicit-emits 是必开项，flat 下用 pluginVue.configs['flat/recommended']。
js
// 适配 React 的完整片段（ESLint 9 + flat）
import reactHooks from 'eslint-plugin-react-hooks';
export default [
  {
    files: ['**/*.{ts,tsx}'],
    plugins: { 'react-hooks': reactHooks },
    rules: {
      ...reactHooks.configs.recommended.rules,
      'react-hooks/exhaustive-deps': 'warn',
    },
  },
];

四、Prettier 与 ESLint 协作 ​

  • 别让两者管同一件事：格式归 Prettier，ESLint 关掉所有格式类规则（用 eslint-config-prettier 兜底）。
  • 不要用 eslint-plugin-prettier 把 Prettier 变成 ESLint 规则（旧做法）：它会让格式化差异变成 error、拖慢 lint、且与编辑器实时格式化互相打架。新趋势是让两者独立、各跑各的。
  • prettier --check 进 CI，prettier --write 在编辑器保存时触发（配合 lint-staged）。
json
// .prettierrc.json
{
  "semi": true,
  "singleQuote": true,
  "trailingComma": "all",
  "printWidth": 100,
  "arrowParens": "always",
  "endOfLine": "lf"
}
# .prettierignore
dist
coverage
pnpm-lock.yaml
CHANGELOG.md

五、Stylelint 实战规则与踩坑 ​

5.1 配置 ​

js
// stylelint.config.js
export default {
  extends: ['stylelint-config-standard', 'stylelint-config-recommended-vue'],
  rules: {
    'no-descending-specificity': null,          // 见下方踩坑说明，常需关闭
    'selector-not-notation': 'complex',          // 要求 :not(a):not(b) 而非 :not(a, b)
    'media-feature-range-notation': 'context',   // 要求 (width < 600px) 而非 (max-width: 600px)
    'color-function-notation': 'modern',
    'selector-class-pattern': '^[a-z][a-z0-9]*(?:-[a-z0-9]+)*(?:__[a-z0-9-]+)?(?:--[a-z0-9-]+)?$', // BEM
    'custom-property-pattern': '^[a-z][a-z0-9-]*$',
    'declaration-block-no-redundant-longhand-properties': true,
  },
};

5.2 高频规则与坑 ​

  • no-descending-specificity：要求「低优先级选择器不得出现在高优先级之后」。与 BEM/CSS 变量主题、第三方样式覆盖天然冲突，误报极多。要么重构选择器顺序，要么（常见做法）关掉它。
  • selector-not-notation：complex 要求 :not(a):not(b)，simple 允许 :not(a, b)。老浏览器兼容需注意 :not(a, b) 的支持度（现代浏览器 OK）。
  • media-feature-range-notation：context 要求 (width >= 768px)，prefix 允许 (min-width: 768px)。团队历史 CSS 多是 min-width，迁移时要么切换 notation 自动修复（--fix），要么设 prefix 兼容。
  • selector-class-pattern：用来强制 BEM 命名，但要允许 __element、--modifier 与状态类（is-*、has-*），否则全局状态类会报错。
  • stylelint 与 <style> in SFC：装 stylelint-config-recommended-vue（或 postcss-html customSyntax）才能检查 .vue/.html 内嵌样式。
bash
npx stylelint "**/*.{css,scss,vue}" --fix

六、Husky + lint-staged 预提交 ​

目的：只检查本次改动文件，让提交秒级完成，全量留给 CI。

bash
pnpm add -D husky lint-staged
pnpm husky init            # 创建 .husky/ 并写 pre-commit
json
// package.json
{
  "scripts": { "prepare": "husky" },
  "lint-staged": {
    "*.{ts,tsx,js,jsx}": ["eslint --fix --max-warnings=0", "prettier --write"],
    "*.{css,scss,vue}": ["stylelint --fix", "prettier --write"],
    "*.{json,md,yml,yaml}": ["prettier --write"]
  }
}
sh
# .husky/pre-commit
pnpm lint-staged
# .husky/commit-msg
pnpm commitlint --edit "$1"

坑：

  • prepare 脚本在 CI 里 pnpm install --frozen-lockfile 时也会跑 husky，若 .git 不存在会报错；可用 husky || true 或在 CI 设 HUSKY=0。
  • lint-staged 会把文件先加到暂存区再传参，若规则会改写文件，需要它自动 git add 回暂存区（默认行为）；配置 --fix 后注意不要漏加。
  • 别在 pre-commit 里跑 tsc/全量测试——太慢会让开发者用 --no-verify 绕过。类型检查放 CI（或 pre-push）。

七、commitlint ​

js
// commitlint.config.js
export default {
  extends: ['@commitlint/config-conventional'],
  rules: {
    'scope-enum': [2, 'always', ['ui', 'utils', 'docs', 'ci', 'deps', 'release']],
    'subject-case': [0],       // 中文 subject 常需关闭大小写校验
    'header-max-length': [2, 'always', 100],
  },
};

配合 commit-msg 钩子，提交信息不合规直接拒绝。好处：CHANGELOG 自动生成、语义化版本推导（见 Git 工作流 的 Conventional Commits）。

八、编辑器集成 ​

  • .vscode/settings.json：editor.formatOnSave: true + editor.codeActionsOnSave: { "source.fixAll.eslint": "explicit" }。
  • .vscode/extensions.json 推荐 ESLint / Prettier / Stylelint 插件，新人克隆即得一致体验。
  • 用 eslint.useFlatConfig（新版本默认）确认编辑器走 flat config。
  • 设置 prettier.requireConfig: true，避免没有配置文件的目录被误格式化。
json
{
  "editor.formatOnSave": true,
  "editor.defaultFormatter": "esbenp.prettier-vscode",
  "editor.codeActionsOnSave": { "source.fixAll.eslint": "explicit" },
  "eslint.useFlatConfig": true
}

九、代码评审清单与「编码品味」 ​

评审时按下面清单快速过一遍，覆盖 80% 的常见问题：

正确性：边界（空数组/0/负数/超长字符串）、错误处理是否遗漏、异步是否 await、useEffect 依赖是否完整。 可读性：命名是否表意、函数是否过长（> 50 行拆分）、嵌套是否过深（> 3 层早返回）。 一致性：是否沿用既有模式与目录约定、命名风格（BEM/组件 PascalCase）是否统一。 可维护性：魔法数字是否提为常量、重复逻辑是否抽函数、TS 是否用 unknown 而非 any。 性能与安全：无用重渲染、大列表是否虚拟化、是否有 XSS 风险（dangerouslySetInnerHTML）、密钥是否误入库。

编码品味（面试常被追问的软实力）：

  • 早返回优于深嵌套，让主流程在左侧竖直对齐。
  • 避免 any 与 as 强转，用类型守卫（type guard）与泛型收敛不可信输入。
  • 组件只做一件事，受控/非受控逻辑抽 hook，而不是在组件里堆 if。
  • 命名即文档：handleSubmit、isLoading、hasError 比 flag、data2 有信息量。
  • 删除优于注释：死代码直接删（有 Git 兜底），注释只解释「为什么」而非「是什么」。

面试要点 ​

  1. ESLint 9 flat config 和旧 .eslintrc 的核心区别？ 配置是普通 JS 数组、插件显式导入、用 files glob 取代 extends/overrides 层叠。
  2. ESLint 与 Prettier 如何分工？ Prettier 管格式、ESLint 关掉格式规则只管语义；不要让二者重复管同一件事。
  3. 为什么不再推荐 eslint-plugin-prettier？ 会把格式差异变成 ESLint 错误、拖慢、与编辑器格式化冲突。
  4. react-hooks 插件在 ESLint 9 下有哪些坑？ peer 依赖冲突、flat 接入方式变化、exhaustive-deps 误报需按行豁免。
  5. no-descending-specificity 为什么常被关闭？ 与 BEM/主题覆盖冲突、误报多，重构成本高于收益。
  6. lint-staged 的工作原理？ 只把本次暂存文件传给对应命令，--fix 后自动重新 git add，实现增量检查。
  7. pre-commit 该不该跑 tsc 和全量测试？ 不该，太慢会诱发 --no-verify 绕过；类型检查与全量测试放 CI。
  8. 如何用 ESLint 做架构约束？ 用 no-restricted-imports 禁依赖、no-restricted-syntax 按 AST selector 禁模式。
  9. 什么是「编码品味」？ 早返回、少嵌套、拒绝 any、命名表意、删除死代码、注释只讲为什么。
