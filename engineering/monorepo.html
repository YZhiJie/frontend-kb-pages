pnpm workspace 与 Monorepo ​

Monorepo 是「多包同仓」的工程组织方式。本文以 pnpm workspace + Turbo + Changesets 为主线，讲清 pnpm 的存储与链接机制、任务编排、版本发布，以及跨包开发最常见的几个坑。构建配置细节见 构建工具：Vite / Webpack，对外发布流程见 组件库建设与发布。

一、Monorepo 的价值与代价 ​

价值：

  • 依赖与版本统一：一份 lockfile、一套工具链，避免多仓各自升级导致的「依赖漂移」。
  • 原子提交（atomic commit）：改了组件库 API，可以同一个 commit 里改完所有使用方，CI 一次跑完，不会出现「A 仓发了新版、B 仓还没升」的中间态。
  • 代码复用成本低：ui、utils、types 直接引用源码，省去「本地 link 调试」。
  • 统一规范与 CI：一套 ESLint/Prettier/TS 配置，一次门禁覆盖所有包。

代价：

  • 仓库体积与克隆耗时增长，CI 需要做增量（否则每次全量跑所有包）。
  • 构建顺序与依赖耦合：包之间有拓扑依赖，乱序构建会失败。
  • 工具链复杂度：包管理器链接机制、TS 路径、缓存失效策略都要理解。
  • 不适合「完全独立团队 + 独立发布节奏」的强隔离场景。

二、pnpm 的核心机制 ​

2.1 内容寻址存储（content-addressable store） ​

pnpm 把每个文件按内容哈希存进全局 store（默认 ~/.pnpm-store 或 pnpm store path 给出的路径），node_modules 里存的是指向 store 的硬链接（hard link），而不是复制。

  • 同一版本被 N 个项目使用，磁盘只存一份。
  • 硬链接指向同一 inode，修改包内容不会「污染」其他项目（除非原地改，那会同时改，实际应避免）。
# 查看 store 位置
pnpm store path
# 清理未引用的包（store 里的孤儿文件）
pnpm store prune

2.2 符号链接与严格依赖隔离 ​

pnpm 的 node_modules 结构与 npm/yarn 完全不同：

node_modules/
├── .pnpm/                      # 真实包都在这里，按「版本+依赖指纹」平铺
│   ├── react@18.3.1/node_modules/react
│   └── lodash@4.17.21/node_modules/lodash
├── react -> .pnpm/react@18.3.1/node_modules/react   # 顶层是符号链接
└── .modules.yaml
  • 顶层 node_modules 只软链你显式声明在 package.json 的依赖（直接依赖）。
  • 传递依赖（transitive）只能从 .pnpm/<pkg>/node_modules 内部软链访问，无法凭空 import。
  • 这消除了 npm 的「幽灵依赖（phantom dependency）」：只用 package.json 声明的包才 import 得到，逼你诚实声明依赖。

2.3 hoisting 与实际差异 ​

pnpm 的「提升（hoisting）」是把包软链到 .pnpm/node_modules，供传递依赖互相解析，而不是塞进顶层 node_modules。这与 npm/yarn 的扁平化提升不同，所以：

  • 从 npm/yarn 迁移到 pnpm 后，常见报错是 Cannot find module 'xxx' —— 因为那个包本来是幽灵依赖。
  • 正确做法是补进 package.json，而不是开 shamefully-hoist。
ini
# .npmrc：不推荐轻易开启，它会退回扁平化，破坏严格隔离
shamefully-hoist=true
# 更精确的替代：只为特定构建工具放开
public-hoist-pattern[]=*eslint*
public-hoist-pattern[]=*prettier*
# 允许执行安装脚本的白名单（pnpm 10 默认禁用 postinstall，安全第一）
onlyBuiltDependencies[]=esbuild
onlyBuiltDependencies[]=sharp

pnpm 10 起默认不执行依赖的 postinstall 脚本（防止供应链攻击），需要二进制下载的包（esbuild、sharp、puppeteer）必须加进 onlyBuiltDependencies，否则会报「Ignored build scripts」。

三、workspace 配置与包引用 ​

3.1 根配置 ​

yaml
# pnpm-workspace.yaml（pnpm 10 推荐把 onlyBuiltDependencies 也放这里）
packages:
  - "packages/*"
  - "apps/*"
  - "!**/test/**"
json
// 根 package.json
{
  "name": "monorepo-root",
  "private": true,
  "packageManager": "pnpm@9.12.0",
  "scripts": {
    "build": "turbo run build",
    "dev": "turbo run dev",
    "lint": "turbo run lint",
    "test": "turbo run test",
    "release": "pnpm build && changeset publish"
  }
}

packageManager 字段 + 仓库根 .npmrc 里的 engine-strict，可强制团队成员使用同一 pnpm 版本（Corepack 会据此自动切换）。

3.2 workspace: 协议引用内部包 ​

json
// packages/app/package.json
{
  "dependencies": {
    "@your-org/ui": "workspace:*",
    "@your-org/utils": "workspace:^"
  }
}
  • workspace:*：链接到本地任意版本，发布时会被替换成具体版本号（Changesets 负责替换）。
  • workspace:^ / workspace:~：链接本地，但保留 ^/~ 语义，控制发布后语义化范围。
  • 只在 dependencies / devDependencies 里写 workspace: 协议；应用包应 private: true 且不发布。

四、Turbo 任务编排 ​

4.1 turbo.json 核心字段 ​

json
{
  "$schema": "https://turbo.build/schema.json",
  "tasks": {
    "build": {
      "dependsOn": ["^build"],       // 先构建所有上游依赖包
      "outputs": ["dist/**", ".vitepress/dist/**"]
    },
    "test": {
      "dependsOn": ["build"],        // 同包内先 build 再 test
      "outputs": ["coverage/**"]
    },
    "dev": {
      "cache": false,               // dev 是长驻服务，不能缓存
      "persistent": true
    },
    "lint": { "outputs": [] }
  }
}

关键语义：

  • ^build：^ 表示「上游包」，即先跑依赖包的 build（拓扑顺序，Turbo 自动并行无依赖关系的任务）。
  • 不带 ^ 的 dependsOn：表示同包内的前置任务（如 test 依赖同包 build）。
  • outputs：声明产物路径，命中缓存时直接恢复这些目录，跳过重跑。
  • cache: false / persistent: true：dev/watch 类长驻任务。

4.2 缓存与远程缓存 ​

Turbo 对每个任务算一个 hash（输入 = 源码 + 依赖版本 + 环境变量 + 任务配置指纹），命中即跳过执行：

bash
# 本地缓存默认在 node_modules/.cache/turbo
turbo run build --dry=json   # 查看哪些任务会命中缓存（不真正执行）

# 远程缓存：CI 与本地共享，大幅减少重复构建
turbo login && turbo link          # 关联 Vercel Remote Cache
# 或在 CI 里注入
TURBO_TOKEN=xxx TURBO_TEAM=your-team turbo run build

命中缓存的前提是任务输入保持一致。如果构建脚本读取了未声明的环境变量、或用 Date.now() 生成内容，缓存会“命中但结果错误”或永远失效。

五、Changesets 版本管理与多包联动发布 ​

Changesets 用**变更文件（changeset）**驱动版本：开发者在 PR 里写「我要给哪个包升什么级别、写什么 changelog」，CI 再统一消费。

bash
pnpm add -D @changesets/cli -w
pnpm changeset init      # 生成 .changeset/config.json
pnpm changeset           # 交互式选择包 + 语义化级别(major/minor/patch) + 摘要
pnpm changeset version   # 根据 changeset 提升版本号、改依赖范围、写 CHANGELOG.md
pnpm changeset publish   # 发布所有版本有变化的包，并打 git tag
json
// .changeset/config.json 常用项
{
  "access": "public",
  "baseBranch": "main",
  "updateInternalDependencies": "patch",
  "linked": [["@your-org/ui", "@your-org/icons"]],
  "ignore": ["@your-org/playground"]
}
  • 联动（linked）：一组包版本号同步进退，适合「主包 + 图标包」这类强绑定关系。
  • fixed：更严格的强同步（整组永远同版本）。linked 允许相对差异，fixed 强制一致。
  • updateInternalDependencies：当被依赖的内部包版本变化时，自动更新使用时声明的范围。

六、Monorepo 下的 TS 路径与构建顺序 ​

6.1 两种引用内部包的方式 ​

方式写法适用
源码引用（开发）paths 指向 ../ui/src/index.ts本地 dev 实时热更，无需先 build
产物引用（发布）走 node_modules 的 exports发布/下游使用，用 dist 产物
json
// tsconfig.base.json
{
  "compilerOptions": {
    "paths": {
      "@your-org/ui": ["packages/ui/src/index.ts"],
      "@your-org/utils": ["packages/utils/src/index.ts"]
    },
    "composite": true,
    "moduleResolution": "Bundler"
  }
}

6.2 构建顺序 ​

  • Turbo 的 dependsOn: ["^build"] 已保证拓扑顺序；手动用 pnpm -r run build 也要靠 --sort（pnpm 默认按拓扑排序，加 --workspace-concurrency 控制并发）。
  • 需要「先 build 依赖再 dev 自身」时，用 turbo run dev --filter=app...（三个点表示「含依赖」）；app^... 表示「含其依赖」的不同写法，注意 --filter 后缀语义：pkg 自身、pkg... 自身+下游、...pkg 自身+上游。

七、常见坑与实战要点 ​

  1. TS2307 找不到模块：monorepo 里 Cannot find module '@your-org/ui'。原因通常是 (a) tsconfig 的 paths 没配，(b) 或包没列进 workspace，(c) 或该包用产物引用但还没 build。先确认「源码引用 or 产物引用」策略，别混用。
  2. dev 时序竞态：turbo run dev 并行启动，依赖包尚未产出 dist，应用就报找不到模块。解法：给 dev 也加 dependsOn: ["^build"]，或依赖包用源码引用（exports 指向 src，配合宿主打包器的 alias）。
  3. 依赖版本统一：多个包各自声明同一库的不同版本，pnpm 会装多份。用 pnpm dedupe 或根 pnpm.overrides 强制统一：
    json
    { "pnpm": { "overrides": { "react": "18.3.1", "typescript": "5.6.3" } } }
  4. 幽灵依赖：迁移到 pnpm 后大量 Cannot find module，本质是以前用了没声明的包。补 package.json，而非开 shamefully-hoist。
  5. 发布时忘记把 workspace:* 换成版本号：用 pnpm publish（而非 npm publish）或在发布前跑 changeset version，它会完成替换。
  6. onlyBuiltDependencies 缺失：pnpm 10 下 esbuild/sharp 等被忽略构建脚本，报错要按提示加进白名单。
  7. CI 全量跑：用 --filter="...[origin/main]" 只跑受影响的包；Turbo 的远程缓存让未变更任务秒回。
  8. 构建产物未声明为 outputs：Turbo 缓存命中却拿不到 dist，检查 turbo.json 的 outputs 是否覆盖了产物目录。

面试要点 ​

  1. 为什么用 pnpm 而不是 npm/yarn？ 内容寻址存储 + 硬链接省磁盘、严格依赖隔离消除幽灵依赖、安装更快。
  2. pnpm 的 node_modules 结构为什么能防幽灵依赖？ 顶层只软链直接依赖，传递依赖藏在 .pnpm/<pkg>/node_modules，未声明的包 import 不到。
  3. shamefully-hoist 是什么？ 退回扁平化提升的兼容开关，会破坏隔离，能不用就不用，改用 public-hoist-pattern 精确放开。
  4. Turbo 的 ^build 和 build 有何区别？ 前者指上游依赖包的 build（拓扑顺序），后者指同包内前置任务。
  5. Turbo 缓存的 key 由什么决定？ 源码内容、依赖版本、环境变量、任务配置指纹等输入的哈希；输入变了则缓存失效。
  6. Changesets 的 linked 与 fixed 区别？ linked 允许组内相对差异，fixed 强制整组版本完全一致。
  7. workspace:* 发布后会变成什么？ 被替换为本地实际版本号，这是 pnpm publish/changeset version 自动完成的。
  8. monorepo 里 TS 找不到内部包怎么排查？ 检查 tsconfig paths、workspace 声明、以及是否采用了「产物引用但未构建」。
  9. 如何让 CI 只跑受影响的包？ 用 pnpm --filter="...[origin/main]" 或 Turbo 的 GitHub 集成做变更分析。
