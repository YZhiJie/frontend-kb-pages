双栈对比与同构组件库 ​

本页对应 JD 要求 A1（React 或 Vue，多数要求双栈）、A5（组件化/组件库/公共能力建设，含 SDK 交付，出现 7 份）、C8（pnpm workspace/monorepo）。本页是简历"跨框架同构组件库"这一结构性优势的技术落点，面试中用于展示架构设计能力。

一、React 与 Vue 心智模型对比 ​

维度ReactVue 3
数据模型不可变（immutable），改状态靠 setState 换新引用响应式（reactive），直接改即可通知
逻辑组织Hooks（函数，靠调用顺序）组合式函数（靠响应式依赖）
视图描述JSX（JS 表达式，受 TS 类型约束强）模板（编译期优化，v- 指令）
更新机制渲染函数重建 VNode 树 + diff，靠 memo/keyPatchFlag + Block Tree 靶向 diff
状态存储Fiber 上的 hook 链表组件实例上的 effect 依赖图
插槽/组合children + render prop具名/作用域插槽
生态Redux/Zustand、React Router、TanStack QueryPinia、Vue Router、VueUse

共同点：都以组件为单元、都用虚拟 DOM + diff、都有单向数据流（props down / events up）。这决定了框架无关的核心逻辑可以复用。

二、双栈能力的职业价值 ​

  • JD 覆盖率：10 份 JD 中 9 份要求 React 或 Vue，其中多数要求"双栈"；跨框架组件库是 A5 要求的最强证据。
  • 迁移成本低：能同时维护两套技术栈的中后台/组件库，减少团队切换框架的阻力。
  • 抽象能力证明：能把"框架无关逻辑"抽出来，证明候选人有架构分层与契约设计能力，而非只会写页面。
  • 交付能力：组件库/SDK 对外交付（A5）要求稳定的 API 契约、版本管理、文档与测试，这是同构设计天然覆盖的。

三、跨框架同构组件库设计 ​

3.1 整体分层 ​

packages/
  core/        # 框架无关：状态机、校验、虚拟滚动、浮层避让、i18n、类型契约
  vue/         # 适配层：渲染桥接，无业务逻辑
  react/       # 适配层：渲染桥接，无业务逻辑
  tokens/      # 设计令牌：CSS 变量 + BEM 类名（样式单一来源）

核心原则：逻辑只写一遍，渲染各写一次。core 不依赖任何框架与 DOM。

3.2 以 ComponentSpec 为双端唯一契约 ​

ComponentSpec 是描述"一个组件长什么样"的机器可读契约（props、事件、插槽、默认值）。两端适配层与契约测试都从它派生，保证不漂移。

ts
// packages/core/src/spec.ts
export type PropType = 'string' | 'number' | 'boolean' | 'function' | 'array' | 'object';
export interface PropSpec {
  name: string;
  type: PropType;
  required?: boolean;
  default?: unknown;
  /** 受控模式：值 prop 的配套变更回调 */
  controlled?: { value: string; onChange: string };
}
export interface SlotSpec {
  name: string;          // 'default' | 'header' | ...
  scoped?: Record<string, PropType>; // 作用域插槽参数 → React 回调入参
}
export interface ComponentSpec {
  name: string;
  props: PropSpec[];
  emits: { name: string; payload: { name: string; type: PropType }[] }[];
  slots: SlotSpec[];
}

export const InputSpec: ComponentSpec = {
  name: 'Input',
  props: [
    { name: 'value', type: 'string', controlled: { value: 'value', onChange: 'onValueChange' } },
    { name: 'placeholder', type: 'string' },
    { name: 'disabled', type: 'boolean', default: false },
    { name: 'maxLength', type: 'number' },
  ],
  emits: [{ name: 'valueChange', payload: [{ name: 'value', type: 'string' }] }],
  slots: [{ name: 'prefix' }, { name: 'suffix' }],
};

3.3 核心逻辑下沉：以"受控输入 + 校验"为例 ​

core 只导出纯函数与订阅式状态机，不碰 DOM：

ts
// packages/core/src/useField.ts
export interface FieldOptions {
  initial: string;
  maxLength?: number;
  validate?: (v: string) => string | null;
}
export interface FieldState { value: string; error: string | null; touched: boolean }

/** 框架无关的状态机：订阅者只拿到快照 */
export function createField(opts: FieldOptions) {
  let state: FieldState = { value: opts.initial, error: null, touched: false };
  const listeners = new Set<(s: FieldState) => void>();
  const emit = () => listeners.forEach(l => l(state));

  return {
    getState: () => state,
    subscribe(l: (s: FieldState) => void) {
      listeners.add(l);
      return () => listeners.delete(l);
    },
    setValue(next: string) {
      if (opts.maxLength != null && next.length > opts.maxLength) next = next.slice(0, opts.maxLength);
      state = { ...state, value: next, error: opts.validate?.(next) ?? null };
      emit();
    },
    blur() { state = { ...state, touched: true }; emit(); },
  };
}

关键：getState 必须返回稳定快照（这里 state 只在变更时整体新建，订阅者可用引用比较），否则会踩 useSyncExternalStore 的无限重渲染坑。

3.4 双端适配层只做渲染桥接 ​

React 侧用 useSyncExternalStore 订阅 core；Vue 侧用 shallowRef + subscribe。适配层不含业务逻辑。

tsx
// packages/react/src/Input.tsx
import { useSyncExternalStore } from 'react';
import { createField, type FieldOptions } from '@kb/core';

interface InputProps extends FieldOptions {
  value?: string;                 // 受控
  onValueChange?: (v: string) => void;
  className?: string;
  renderPrefix?: () => React.ReactNode; // 具名插槽 prefix 的 React 形态
  renderSuffix?: () => React.ReactNode;
}

export function Input({ value, onValueChange, className, renderPrefix, renderSuffix, ...opts }: InputProps) {
  const field = useMemo(() => createField(opts), [opts.initial, opts.maxLength]); // eslint-disable-line
  const state = useSyncExternalStore(field.subscribe, field.getState, field.getState);

  const current = value ?? state.value;                 // value 优先（受控）
  const change = (v: string) => { field.setValue(v); onValueChange?.(v); }; // 统一回调名
  return (
    <div className={`kb-input ${className ?? ''}`}>
      {renderPrefix && <span className="kb-input__prefix">{renderPrefix()}</span>}
      <input className="kb-input__inner" value={current} onChange={e => change(e.target.value)} />
      {renderSuffix && <span className="kb-input__suffix">{renderSuffix()}</span>}
    </div>
  );
}
vue
<!-- packages/vue/src/Input.vue -->
<script setup lang="ts">
import { shallowRef } from 'vue';
import { createField } from '@kb/core';
const props = withDefaults(defineProps<{
  value?: string;
  onValueChange?: (v: string) => void;
  initial?: string;
  maxLength?: number;
  class?: string;
}>(), { initial: '' });
const field = createField({ initial: props.value ?? props.initial, maxLength: props.maxLength });
const state = shallowRef(field.getState());
field.subscribe(s => (state.value = s)); // 桥接：把订阅映射到 Vue 响应式
function onInput(e: Event) {
  const v = (e.target as HTMLInputElement).value;
  field.setValue(v); props.onValueChange?.(v);
}
</script>

<template>
  <div class="kb-input" :class="props.class">
    <span v-if="$slots.prefix" class="kb-input__prefix"><slot name="prefix" /></span>
    <input class="kb-input__inner" :value="props.value ?? state.value" @input="onInput" />
    <span v-if="$slots.suffix" class="kb-input__suffix"><slot name="suffix" /></span>
  </div>
</template>

四、插槽映射规则 ​

VueReact契约（ComponentSpec.slots）
默认插槽 <slot />children{ name: 'default' }
具名插槽 <slot name="header" />renderHeader?: () => ReactNode{ name: 'header' }
作用域插槽 <slot :item="item" />children: (item) => ReactNode 或 renderItem{ name: 'default', scoped: { item: 'object' } }
多个作用域参数 #row="{ item, index }"renderRow: (item, index) => ReactNodescoped: { item, index }

映射规则由 ComponentSpec.slots 机器化描述，两端适配层的类型与运行时都对齐它。

五、样式单一来源 ​

样式只写在 tokens 包，用 BEM 命名 + CSS 变量，两端共用同一份 CSS，框架无关：

css
/* packages/tokens/src/input.css */
:root {
  --kb-color-primary: #2563eb;
  --kb-input-height: 32px;
  --kb-input-radius: 4px;
}
.kb-input { display: inline-flex; height: var(--kb-input-height); border-radius: var(--kb-input-radius); }
.kb-input__inner { flex: 1; border: 1px solid var(--kb-color-primary); }
.kb-input--disabled { opacity: .5; cursor: not-allowed; }

主题切换只需改 CSS 变量（:root[data-theme="dark"]），不用给两套框架各写主题逻辑。

六、受控模式统一约定（value + onValueChange） ​

统一约定：值 prop 用 value，变更回调用 onValueChange（而非 React 的 onChange）。

原因：

  • React 原生 onChange 语义是"输入即触发"，Vue 的 @change 是"失焦/提交才触发"，两者语义不一致。
  • 统一用 onValueChange 避免语义混淆；React 侧映射到 onChange、Vue 侧映射到 @input。
  • 受控/非受控切换：value 传入即受控（由父维护），不传则组件内部 initial 自管。

在 ComponentSpec.props[i].controlled 中声明"值 prop 与变更回调的配对关系"，契约测试据此校验两端一致。

七、三方契约对齐测试（CI 机器化强制） ​

目标：core / vue / react 的 props、事件、默认值、插槽在三端机器化一致，任何漂移在 CI 拦截。

ts
// packages/core/__tests__/contract.spec.ts（Vitest）
import { describe, it, expect } from 'vitest';
import { InputSpec } from '../src/spec';
import { inputProps as reactProps } from '@kb/react/manifest';
import { inputProps as vueProps } from '@kb/vue/manifest';

function normalize(spec: typeof InputSpec) {
  return {
    props: spec.props.map(p => `${p.name}:${p.required ?? false}:${JSON.stringify(p.default ?? null)}`).sort(),
    emits: spec.emits.map(e => e.name).sort(),
    slots: spec.slots.map(s => s.name).sort(),
  };
}

describe('Input 三端契约一致', () => {
  const base = normalize(InputSpec);
  it('React 适配层与契约一致', () => expect(normalize(reactProps)).toEqual(base));
  it('Vue 适配层与契约一致', () => expect(normalize(vueProps)).toEqual(base));
});

配合 pnpm workspace：根 pnpm -r test 一次跑完，CI 中任何端落后即红灯。这正好命中 JD 的"测试能力（Vitest）+ monorepo + 组件库"。

八、适配层类型与 tsconfig paths 的坑 ​

同构库常出现"源码里 import '@kb/core' 指向 src，但发布后指向 dist/types"的双形态。配置不当会踩以下坑：

  1. paths 指到 dist/types 却没先 build：类型不存在 → 编译报错。要么先 pnpm -r build 再 typecheck，要么 paths 指向 src 并用 references。
  2. 类型与运行时双源：paths 指 src（类型来自源码），但实际打包用 dist（运行时来自产物），若两者不同步会出现"类型通过但运行时 API 不存在"。解法是让 TS 与入口都指向同一形态（常用 dist/index.d.ts + exports 字段）。
  3. composite: true + references：monorepo 项目引用需要 tsconfig.build.json 声明 references，且被引用包必须 composite，否则增量构建失效。
  4. moduleResolution: "bundler"：Vue/React 适配层推荐 bundler，配合 exports 的 types 条件；旧项目用 node 会在子路径导入时找不到声明。
jsonc
// packages/react/tsconfig.json
{
  "compilerOptions": {
    "moduleResolution": "bundler",
    "composite": true,
    "paths": { "@kb/core": ["../core/dist/index.d.ts"] }
  },
  "references": [{ "path": "../core" }]
}

九、包体积预算 ​

同构组件库要对外交付，体积是硬指标。建议在 CI 设预算并拦截：

  • 按需导出：每个组件独立入口（exports 的 ./input 子路径），配合 tree-shaking；避免"一个入口导出全部"导致整包引入。
  • sideEffects: false：package.json 声明，让打包器可以摇树；样式单独入口并显式 import，避免误删。
  • 外部依赖 externalize：react/vue 及大库（echarts、lodash）声明为 peerDependencies 并 external，不打进产物。
  • 预算阈值：用 size-limit（或 bundle-analyzer + 自定义脚本）设阈值，例如单组件 gzip < 5KB，整包首屏 < 40KB，超限 CI 失败。
jsonc
// package.json
{
  "sideEffects": ["*.css"],
  "exports": {
    ".": { "types": "./dist/index.d.ts", "import": "./dist/index.mjs" },
    "./input": { "types": "./dist/input.d.ts", "import": "./dist/input.mjs" }
  },
  "peerDependencies": { "react": ">=18", "react-dom": ">=18", "vue": ">=3.4" }
}
jsonc
// .size-limit.json
[ { "name": "Input", "path": "dist/input.mjs", "limit": "5 kB" } ]

十、常见坑速查 ​

坑现象解法
core 依赖框架逻辑无法复用core 不 import react/vue，纯 TS
适配层写业务逻辑两端行为漂移逻辑只在 core，适配层只桥接渲染
onChange 语义两端不一致React 输入即触发、Vue 失焦触发统一 onValueChange，各自映射
getSnapshot 返回新对象React 无限重渲染core 返回稳定引用快照
样式写两套主题不一致、维护翻倍BEM + CSS 变量单一来源
paths 指 dist 未 build类型编译失败先 build 或指 src + references
整包导出、无 sideEffects体积超标子路径导出 + sideEffects: false
契约靠人肉对齐一端改 api 另一端忘同步CI 机器化契约测试

面试要点 ​

  1. React 和 Vue 最本质的心智差异？ 答：React 不可变需换引用、靠 re-render 重算；Vue 响应式可直接改、依赖追踪派发更新。
  2. 跨框架同构组件库怎么做到"逻辑只写一遍"？ 答：核心逻辑下沉到框架无关的 core，两端适配层只做渲染桥接，用 ComponentSpec 作为唯一契约。
  3. 插槽如何在两框架间映射？ 答：默认插槽↔children，具名插槽↔renderXxx 回调，作用域插槽↔接收参数的 render 回调，由 spec.slots 描述。
  4. 受控模式为什么统一用 value + onValueChange？ 答：React onChange 与 Vue @change 语义不同，统一命名消除歧义，各自映射到底层事件。
  5. 三方契约测试的价值？ 答：在 CI 机器化强制 core/Vue/React 的 props/事件/默认值/插槽一致，防止 API 漂移。
  6. 适配层 tsconfig paths 指 dist/types 的坑？ 答：未先 build 则类型缺失；类型与运行时若来源不一致会出现"编译过但运行崩"，需统一入口形态 + references。
  7. 同构库如何控制体积？ 答：子路径按需导出、sideEffects: false、大依赖 external/peer、用 size-limit 设预算并在 CI 拦截。
  8. 样式如何单一来源？ 答：BEM 类名 + CSS 变量，主题切换只改变量，两端共用同一份 CSS，不写框架特有样式逻辑。
  9. 双栈能力对团队的价值？ 答：降低框架切换成本、组件库/SDK 可跨栈交付、证明架构分层与抽象能力。
  10. core 层订阅如何避免 React 的无限重渲染？ 答：core 用订阅 + 稳定快照，React 侧用 useSyncExternalStore，Vue 侧用 shallowRef 桥接。
