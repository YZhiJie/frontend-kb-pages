React 18/19 深入 ​

本页对应 JD 要求 A1（React 或 Vue，且多数要求双栈）、B1（B 端中后台）、B6（状态管理与路由）、C7（响应式原理）。React 18 引入了并发渲染，React 19 补齐了 Actions 与编译器优化的地基，面试中几乎必问"渲染机制 + Hooks 规则 + 性能优化"三件套。

一、组件与 JSX 的本质 ​

JSX 不是模板语法，而是 React.createElement(type, props, ...children) 的语法糖。React 17 起改用 react/jsx-runtime 的 jsx()，不再在模块作用域注入 React，所以不写 import React 也能编译。

tsx
// 等价关系
const el = <button className="btn" onClick={fn}>点我</button>;
const el2 = React.createElement('button', { className: 'btn', onClick: fn }, '点我');

关键结论：

  • 组件本质是返回 React 元素（或元素树）的函数。<Foo /> 编译后是 createElement(Foo)，React 在渲染时把它当作"组件类型"去调用，而不是当作 DOM 标签。
  • 小写标签（div）映射为宿主（host）元素，大写标识符（Foo）映射为组件类型；这是 JSX 区分二者的唯一规则。
  • key 只在兄弟节点 diff 时用于身份识别，不会透传到 DOM，也不参与 props 展开。

二、Hooks 的规则与原理 ​

2.1 为什么不能条件调用 ​

Hooks 在 Fiber 节点上以链表存储（memoizedState 指向第一个 hook，hook.next 串成链表）。React 靠调用顺序把当前调用与上次的记忆槽位一一匹配：

ts
// 伪代码：简化版的 mount 阶段
function mountWorkInProgressHook() {
  const hook = { memoizedState: null, queue: null, next: null };
  if (workInProgressHook === null) {
    currentlyRenderingFiber.memoizedState = workInProgressHook = hook;
  } else {
    workInProgressHook = workInProgressHook.next = hook;
  }
  return workInProgressHook;
}

如果 if (cond) useState() 导致某次渲染的调用顺序与上次不同，React 就会把 useState 的状态对到 useEffect 的槽位上，直接抛 "Rendered fewer hooks than expected" 或产生错误状态。因此规则是：只在顶层调用、不在条件/循环/嵌套函数里调用（自定义 Hook 除外）。

2.2 常用 Hooks 深入 ​

Hook记忆内容触发重渲染关键点
useStatestate 值 + update queue是值更新用函数式 setX(prev => ...) 避免闭包旧值
useReducerstate + dispatch是复杂状态/多字段联动/需要"动作语义"时优于多个 useState
useEffect依赖数组 + create/cleanup否依赖比较用 Object.is，数组/对象字面量每次都是新引用
useLayoutEffect同上否在 DOM 变更后、浏览器绘制前同步执行，用于测量布局、防闪烁
useMemo值 + 依赖否计算昂贵或需稳定引用时用，不是语义保证，React 可丢弃缓存
useCallback函数 + 依赖否等价于 useMemo(() => fn, deps)，用于稳定引用
useRef{ current } 容器否变更 .current 不触发渲染，是"盒子"而非"状态"
tsx
import { useReducer } from 'react';

type Action = { type: 'add'; n: number } | { type: 'reset' };
function reducer(state: number, action: Action) {
  switch (action.type) {
    case 'add': return state + action.n;
    case 'reset': return 0;
  }
}
function Counter() {
  const [count, dispatch] = useReducer(reducer, 0);
  return <button onClick={() => dispatch({ type: 'add', n: 1 })}>{count}</button>;
}

2.3 useEffect 的清理与闭包陷阱 ​

useEffect 的 create 函数捕获了当前渲染的 props/state 快照。若依赖数组为空，回调永远看到首次渲染的值：

tsx
function Timer() {
  const [count, setCount] = useState(0);
  useEffect(() => {
    const id = setInterval(() => setCount(c => c + 1), 1000); // 用函数式更新，正确
    return () => clearInterval(id); // cleanup：卸载或下次 effect 前执行
  }, []); // 空依赖只跑一次
  return <span>{count}</span>;
}

陷阱清单：

  • 忘记 return cleanup → 订阅/定时器/事件监听泄漏。
  • 依赖数组里放 onChange 这类父组件每次渲染都新建的回调 → effect 每次都重跑（见第十节 latest-ref 模式）。
  • cleanup 里读取的也是"当次渲染"的闭包，若需最新值应放进依赖或改用 ref。

2.4 useSyncExternalStore（订阅外部 store） ​

React 18 新增 useSyncExternalStore，用于安全订阅 React 之外的数据源（Redux、Zustand、浏览器 API）。它要求提供 getSnapshot，React 用快照判断是否需要重渲染。

tsx
import { useSyncExternalStore } from 'react';

const store = {
  listeners: new Set<() => void>(),
  value: 0,
  subscribe(cb: () => void) {
    store.listeners.add(cb);
    return () => store.listeners.delete(cb);
  },
  getSnapshot() { return store.value; },
  set(v: number) { store.value = v; store.listeners.forEach(l => l()); },
};

function useStoreValue() {
  return useSyncExternalStore(store.subscribe, store.getSnapshot);
}

关键陷阱：getSnapshot 必须返回稳定值。若每次返回新对象（如 { value: n }），React 判断"快照变了"会无限重渲染，报 "getSnapshot should be cached"。解法是让 store 内部缓存对象引用，或在消费端用 useMemo(() => ({ value: raw }), [raw]) 缓存派生对象。

三、Context 与性能 ​

Context 的值变化会让所有消费者重渲染（无论中间层是否 memo）。因此：

  • 把高频变化的值与低频的值拆成两个 Context（如 ThemeContext 与 StateContext）。
  • value 用 useMemo 包裹，避免父组件重渲染时意外改变引用。
  • 不可变与可变分离：稳定引用对象放进单独 Context。
tsx
const UserContext = createContext<User | null>(null);

function Provider({ user, children }: { user: User; children: ReactNode }) {
  const [theme, setTheme] = useState<'light' | 'dark'>('light');
  const userValue = useMemo(() => ({ user }), [user]);
  return (
    <ThemeContext.Provider value={theme}>
      <UserContext.Provider value={userValue}>{children}</UserContext.Provider>
    </ThemeContext.Provider>
  );
}

只有在父组件有相同子元素 children 透传时，Provider 自身重渲染才不会导致消费者重渲染（因为 children 引用未变）。

四、渲染机制与 Fiber ​

4.1 双缓冲与两阶段 ​

React 用 Fiber 树实现可中断的渲染。内存中同时存在 current（当前屏幕）与 workInProgress（正在构建）两棵树，通过 alternate 指针互连，提交时切换，形成双缓冲。

  • Render 阶段（可中断）：从根开始 beginWork 向下、completeWork 向上，构建 workInProgress 树，计算 diff（effect list）。
  • Commit 阶段（不可中断）：beforeMutation（getSnapshotBeforeUpdate）→ mutation（真正操作 DOM）→ layout（useLayoutEffect/componentDidMount）。

4.2 diff 策略 ​

React 的 diff 是 O(n) 的启发式算法，三条假设：

  1. 不同类型元素产生不同树（div → span 直接卸载重建）。
  2. 同层比较，不跨层移动。
  3. 通过 key 标识稳定身份，key 变化即视为新节点。

列表中使用数组下标作 key 是典型坑：插入/删除会导致后续节点 key 全部位移，状态（输入框内容、选中态）错位。稳定唯一 id 才是正解。

五、并发特性 ​

React 18 开启并发渲染后，新增三个面向用户的能力：

  • useTransition：把非紧急更新标记为 transition，让紧急更新（如输入）先渲染。
  • useDeferredValue：延迟某个值的传播，渲染时可先用旧值。
  • <Suspense>：协调 loading 状态，配合 lazy 做代码分割。
tsx
function Search() {
  const [query, setQuery] = useState('');
  const [list, setList] = useState<string[]>([]);
  const [isPending, startTransition] = useTransition();
  function onChange(e: React.ChangeEvent<HTMLInputElement>) {
    const v = e.target.value;
    setQuery(v); // 紧急：输入框立即回显
    startTransition(() => setList(heavyFilter(v))); // 非紧急：可被打断
  }
  const deferred = useDeferredValue(query);
  return <>{isPending ? <Spinner /> : <List data={list} deferred={deferred} />}</>;
}

要点：useTransition 给你 isPending 做降级 UI；useDeferredValue 适合"下游组件很重、拿不到 setState"的场景。二者都需要真实并发渲染器（createRoot）才生效。

六、性能优化与度量 ​

优化手段按收益排序：

  1. 减少渲染范围：React.memo（浅比较 props）、useMemo/useCallback 稳定引用、拆分组件让状态下沉。
  2. 减少渲染成本：虚拟列表（react-window/react-virtual）、key 稳定、避免在渲染里创建大对象/大数组。
  3. 减少包体积：路由级 React.lazy + <Suspense>、具名导入避免 tree-shaking 失效、分析 vite build --report。
  4. 状态设计：把高频状态放到最靠近消费者的组件，避免提升到根导致全树重渲染。

度量：React DevTools Profiler 看 flamegraph 与 ranked 视图；<React.Profiler> 埋点收集 commit 耗时。

tsx
import { Profiler } from 'react';
<Profiler id="List" onRender={(id, phase, actualDuration) => {
  if (actualDuration > 16) console.warn('慢渲染', id, phase, actualDuration);
}}>
  <List />
</Profiler>

常见坑：React.memo 对 children 中包含 JSX 的组件无效，因为 JSX 每次都是新对象；此时应透传 children 而不在父层重建。

七、错误边界 ​

错误边界是唯一仍需 class 组件的场景，因为它依赖 getDerivedStateFromError / componentDidCatch。它只捕获子树渲染、生命周期、构造函数中的错误，不捕获事件处理器、异步回调、SSR、边界自身抛出的错误。

tsx
class ErrorBoundary extends React.Component<
  { fallback: React.ReactNode; children: React.ReactNode },
  { hasError: boolean }
> {
  state = { hasError: false };
  static getDerivedStateFromError() { return { hasError: true }; }
  componentDidCatch(error: Error, info: React.ErrorInfo) {
    logToSentry(error, info.componentStack); // 上报
  }
  render() {
    return this.state.hasError ? this.props.fallback : this.props.children;
  }
}

配合 Sentry 时用 react-error-boundary 的 resetKeys 在路由变化时自动重置错误态。

八、React 19 新特性 ​

  • Actions：把"提交 + 处理 pending + 乐观更新"标准化。<form action={fn}> 中 fn 收到 FormData，可在异步中直接 setState。
  • useActionState：管理 action 的返回值与 pending 状态。
  • useFormStatus：子组件读取父表单的 pending 状态，无需层层透传 props。
  • use：在渲染中读取 Promise（配合 Suspense）或 Context（可在条件语句中调用，区别于 useContext）。
  • ref 作为 prop：函数组件可直接接收 ref，不再需要 forwardRef；ref cleanup 支持返回清理函数。
  • useOptimistic：乐观更新，失败回滚。
  • React Compiler：编译期自动 memo，核心理念是"让开发者写朴素代码，编译器消除过度渲染"，减少手工 useMemo/useCallback。
tsx
import { useActionState, useFormStatus } from 'react';

function SubmitButton() {
  const { pending } = useFormStatus();
  return <button disabled={pending}>{pending ? '提交中' : '提交'}</button>;
}

function Form() {
  const [state, formAction, isPending] = useActionState(
    async (_prev: string | null, formData: FormData) => {
      const res = await api.save(formData.get('name') as string);
      return res.ok ? null : res.message;
    },
    null,
  );
  return (
    <form action={formAction}>
      <input name="name" />
      {state && <p className="error">{state}</p>}
      <SubmitButton />
    </form>
  );
}

九、受控与非受控 ​

  • 受控：value + onChange 由 React state 驱动，单一数据源，适合校验/联动/受控提交。
  • 非受控：用 defaultValue + ref 读取，DOM 自己维护状态，适合大表单性能敏感项或与三方库集成。
  • React 19 起 <input> 支持 defaultValue 与 value 并存，非受控可后续被"接管"为受控。
  • 读取非受控值用 ref.current?.value；以"是否传入 value"作为受控开关。

十、latest-ref 模式（消除回调引用导致的竞态） ​

场景：useEffect 依赖了一个"每次渲染都新建"的回调，导致 effect 每次重跑 → 频繁请求 / 竞态。典型解法把回调存进 ref，effect 只依赖稳定引用：

tsx
function useLatest<T>(value: T) {
  const ref = useRef(value);
  ref.current = value; // 每次渲染同步最新值
  return ref;
}

function useInterval(callback: () => void, delay: number) {
  const latestCb = useLatest(callback);
  useEffect(() => {
    const id = setInterval(() => latestCb.current(), delay);
    return () => clearInterval(id);
  }, [delay]); // 只依赖 delay，callback 变更不再重启定时器
}

另一种：用 AbortController 让旧请求失效——在 effect 中创建 ctrl，fetch(url, { signal: ctrl.signal })，cleanup 里 ctrl.abort()，即可避免"后发先至"覆盖新结果（AbortError 需单独忽略）。

面试要点 ​

  1. 为什么 Hooks 不能写在条件语句里？ 答：Fiber 用链表按调用顺序存储 hook，顺序变化会导致状态槽位错配。
  2. useEffect 依赖数组为空 vs 缺省的区别？ 答：空数组 = 只挂载执行一次；缺省 = 每次渲染后都执行。
  3. useMemo/useCallback 能保证一定缓存吗？ 答：不能，React 可能丢弃缓存，它们是性能优化而非语义保证。
  4. useLayoutEffect 与 useEffect 的区别？ 答：前者在 DOM 变更后、浏览器绘制前同步执行，用于测量布局防闪烁；后者异步（绘制后）。
  5. Context 为什么会引发全量重渲染，如何优化？ 答：value 变化通知所有消费者；拆分 Context、useMemo 稳定 value、让 children 透传。
  6. React diff 为何是 O(n)，key 的作用？ 答：基于同层比较 + 类型 + key 三条启发式；key 标识节点身份，避免错位。
  7. useTransition 与 useDeferredValue 的区别？ 答：前者包裹 setState 并给 isPending；后者延迟已经产生的值的传播，适合下游重组件。
  8. React 19 的 Actions 解决了什么问题？ 答：把提交、pending、乐观更新、错误回显标准化，useActionState/useFormStatus 免去手写状态机。
  9. useSyncExternalStore 的 getSnapshot 为什么要缓存？ 答：React 靠快照引用判断是否重渲染，返回新对象会导致无限循环。
  10. 回调引用变化导致 effect 重跑的解法？ 答：latest-ref（把回调写进 ref，effect 只依赖稳定值），或用 AbortController 取消旧请求。
