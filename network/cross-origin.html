浏览器跨域机制 ​

对应 JD 的「浏览器原理 / 跨域」B 级高频项。跨域是面试最爱追问、日常最爱踩坑的领域：你既要能背出同源策略与 CORS 各响应头，也要能解释「WebView 里 Hybrid 通信本质就是 postMessage 桥接」。本文按「同源策略 → 方案全景 → CORS → JSONP → postMessage / JSBridge → Nginx / Cookie / IndexedDB → 排查」组织。

一、同源策略（Same-Origin Policy） ​

同源 = 协议（protocol）+ 主机（host）+ 端口（port）三者全等。任一不同即为跨域：

当前页目标是否同源原因
https://a.com/xhttps://a.com/y是路径不参与判定
http://a.comhttps://a.com否协议不同
https://a.comhttps://a.com:8443否端口不同
https://a.comhttps://b.a.com否子域不同
https://a.comhttps://93.184.216.34否域名与 IP 不等

注意：IE 曾把端口省略视为默认端口（不参与判定），现代浏览器已统一；document.domain 已废弃，不要再依赖。

同源策略限制的范围：

  • DOM 访问：跨域 iframe 的 contentDocument、contentWindow.document 不可读写。
  • 存储：localStorage / sessionStorage / IndexedDB 按源隔离，跨域读不到。
  • 网络请求响应：fetch / XHR 默认不能读取跨域响应内容（能发出去、读不到）。
  • Cookie：跨站请求默认不携带第三方 Cookie（受 SameSite 约束）。

不被限制的：<script>、<img>、<link>、<iframe> 的加载（这正是 JSONP 与图片探测存在的原理）；跨域写 Cookie / 改 location 也在一定条件下允许。

二、跨域方案全景对比 ​

方案原理适用凭证局限
CORS服务端回 Access-Control-Allow-*标准 API 跨域支持需服务端配合、预检多一次往返
JSONP<script> 拉取 + 回调函数仅老系统 / 第三方只读不支持仅 GET、无错误码、有 XSS 风险
postMessage跨窗口 / iframe 消息iframe 嵌入、WebView、弹窗—需双向校验 origin
Nginx 反向代理同域转发到后端前端无后端改造权时的首选天然同源需运维配置、丢失真实 IP 需透传
跨域 CookieSameSite=None; Secure第三方登录态支持受浏览器第三方 Cookie 策略限制
IndexedDB按源隔离存储本地大数据缓存—不能跨源共享，需 postMessage 中继

三、CORS 详解 ​

3.1 简单请求 vs 预检请求 ​

简单请求（同时满足以下三条才免预检）：

  1. 方法为 GET / HEAD / POST；
  2. Content-Type 仅为 application/x-www-form-urlencoded、multipart/form-data、text/plain；
  3. 未携带自定义请求头（如 Authorization、X-Token）。

任一不满足即触发预检（Preflight）——浏览器先发 OPTIONS 询问服务端：

http
OPTIONS /api/orders HTTP/1.1
Origin: https://shop.example.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: authorization,content-type
http
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://shop.example.com
Access-Control-Allow-Methods: GET,POST,PUT,DELETE
Access-Control-Allow-Headers: authorization,content-type
Access-Control-Allow-Credentials: true
Access-Control-Max-Age: 86400

3.2 CORS 响应头一览 ​

响应头作用备注
Access-Control-Allow-Origin（ACAO）允许的源可回显具体源或 *；带凭证时不能为 *
Access-Control-Allow-Methods（ACAM）允许的方法仅预检需要
Access-Control-Allow-Headers（ACAH）允许的请求头仅预检需要，须覆盖真实请求的自定义头
Access-Control-Allow-Credentials（ACAC）true 时才转发 Cookie与 ACAO * 互斥
Access-Control-Expose-Headers（ACEH）允许 JS 读取的响应头默认只能读 6 个「简单响应头」
Access-Control-Max-Age（ACMA）预检结果缓存秒数减少 OPTIONS 次数

注意：Access-Control-Allow-Origin: * 与 credentials: 'include' 不能共存，浏览器会直接报错。带凭证时服务端必须回显具体源（Origin 白名单校验后返回），而不是回 *。

3.3 凭证（credentials） ​

ts
// 前端：显式声明携带 Cookie
await fetch('https://api.example.com/user', {
  method: 'GET',
  credentials: 'include',   // 等价 axios 的 withCredentials: true
});

// axios
import axios from 'axios';
axios.defaults.withCredentials = true;

credentials 三个值：omit（默认，不带凭证）、same-origin（同源带）、include（跨域也带）。跨域带 Cookie 必须三处配合：前端 credentials: 'include' + 服务端 ACAC: true + 服务端回显具体 Origin。

四、JSONP 原理与局限 ​

JSONP 利用 <script> 不受同源策略限制的特性：服务端把数据包在回调函数里返回，<script> 加载即执行回调。

js
function jsonp(url, params = {}, timeout = 5000) {
  return new Promise((resolve, reject) => {
    const cb = `__jsonp_${Date.now()}_${Math.random().toString(36).slice(2)}`;
    const script = document.createElement('script');
    const qs = new URLSearchParams({ ...params, callback: cb }).toString();

    window[cb] = (data) => { resolve(data); cleanup(); };
    const timer = setTimeout(() => { reject(new Error('jsonp timeout')); cleanup(); }, timeout);

    function cleanup() {
      delete window[cb];                 // 用完即删，避免全局污染
      script.remove();
      clearTimeout(timer);
    }
    script.src = `${url}${url.includes('?') ? '&' : '?'}${qs}`;
    script.onerror = () => { reject(new Error('jsonp error')); cleanup(); };
    document.body.appendChild(script);
  });
}

局限：只支持 GET（无法承载 body）；拿不到 HTTP 状态码，500 与网络失败都只表现为 onerror；回调名注入有 XSS 风险（服务端若拼接用户输入）；已被 CORS 完全取代，仅在对接无法改造的老接口时保留。

五、postMessage：跨窗口 / iframe / WebView 通信 ​

postMessage 是跨源窗口间唯一官方通信通道，用于 iframe 嵌入、window.open 弹窗、WebView 与 H5 通信。

ts
// 父页 → iframe：必须指定目标源（切勿用 '*' 传敏感数据）
const iframe = document.getElementById('child') as HTMLIFrameElement;
iframe.contentWindow?.postMessage({ type: 'theme', value: 'dark' }, 'https://embed.example.com');

// iframe / 子页 → 父页
window.parent.postMessage({ type: 'resize', height: document.body.scrollHeight }, 'https://host.example.com');

// 接收侧：必须校验 origin，不能只信 data
window.addEventListener('message', (e: MessageEvent) => {
  if (e.origin !== 'https://embed.example.com') return;   // 拒绝不可信来源
  const msg = e.data as { type: string; [k: string]: unknown };
  if (msg.type === 'resize') {
    iframe.style.height = `${msg.height as number}px`;
  }
});

要点：发送端用精确 targetOrigin（用 * 等于把数据广播给任何监听者，是常见安全事故）；接收端必须校验 e.origin，并做消息结构校验，否则任意站点都能通过 iframe 向你注入伪造指令。

5.1 与 JSBridge 的本质关系 ​

WebView 通信本质上就是 postMessage 桥接：Native 侧与 H5 之间通过一个「消息通道」传递 JSON 字符串，H5 发出的每个「调用」都是一条 postMessage，Native 收到后执行原生能力并把结果 postMessage 回来。

H5 → Native 的三种常见注入方式：

ts
// 1) 现代注入对象（RN WebView / 各 App 自定义）
window.ReactNativeWebView?.postMessage(JSON.stringify({ method: 'getLocation', params: {}, callback: 'cb_1' }));
// 2) iOS WKWebView 消息处理器
(window as any).webkit?.messageHandlers?.bridge?.postMessage({ method: 'getLocation' });
// 3) 兼容兜底：修改 location 触发原生拦截
const iframe = document.createElement('iframe');
iframe.style.display = 'none';
iframe.src = `myapp://getLocation?callback=cb_1`;
document.body.appendChild(iframe);
setTimeout(() => iframe.remove(), 100);

Native → H5 则通过 evaluateJavascript 注入一段脚本，最终调用的就是 H5 侧挂载的回调（内部 dispatchEvent 一个自定义事件或直接执行回调函数）。

ts
// H5 侧统一的 Bridge 抽象（Promise 化）
type Handler = (params: unknown) => void;
const callbacks = new Map<string, Handler>();

export function callNative<T>(method: string, params: Record<string, unknown> = {}): Promise<T> {
  return new Promise((resolve, reject) => {
    const cbId = `cb_${Date.now()}_${Math.random().toString(36).slice(2)}`;
    callbacks.set(cbId, (res) => {
      const { code, data } = res as { code: number; data: T };
      code === 0 ? resolve(data) : reject(new Error(`bridge error ${code}`));
    });
    const payload = JSON.stringify({ method, params, callback: cbId });
    if ((window as any).ReactNativeWebView) (window as any).ReactNativeWebView.postMessage(payload);
    else (window as any).webkit?.messageHandlers?.bridge?.postMessage(payload);
  });
}

// Native 回包时调用 H5 暴露的全局函数
(window as any).__bridgeCallback = (cbId: string, res: unknown) => {
  callbacks.get(cbId)?.(res);
  callbacks.delete(cbId);
};

要点：桥接协议要版本化（bridgeVersion），App 与 H5 各自灰度；回调必须有超时与失败兜底，否则 Native 不回调时 Promise 永久挂起；能力探测（存在性判断）先于调用，H5 在浏览器里跑时不能崩。

六、Nginx 反向代理（前端最常用） ​

当后端无法改 CORS，最稳的是运维加一层同域代理——浏览器看到的是同源 /api，由 Nginx 转发到真实后端：

nginx
server {
  listen 443 ssl;
  server_name www.example.com;

  location / {
    root /var/www/app;
    try_files $uri $uri/ /index.html;   # SPA 路由回退
  }

  location /api/ {
    proxy_pass http://backend-svc:8080/;   # 末尾斜杠会去掉 /api 前缀
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;   # 后端判断原始协议
    proxy_read_timeout 120s;                       # WebSocket/SSE 需长超时
  }

  # WebSocket 升级
  location /ws/ {
    proxy_pass http://backend-svc:8080/ws/;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
  }
}

坑：proxy_pass 结尾有无斜杠决定是否剥前缀；X-Forwarded-* 不配后端会拿不到真实 IP / 协议；WebSocket 忘了 Upgrade 头会连不上（表现为 400）。

七、跨域 Cookie：SameSite / Secure / Partitioned ​

属性值含义
SameSiteStrict任何跨站请求都不带 Cookie（最严）
SameSiteLax（现代默认）顶层导航（GET）带，跨站子请求 / iframe 不带
SameSiteNone跨站也带，必须同时 Secure
Secure—仅 HTTPS 传输
Domain.example.com覆盖子域（a.example.com 与 b.example.com 共享）
HttpOnly—JS 无法读取（防 XSS 窃取）
Partitioned—CHIPS：第三方 Cookie 按「顶层站点」分区隔离

第三方登录态（如 A 站 iframe 嵌入 B 站 SDK）需要 SameSite=None; Secure。但浏览器在收紧第三方 Cookie：Safari ITP 与 Chrome 隐私沙盒会限制甚至默认阻止第三方 Cookie，此时需转向 CHIPS（Partitioned） 或 Storage Access API。这意味着「跨域共享登录态」这类设计要提前评估浏览器版本覆盖。

八、IndexedDB 与源隔离 ​

IndexedDB 严格按源隔离，https://a.com 的库 https://b.com 读不到；跨域 iframe 里的 IndexedDB 属于 iframe 自己的源。因此大文件缓存若分散在多个域名，需各自维护，或通过 postMessage 把数据中继给主域统一存储。

ts
const db = await new Promise<IDBDatabase>((resolve, reject) => {
  const req = indexedDB.open('cache', 1);
  req.onupgradeneeded = () => req.result.createObjectStore('blobs', { keyPath: 'id' });
  req.onsuccess = () => resolve(req.result);
  req.onerror = () => reject(req.error);
});
await new Promise((res, rej) => {
  const tx = db.transaction('blobs', 'readwrite');
  tx.objectStore('blobs').put({ id: 'report-1', bytes });
  tx.oncomplete = res; tx.onerror = () => rej(tx.error);
});

九、iframe 集成与沙箱 ​

嵌入第三方页面时用 sandbox 最小化权限；不写 sandbox 等于全权限（含执行脚本、发请求、弹窗）。

html
<!-- 只允许执行脚本 + 同源，禁表单/弹窗/顶层导航 -->
<iframe
  src="https://embed.example.com/widget"
  sandbox="allow-scripts allow-same-origin"
  referrerpolicy="no-referrer"
  loading="lazy"
  allow="clipboard-write; camera 'none'"></iframe>

坑：allow-scripts 与 allow-same-origin 同时给等于没沙箱（脚本可自行移除沙箱属性重载）。若要跨源通信，优先 allow-scripts + postMessage，而不是把同源也放开。

面试要点 ​

  1. 同源策略怎么判定？ 答：协议 + 主机 + 端口三者全等；路径不参与判定。
  2. 同源策略限制了哪些操作？ 答：跨域 DOM 访问、存储读取、网络请求响应读取、第三方 Cookie；不限制 <script>/<img>/<iframe> 的加载。
  3. 简单请求的判定条件？ 答：方法为 GET/HEAD/POST、Content-Type 仅三种、无自定义头；任一不满足即触发 OPTIONS 预检。
  4. 带 Cookie 跨域为什么要三处配合？ 答：前端 credentials: 'include' + 服务端 ACAC: true + 服务端回显具体 Origin（不能用 *）。
  5. 为什么预检请求不能重定向、不能要求认证？ 答：预检由浏览器自动发起且不带凭证，302/401 会让 CORS 校验失败。
  6. JSONP 的原理和局限？ 答：利用 <script> 不受同源限制，服务端返回可执行回调；仅 GET、拿不到状态码、有 XSS 风险。
  7. postMessage 的关键安全点？ 答：发送用精确 targetOrigin、接收校验 e.origin；用 * 或只信 data 都会被伪造。
  8. JSBridge 和 postMessage 是什么关系？ 答：WebView 通信本质就是 postMessage 桥接——H5 发消息给 Native，Native 执行能力后把结果 post 回来。
  9. Nginx 代理为什么能解决跨域且最稳？ 答：浏览器只看到同源 /api，转发在其后发生，无预检、不依赖后端改 CORS，但要配 X-Forwarded-* 与 Upgrade。
  10. 第三方 Cookie 正在被淘汰，跨域共享登录态怎么办？ 答：优先同源代理或 OAuth 顶层跳转，其次 CHIPS（Partitioned）与 Storage Access API，需评估浏览器覆盖。
