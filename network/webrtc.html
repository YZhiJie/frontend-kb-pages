音视频与 WebRTC ​

对应 JD 的「音视频 / WebRTC」C 级差异化项（2 份提及，见 #8 鹏开信息 IM + 音视频 + Hybrid），也是日常会议、直播、录制回放场景的必备知识。本文按「采集与播放 → WebRTC 架构与信令 → STUN/TURN 穿透 → 质量监控与兼容 → HLS/flv.js 与桌面端编解码 → 常见坑」组织。

一、音视频前端全景 ​

音视频前端可拆成四条链路，各自 API 与难点不同：

链路关键 API难点
采集navigator.mediaDevices.getUserMedia、MediaRecorder权限、分辨率协商、设备热插拔
播放<video>、MediaSource、WebAudio自动播放策略、格式兼容、低延迟
录制回放MediaRecorder、MediaSource 分片编码格式、时间轴、分片上传
会议RTCPeerConnection、信令、SFU穿透、带宽自适应、多路混流
ts
// 采集：约束（constraints）同时决定质量与兼容性
const stream = await navigator.mediaDevices.getUserMedia({
  video: { width: { ideal: 1280 }, height: { ideal: 720 }, frameRate: { ideal: 30, max: 30 }, facingMode: 'user' },
  audio: { echoCancellation: true, noiseSuppression: true, autoGainControl: true },
});
const video = document.querySelector('video')!;
video.srcObject = stream;
await video.play();

ideal 是「尽量满足」、exact 是「必须满足」（不满足直接报 OverconstrainedError）、max/min 限定范围。设备枚举必须在授权之后（enumerateDevices 在未授权时返回空 label）：

ts
await navigator.mediaDevices.getUserMedia({ audio: true });   // 先触发授权
const devices = await navigator.mediaDevices.enumerateDevices();
const cams = devices.filter((d) => d.kind === 'videoinput');
// 热插拔监听
navigator.mediaDevices.addEventListener('devicechange', refreshDevices);

录制（MediaRecorder 输出 Blob，注意容器格式）：

ts
const recorder = new MediaRecorder(stream, { mimeType: 'video/webm;codecs=vp8,opus' });
const chunks: Blob[] = [];
recorder.ondataavailable = (e) => e.data.size && chunks.push(e.data);
recorder.onstop = () => {
  const blob = new Blob(chunks, { type: 'video/webm' });
  URL.createObjectURL(blob);            // 用完记得 revokeObjectURL
};
recorder.start(1000);                   // 每 1s 产出一个分片，便于分片上传

二、WebRTC 核心架构 ​

WebRTC 是浏览器内置的点对点实时音视频 / 数据通道能力，核心是三件事：信令协商（怎么连）→ 网络穿透（连得上）→ 媒体传输（传什么）。

A 端                                         B 端
 │── createOffer ──→ SDP ──信令服务器──→ SDP │
 │←── 信令服务器 ──── SDP ── createAnswer ────│
 │── ICE candidate ──信令服务器──→ candidate ─│
 │←── candidate ──── 信令服务器 ──────────────│
 │═════ RTCPeerConnection 媒体流（P2P）═══════│

关键概念：

  • RTCPeerConnection：会话主体，管理媒体轨道、编解码协商、ICE。
  • SDP（Session Description Protocol）：文本格式的能力描述（编解码、分辨率、加密、候选地址），offer 是发起方、answer 是应答方。
  • ICE（Interactive Connectivity Establishment）：候选地址收集与连通性检查。
  • RTCDataChannel：复用同一 P2P 通道的任意数据通道（可不可靠 / 有序配置）。
ts
const pc = new RTCPeerConnection({
  iceServers: [
    { urls: 'stun:stun.l.google.com:19302' },
    { urls: 'turn:turn.example.com:3478', username: 'u', credential: 'p' },  // TURN 需凭证
  ],
  // iceTransportPolicy: 'relay',   // 强制走 TURN（调试 NAT 穿透时用）
});

// 添加本地媒体
for (const track of localStream.getTracks()) pc.addTrack(track, localStream);

// 远处媒体到达
pc.ontrack = (e) => { remoteVideo.srcObject = e.streams[0]; };

// ICE 候选
pc.onicecandidate = (e) => { if (e.candidate) signal.send('candidate', e.candidate); };

// 连接状态（失败要触发 ICE 重启）
pc.onconnectionstatechange = () => {
  if (pc.connectionState === 'failed') pc.restartIce();
};

三、信令协商：SDP offer / answer ​

WebRTC 规范不定义信令协议——createOffer 产生的 SDP 必须由开发者通过自己的服务器（WS / HTTP / 甚至粘贴文本的「手动信令」）转发。典型流程（pollite/impolite peer 由「完美协商」决定）：

ts
// A 端：发起
async function call(peerId: string) {
  const offer = await pc.createOffer();
  await pc.setLocalDescription(offer);
  signal.send('offer', { to: peerId, sdp: pc.localDescription });
}

// B 端：应答
async function onOffer({ sdp }: { sdp: RTCSessionDescriptionInit }) {
  await pc.setRemoteDescription(sdp);
  const answer = await pc.createAnswer();
  await pc.setLocalDescription(answer);
  signal.send('answer', { sdp: pc.localDescription });
}

// 双向：设置远端描述 + 加入 ICE 候选
signal.on('candidate', ({ candidate }) => pc.addIceCandidate(candidate));

要点：必须严格串行 setLocalDescription / setRemoteDescription，在信令未就绪时直接 addIceCandidate 会抛错，需先缓存在数组里、setRemoteDescription 后再批量加入；协商顺序（谁先 offer）要按「完美协商」规则（双方同时 offer 时由 MSB 比较 role 决定谁是 polite peer）避免 glare（碰撞）。

四、ICE 与 STUN / TURN 穿透 ​

NAT 让外网无法直连内网地址，ICE 负责找到可连通的路径：

类型作用说明
Host本机内网地址局域网内可直接用
Server-reflexive (srflx)经 STUN 得到的公网映射地址锥形 NAT 下可 P2P 直连
Relay经 TURN 中转对称 NAT / 严格防火墙下唯一能连的路径
  • STUN：轻量，仅帮客户端发现自己公网地址，无带宽成本 → 用于获得 srflx 候选。
  • TURN：中继服务器，媒体流量经它转发 → 有带宽成本，是「兜底路径」。

ICE 收集候选（onicecandidate）→ 配对（pairing）→ 连通性检查（STUN binding request），选出优先级最高且可连的 pair。生产必须配 TURN：只配 STUN 时，对称 NAT 用户（企业网络、部分移动网络）连接会失败，表现是「一直 connecting」。TURN 常见方案：coturn、云厂商 RTC 服务。

ts
// 收集候选期间可打印进度（调试穿透问题）
pc.onicegatheringstatechange = () => console.log('ICE gathering:', pc.iceGatheringState);
pc.onicecandidateerror = (e) => console.warn('ICE error', e.url, e.errorCode, e.errorText);

五、RTCDataChannel（数据通道） ​

不需要媒体时可只用 DataChannel 传消息 / 文件（浏览器间 P2P 传文件、协同编辑）：

ts
const dc = pc.createDataChannel('chat', {
  ordered: false,      // 允许乱序（低延迟优先）
  maxRetransmits: 0,   // 0 次重传 = 不可靠，近似 UDP 语义
});
dc.onopen = () => dc.send(JSON.stringify({ type: 'hello' }));
dc.onmessage = (e) => console.log('peer:', e.data);

// 接收方
pc.ondatachannel = (e) => { e.channel.onmessage = (ev) => console.log(ev.data); };

配置权衡：**可靠有序（默认）**适合控制信令；**不可靠（maxRetransmits: 0 / maxPacketLifeTime）**适合实时位置 / 白板笔迹等可容忍丢包的场景。

六、SFU / MCU 架构 ​

多人会议不可能两两 P2P（N 人需 N×(N-1)/2 条连接，上行带宽爆炸），需服务端架构：

架构原理上行带宽（客户端）服务端负载延迟适用
Mesh两两直连N-1 路无低2~4 人小型通话
SFU每人上行 1 路，服务端转发选流1 路中低主流（Zoom/腾讯会议）
MCU服务端混流解码后下发单路1 路高（解码混流）略高弱终端 / 直播式

SFU（Selective Forwarding Unit） 是现代主流：客户端只推一路流，服务端按需把「发言者」的高清流和其他人的低清流转发给各端，配合 simulcast（同时发多档分辨率，服务端选档转发）实现带宽自适应。

七、getStats：质量监控 ​

RTCPeerConnection.getStats() 返回实时统计，是做「网络质量指示灯」与故障定位的关键：

ts
async function collectStats(pc: RTCPeerConnection) {
  const report = await pc.getStats();
  report.forEach((s) => {
    if (s.type === 'inbound-rtp' && s.kind === 'video') {
      console.log('收帧:', s.framesDecoded, '丢包:', s.packetsLost, '抖动:', s.jitter);
      console.log('关键帧请求:', s.keyFramesDecoded);
    }
    if (s.type === 'candidate-pair' && s.state === 'succeeded' && s.nominated) {
      console.log('当前路径 RTT:', s.currentRoundTripTime, '可用带宽:', s.availableOutgoingBitrate);
    }
    if (s.type === 'remote-inbound-rtp') {
      console.log('上行丢包率:', s.fractionLost);
    }
  });
}
setInterval(() => collectStats(pc), 3000);

要点：packetsLost / fractionLost 判断丢包，jitter 判断网络抖动，currentRoundTripTime 判断延迟，nominated 的 candidate-pair 表明当前生效路径（若类型是 relay 说明走了 TURN）。上报这些指标到监控平台，才能在用户投诉前发现「某地区大量走 relay、RTT 飙高」。

八、音视频兼容性 ​

问题场景解法
视频无法内联播放、自动全屏iOS Safari加 playsinline 属性 + webkit-playsinline
自动播放被拦截Chrome / Safarivideo.muted = true + playsinline，或等用户手势后 play()
微信内自动播放失败微信 WebView依赖 WeixinJSBridgeReady 或用户点击触发
编码不支持老设备 / 国产浏览器MediaRecorder.isTypeSupported(mime) 能力探测

采集权限被拒用户拒绝getUserMedia 抛 NotAllowedError，给出引导而不是崩溃
ts
// H.264 能力探测（MediaRecorder）
const candidates = ['video/webm;codecs=vp9,opus', 'video/webm;codecs=vp8,opus', 'video/mp4;codecs=h264,aac'];
const mimeType = candidates.find((m) => MediaRecorder.isTypeSupported(m)) ?? '';
html
<!-- iOS / 微信兼容写法 -->
<video id="remote" autoplay playsinline webkit-playsinline muted></video>

autoplay policy：现代浏览器要求「静音或用户手势」才能自动播放。会议远端视频窗通常静音 + playsinline 可自动播；带声音的播放必须等用户交互（提供「点击播放」蒙层）。

九、HLS / DASH 播放与 flv.js ​

点播 / 直播（非 P2P）走流媒体协议，<video> 不能直接播 .m3u8，需要 MSE（Media Source Extensions）或库：

协议分片格式延迟原生支持常用库
HLS.m3u8 + .ts / .m4s10~30s（LL-HLS 3~5s）iOS Safari 原生hls.js
DASH.mpd + .m4s6~15s否dash.js
HTTP-FLV.flv 流1~3s否flv.js
WebRTC—< 1s是原生
ts
import Hls from 'hls.js';
const video = document.querySelector('video')!;
if (video.canPlayType('application/vnd.apple.mpegurl')) {
  video.src = url;                       // Safari 原生播 HLS
} else if (Hls.isSupported()) {
  const hls = new Hls({ lowLatencyMode: true, maxBufferLength: 10 });
  hls.loadSource(url);
  hls.attachMedia(video);
  hls.on(Hls.Events.ERROR, (_e, data) => { if (data.fatal) hls.recoverMediaError(); });
}

要点：延迟敏感（连麦、监控）优先 WebRTC 或 HTTP-FLV；大规模直播分发优先 HLS/DASH（CDN 友好、延迟可接受）。flv.js 已不再积极维护（作者归档），新项目可评估 mpegts.js。

十、桌面端编解码：ffmpeg / fluent-ffmpeg ​

Electron 桌面端常需本地转码、抽帧、生成封面、拼接录制分片。fluent-ffmpeg 是 ffmpeg 的 Node 包装：

ts
import ffmpeg from 'fluent-ffmpeg';
import ffmpegStatic from 'ffmpeg-static';        // 打包时附带二进制，避免依赖系统安装

ffmpeg.setFfmpegPath(ffmpegStatic as unknown as string);

// WebM 录制分片 → 转 MP4（H.264 + AAC），兼容播放器
ffmpeg('input.webm')
  .outputOptions(['-c:v libx264', '-preset veryfast', '-crf 23', '-c:a aac', '-movflags +faststart'])
  .on('progress', (p) => console.log(`${p.percent}%`))
  .on('end', () => console.log('转码完成'))
  .save('output.mp4');

// 抽帧生成封面
ffmpeg('input.mp4').screenshots({ timestamps: ['00:00:01'], filename: 'cover.png', size: '320x180' });

要点：fluent-ffmpeg 只是包装，系统必须能调用真实的 ffmpeg 可执行文件（ffmpeg-static 可随包分发）；转码是 CPU 密集任务，应在 Electron 的独立子进程 / worker 中跑，否则阻塞渲染主进程；+faststart 把 moov 移到文件头，边下边播更流畅。

十一、常见坑 ​

  1. iOS 不加 playsinline：视频会强制全屏，且无法内联；webkit-playsinline 兼容老版本。
  2. 自动播放被拦：非静音视频无用户手势 play() 会抛 NotAllowedError，需静音或等交互。
  3. 只配 STUN 不配 TURN：对称 NAT 用户永远连不上，必须部署 TURN 兜底。
  4. addIceCandidate 早于 setRemoteDescription：会报错，需缓存候选、设置远端描述后批量补加。
  5. 信令碰撞（glare）：双方同时 offer，需用「完美协商」的角色规则处理，避免状态机错乱。
  6. 忘了 stop() track：挂断后摄像头指示灯不灭、麦克风持续占用，track.stop() 必须显式调用。
  7. URL.createObjectURL 泄漏：录制回放 Blob URL 不 revokeObjectURL 会长期占用内存。
  8. MediaRecorder mimeType 未探测：直接写死 WebM 在部分环境生成失败，应先 isTypeSupported。
  9. 多人会议用 Mesh：4 人以上上行带宽爆炸，必须用 SFU。
  10. 重连后 PC 未重建：网络切换后旧 RTCPeerConnection 已 failed，需 restartIce() 或新建连接重新协商。
  11. getStats 未上报：线上音画质量劣化只能靠用户投诉，必须采集丢包 / RTT / 路径（relay 占比）。
  12. Electron 主进程跑 ffmpeg：同步转码阻塞 UI，必须放子进程。

面试要点 ​

  1. WebRTC 的三大模块是什么？ 答：信令协商（SDP）、网络穿透（ICE + STUN/TURN）、媒体传输（RTCPeerConnection / RTP）。
  2. 为什么必须有 TURN？ 答：STUN 只能让客户端发现自己公网地址，对称 NAT / 严格防火墙下无法直连，只有 TURN 中继能保证连通。
  3. SDP offer/answer 的流向？ 答：发起方 createOffer 并 setLocalDescription，接收方 setRemoteDescription 后 createAnswer，再由信令服务器转发。
  4. WebRTC 有定义信令协议吗？ 答：没有，规范只定义媒体与网络层，信令要开发者自建（常见用 WebSocket）。
  5. 为什么多人会议用 SFU 而不是 Mesh？ 答：Mesh 需 N-1 路上行，带宽随人数平方增长；SFU 每人只上行一路，服务端选流转发，配合 simulcast 做自适应。
  6. iOS 视频不能内联播放怎么解？ 答：加 playsinline / webkit-playsinline，非静音还需用户手势触发播放。
  7. 自动播放策略怎么绕过？ 答：静音（muted）+ playsinline 可自动播；带声音必须等用户交互，或用 WeixinJSBridgeReady。
  8. 怎么监控音视频质量？ 答：getStats() 取 packetsLost、jitter、currentRoundTripTime、nominated candidate-pair 类型（relay 占比），定时上报监控。
  9. HLS / FLV / WebRTC 怎么选？ 答：大规模直播用 HLS/DASH（CDN 友好、延迟高）；低延迟连麦用 WebRTC；中间态用 HTTP-FLV（1~3s）。
  10. Electron 里转码为什么不能放主进程？ 答：ffmpeg 是 CPU 密集任务，阻塞主进程会卡死 UI，应放子进程 / worker，且需自带 ffmpeg 二进制（ffmpeg-static）。
