实时通信：WebSocket / SSE ​

对应 JD 的「WebSocket / 实时数据 / RESTful 联调」B 级高频项（5 份提及），也是 IM、监控告警、AI 流式输出的底座。本文按「方案选型 → WebSocket 原理与工程化 → SSE 与 Fetch 流 → 前端实时渲染 → 降级与坑」组织，IM 场景的深度工程化见 IM 前端。

一、实时通信方案对比 ​

方案方向协议服务器压力延迟浏览器兼容适用
短轮询客户端拉HTTP极高（空请求多）轮询间隔全兼容极低频、兜底
长轮询客户端拉（挂起）HTTP高（占连接）近实时全兼容老系统兜底
WebSocket双向ws/wss中（长连接）极低IE10+双向实时、IM、协同
SSE服务端推（单向）HTTP低极低除 IE / 老 Edge通知、进度、AI 流式
Fetch Stream服务端推（单向）HTTP低极低现代浏览器AI 流式（可 POST、可带 header）

选型口诀：要双向用 WebSocket；只要服务端推用 SSE；AI 流式要 POST / 自定义头用 Fetch Stream。

短轮询 / 长轮询的差别在于「服务端何时返回」：短轮询按固定间隔反复请求，长轮询则是服务端 hold 住连接直到有数据才返回，返回后客户端立刻再发一次。长轮询在无 WebSocket 时代是主流，代价是每条连接都占用服务端线程 / 文件描述符。

二、WebSocket 原理与握手 ​

WebSocket 复用一个 HTTP 连接完成「升级（Upgrade）」，握手后协议从 HTTP 切换为全双工的帧协议（ws:// 明文 / wss:// TLS）。

http
GET /ws/chat HTTP/1.1
Host: api.example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13
http
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=

Sec-WebSocket-Key 是客户端随机 16 字节 Base64；服务端拼接固定 GUID 258EAFA5-E914-47DA-95CA-C5AB0DC85B11 后做 SHA-1 再 Base64 得到 Sec-WebSocket-Accept，用于确认服务端支持。握手接口无法自定义请求头（浏览器 API 限制），因此鉴权通常走 URL 查询参数或首次连接后的应用层认证消息。

WebSocket 帧类型：text（UTF-8 文本）、binary、ping/pong、close。浏览器 API 不暴露 ping 帧，需应用层自己实现心跳。

ts
const ws = new WebSocket('wss://api.example.com/ws?token=' + encodeURIComponent(token));
ws.binaryType = 'arraybuffer';   // 二进制消息以 ArrayBuffer 交付，便于 protobuf
ws.onopen = () => ws.send(JSON.stringify({ type: 'auth', token }));
ws.onmessage = (e) => handle(typeof e.data === 'string' ? JSON.parse(e.data) : e.data);

三、心跳保活与断线重连 ​

为什么需要心跳：中间代理（Nginx 默认 60s、云负载均衡、运营商 NAT）会主动断开闲置连接，且客户端无法感知「半开连接」（网络已断但 TCP 未报错）。应用层心跳（ping/pong 业务消息）能让双方及时发现死链。

ts
type Status = 'idle' | 'connecting' | 'open' | 'closed';
interface Options { url: string; heartbeat?: number; pongTimeout?: number; maxRetries?: number; }

export function createSocket({ url, heartbeat = 15_000, pongTimeout = 5_000, maxRetries = 8 }: Options) {
  let ws: WebSocket | null = null;
  let status: Status = 'idle';
  let attempt = 0;
  let hbTimer: ReturnType<typeof setInterval> | null = null;
  let pongTimer: ReturnType<typeof setTimeout> | null = null;
  const listeners = new Set<(s: Status) => void>();

  const emit = (s: Status) => { status = s; listeners.forEach((f) => f(s)); };

  const startHeartbeat = () => {
    stopHeartbeat();
    hbTimer = setInterval(() => {
      if (ws?.readyState !== WebSocket.OPEN) return;
      ws.send(JSON.stringify({ type: 'ping', ts: Date.now() }));
      // 等 pong；超时视为死链，主动关闭触发重连
      pongTimer = setTimeout(() => ws?.close(4000, 'pong timeout'), pongTimeout);
    }, heartbeat);
  };
  const stopHeartbeat = () => {
    if (hbTimer) clearInterval(hbTimer);
    if (pongTimer) clearTimeout(pongTimer);
    hbTimer = pongTimer = null;
  };

  const connect = () => {
    if (status === 'connecting' || status === 'open') return;
    emit('connecting');
    ws = new WebSocket(url);
    ws.onopen = () => { attempt = 0; emit('open'); startHeartbeat(); };
    ws.onmessage = (e) => {
      const msg = JSON.parse(e.data);
      if (msg.type === 'pong') { if (pongTimer) clearTimeout(pongTimer); return; }
      dispatch(msg);
    };
    ws.onclose = () => { stopHeartbeat(); emit('closed'); scheduleReconnect(); };
    ws.onerror = () => ws?.close();
  };

  const scheduleReconnect = () => {
    if (attempt >= maxRetries) return;          // 超限转人工/降级
    const delay = Math.min(30_000, 1000 * 2 ** attempt) + Math.random() * 1000;  // 指数退避 + 抖动
    attempt++;
    setTimeout(connect, delay);
  };

  return { connect, get status() { return status; }, onStatus: (f: (s: Status) => void) => (listeners.add(f), () => listeners.delete(f)) };
  function dispatch(_: unknown) { /* 交给消息分发器 */ }
}

要点：心跳间隔要小于代理 idle 超时（代理 60s → 心跳 15~30s）；指数退避 + 抖动避免服务端重启时客户端同时涌回（惊群）；重连成功后要重新鉴权并补拉离线消息；attempt 在上限内拨打，超限进入降级（提示用户或退化为轮询）。

四、消息协议设计 ​

统一定义信封，让「业务消息」与「心跳 / 系统消息」在一处分流：

ts
type WsMessage =
  | { type: 'ping' }                         // 心跳
  | { type: 'pong' }
  | { type: 'auth'; token: string }
  | { type: 'event'; topic: string; seq: number; payload: unknown }  // 业务事件
  | { type: 'ack'; seq: number };           // 服务端确认

设计要点：

  • 带 seq（服务端或客户端递增序号）：接收端按 seq 排序、按 seq 去重（seq <= lastSeq 直接丢弃），解决乱序与重复投递。
  • 请求-响应配对：客户端发 { type:'req', id }，服务端回 { type:'res', id }，前端用 Map 按 id 挂起 Promise。
  • 二进制优先 protobuf：高频小消息（行情、位置）用 protobuf 比 JSON 省 30%~50% 体积，但调试成本高，通常 JSON 起步、量大再换。
  • 兼容性：消息里带 version，新旧客户端共存时按版本分支。

五、ws 原生 vs socket.io ​

维度原生 WebSocketsocket.io
协议标准 ws私有协议（含引擎层）
降级无自动降级到长轮询
重连需手写内置（reconnection 系列配置）
房间 / 广播需服务端自建内置 rooms / emit
命名空间无有（/chat、/admin）
体积0约 15KB（gzip）
互通任何后端必须 socket.io 服务端

结论：服务端是标准 ws（如 Go/Java 网关）用原生 WebSocket；Node 服务且团队要开箱即用的重连 / 房间 / 命名空间用 socket.io。注意 socket.io 不是 WebSocket 超集，二者二进制协议不互通，混用会握手失败。

六、SSE 原理与 EventSource ​

SSE（Server-Sent Events）是基于纯 HTTP 的单向服务端推送：响应 Content-Type: text/event-stream，连接保持不关闭，服务端按 data: 行持续写出。

http
HTTP/1.1 200 OK
Content-Type: text/event-stream; charset=utf-8
Cache-Control: no-cache
Connection: keep-alive

id: 1
event: progress
data: {"percent": 30}

id: 2
data: {"percent": 60}

: 这是一行注释，可作心跳保活
ts
const es = new EventSource('/api/task/progress');
es.addEventListener('progress', (e) => {
  const { percent } = JSON.parse((e as MessageEvent).data);
  render(percent);
});
es.onerror = (e) => {
  // EventSource 默认自动重连（约 3s）；也可手动控制
  if (es.readyState === EventSource.CLOSED) es.close();
};
// 手动关闭
// es.close();

SSE 特性：自动重连（浏览器内置，重连时带 Last-Event-ID 头，服务端据此续推 id 之后的增量）；单向（只能服务端 → 客户端）；文本协议；受浏览器「每域 6 连接」限制（HTTP/1.1 下，大量 SSE 会占满连接）；EventSource 不能自定义 header（鉴权只能走 URL 或 Cookie）。

七、Fetch Stream：带 header / POST 的流式读取 ​

EventSource 的致命限制是「不能带自定义头、不能 POST」。用 fetch + ReadableStream 可完全控制请求，这也是 AI 流式（ChatGPT 类）的标准做法：

ts
export async function streamPost<T>(
  url: string,
  body: unknown,
  onChunk: (chunk: string) => void,
  signal?: AbortSignal,
): Promise<void> {
  const res = await fetch(url, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json', Authorization: `Bearer ${token}` },
    body: JSON.stringify(body),
    signal,
  });
  if (!res.ok || !res.body) throw new Error(`stream failed: ${res.status}`);

  const reader = res.body.getReader();
  const decoder = new TextDecoder('utf-8');
  let buffer = '';                       // 处理「一个 chunk 被切断成半行」的边界

  while (true) {
    const { done, value } = await reader.read();
    if (done) break;
    buffer += decoder.decode(value, { stream: true });  // stream:true 保留不完整多字节字符
    const lines = buffer.split('\n');
    buffer = lines.pop() ?? '';          // 最后一段可能不完整，留到下一轮
    for (const line of lines) {
      if (!line.startsWith('data:')) continue;
      const data = line.slice(5).trim();
      if (data === '[DONE]') return;
      onChunk(data);
    }
  }
}

要点：TextDecoder 必须传 { stream: true }，否则跨 chunk 的多字节 UTF-8 字符（中文）会被解码成乱码；必须保留 buffer 处理半行，服务端按帧推送时 chunk 边界与行边界不一致；reader.read() 的 done 与用户 AbortController 取消都要处理；还要考虑 SSE 的 event: / id: 行与 data: 行的组合解析。

八、SSE vs WebSocket 选型 ​

维度SSEWebSocket
方向单向（服务端 → 客户端）双向
协议HTTP（走 HTTP/2 可多路复用）独立协议
鉴权只能 URL / Cookie（EventSource）URL / 首帧消息
自动重连浏览器内置 + Last-Event-ID需手写
二进制不支持（仅文本）支持
代理友好好（普通 HTTP）需配 Upgrade
客户端上行需另开接口同连接
典型通知、进度、AI 流式IM、实时协作、行情

结论：只需服务端推、且要简单可靠 → SSE；需要双向高频交互 → WebSocket。AI 流式场景常「SSE 语义 + fetch 实现」（即第七节写法），兼顾 POST / header 与流式。

九、实时数据展示的前端处理 ​

实时消息（尤其行情、IoT 点位）以毫秒级到来，直接 setState 会打爆渲染帧。三招合并：

  • 节流 / 合并（batching）：把窗口内的多条消息合并为一次更新，用 requestAnimationFrame 或固定 100ms 窗口。
ts
const pending = new Map<string, Quote>();
let scheduled = false;
function onQuote(q: Quote) {
  pending.set(q.symbol, q);
  if (scheduled) return;
  scheduled = true;
  requestAnimationFrame(() => {   // 每帧最多刷一次，天然对齐 60fps
    scheduled = false;
    const batch = [...pending.values()];
    pending.clear();
    store.batchUpdate(batch);
  });
}
  • 增量渲染：只更新变化的行，而不是整表重渲染（虚拟列表 + 按 key 局部更新）。
  • 背压（backpressure）：处理速度跟不上时丢「过时快照」（同一 key 只保留最新值），而非排队累积。

十、降级策略 ​

WebSocket 可用？
  ├─ 是 → 正常双向实时
  └─ 否（握手失败 / 连续重连超限）
        ├─ 支持 SSE → 只读数据走 SSE 推送
        └─ 都不支持 → 退化长轮询（间隔 5~10s）

降级要可观测：上报当前通道类型与降级原因（ws / sse / polling），否则线上静默退化无人知晓。服务端能力探测可在登录接口一次性返回「支持的通道列表」，前端按序尝试。

十一、常见坑 ​

  1. 代理 idle 超时断开：Nginx 默认 proxy_read_timeout 60s，心跳间隔必须更短，或显式调大到 120s+。
  2. 无法感知半开连接：网络切换（WiFi→4G）后 TCP 未报错但消息已丢，必须靠应用层心跳发现的 pong 超时。
  3. iOS 后台断连：Safari 切后台会冻结标签页，WebSocket 被系统断开；回到前台需立即重连 + 补拉离线消息。
  4. 消息乱序 / 重复：移动网络重连后旧消息可能重投，靠 seq 去重与排序兜底。
  5. TextDecoder 未开 stream：中文流式输出在 chunk 边界乱码，这是 AI 流式最常见的 bug。
  6. EventSource 打满连接：HTTP/1.1 每域 6 连接，多个 SSE 会饿死普通请求；尽量用 HTTP/2 或合并通道。
  7. 重连不重新鉴权：重连后旧 token 已过期，服务端拒绝后续消息，表现为「连上了但收不到数据」。
  8. 重连风暴：无退避抖动，服务端重启瞬间被全量客户端同时冲击。
  9. onmessage 里同步重活：解析大 JSON + 渲染阻塞主线程，应下沉到 Worker 或分批。
  10. 只连不监控：连接状态、重连次数、消息延迟指标缺失，线上问题无法定位。

面试要点 ​

  1. WebSocket 握手怎么完成？ 答：用 HTTP Upgrade: websocket 请求，服务端回 101 Switching Protocols，之后复用一个 TCP 连接走全双工帧协议。
  2. WebSocket 为什么必须心跳？ 答：中间代理会断闲置连接，且 TCP 无法感知半开连接，只有应用层 ping/pong（含 pong 超时）才能及时发现死链。
  3. 断线重连为什么要退避 + 抖动？ 答：指数退避限制重连频率，抖动打散客户端避免服务端重启时的重连惊群。
  4. WebSocket 消息乱序重复怎么处理？ 答：消息带 seq，接收端丢弃 seq <= lastSeq 的重复、按 seq 排序渲染。
  5. SSE 与 WebSocket 怎么选？ 答：只需服务端推、要简单可靠和自动重连用 SSE；需要双向高频交互、二进制用 WebSocket。
  6. EventSource 的局限？ 答：不能自定义请求头、只能 GET、仅文本、单向；鉴权只能走 URL 或 Cookie，AI 流式因此改用 fetch。
  7. Fetch 流式读取最容易犯的错？ 答：TextDecoder 忘了 { stream: true } 导致中文乱码，以及没保留 buffer 处理「半行」边界。
  8. 实时数据如何避免打爆渲染？ 答：按帧或固定窗口合并消息、增量渲染、对过时快照做背压丢弃。
  9. iOS 上 WebSocket 为什么老断？ 答：切后台时 Safari 冻结页面并断开连接，需监听 visibilitychange 回前台立即重连 + 补拉离线消息。
  10. 降级策略怎么设计才可靠？ 答：按 WebSocket → SSE → 长轮询逐级降级，并上报当前通道与降级原因，避免静默退化。
