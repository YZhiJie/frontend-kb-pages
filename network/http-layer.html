HTTP 与请求层设计 ​

对应 JD 的「HTTP 协议 / 请求层设计」B 级高频项（5 份提及），也是 WebSocket 实时数据、IM、AI 流式的地基。本文按「协议基础 → 缓存与鉴权 → 企业级三层请求层 → 竞态与并发 → 常见坑」组织。跨域细节见 浏览器跨域机制，长连接与流式见 实时通信。

一、HTTP 报文与常见方法 ​

HTTP 是「请求 / 响应」文本协议，报文 = 起始行 + 头部（Header）+ 空行 + 消息体（Body），请求与响应结构对称。

http
POST /api/v1/orders HTTP/1.1
Host: api.example.com
Content-Type: application/json; charset=utf-8
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
X-Request-Id: 9f2c4a10-7b3e-4c1d-8a55-1e2f3d4c5b6a

{"sku":"A-1001","count":2}

HTTP/1.1 201 Created
Location: /api/v1/orders/10086
X-Request-Id: 9f2c4a10-7b3e-4c1d-8a55-1e2f3d4c5b6a

{"id":10086,"status":"created"}
方法语义安全（Safe）幂等典型用途
GET读取资源是是列表 / 详情查询
HEAD只取响应头是是探测存在性、文件大小
OPTIONS查询支持的方法是是CORS 预检
POST创建 / 非幂等动作否否新建、提交订单
PUT全量替换否是覆盖式更新（须带全字段）
PATCH局部更新否通常否部分字段更新
DELETE删除否是删除资源

要点：GET 不应携带请求体（部分网关会丢弃 body）；PUT 必须幂等，否则改用 POST；POST 的幂等要靠业务层实现（下单用客户端 clientOrderId 去重）。前端生成 X-Request-Id 贯穿日志追踪，但绝不能把幂等键交给前端随机生成后无条件信任——必须由服务端校验并持久化。

二、状态码语义 ​

段含义高频码说明
1xx信息100 / 101101 Switching Protocols（WebSocket 升级）
2xx成功200 / 201 / 204 / 206201 创建成功；204 无内容；206 断点续传区间
3xx重定向301 / 302 / 304 / 307 / 308304 触发协商缓存；307/308 保留方法与 body
4xx客户端错误400 / 401 / 403 / 404 / 429401 未认证 vs 403 无权限；429 限流
5xx服务端错误500 / 502 / 503 / 504502 网关收到无效响应；504 网关超时
  • 301/302 vs 307/308：301/302 可能被浏览器把 POST 降级成 GET；307（临时）/308（永久）严格保留方法与 body，API 域名迁移必须用这两个。
  • 304 Not Modified 由协商缓存触发，不带响应体，省带宽但省不掉一次往返（RTT）；429 通常带 Retry-After 头，重试器应读取该值而非盲目退避。
  • 401 与 403 语义绝不能混：401 表示「没登录 / token 失效」→ 跳登录；403 表示「登录了但没权限」→ 提示无权限。

三、HTTP/1.1 vs HTTP/2 vs HTTP/3 ​

维度HTTP/1.1HTTP/2HTTP/3
传输层TCPTCP + TLSQUIC（UDP）
并发每域 6 个 TCP 连接单连接多路复用单连接多路复用
队头阻塞连接级 + 管道化 HOL消除应用层 HOL，TCP 层 HOL 仍在消除 TCP 层 HOL（各流独立）
头部压缩无HPACKQPACK
握手TCP 1 RTT + TLS通常 2 RTT1 RTT，恢复 0 RTT

队头阻塞（HOL Blocking） 是三代协议的核心区分点：HTTP/1.1 一个连接同一时刻只能处理一个请求；HTTP/2 应用层多路复用，但底层共用一条 TCP 连接，丢包时 TCP 按序重传会阻塞后续所有流；HTTP/3 基于 QUIC 把「流」下沉到传输层，某流丢包只影响该流。头部压缩：HTTP/2 的 HPACK 用静态表（常见头名预置）+ 动态表（本次连接增量编码）压缩，Cookie 等大头收益显著；HTTP/3 的 QPACK 进一步处理乱序流之间的头部引用。

四、缓存机制 ​

浏览器缓存分强缓存（命中不发请求，DevTools 显示 200 (from disk cache)）与协商缓存（发请求但服务端回 304）。

http
# 强缓存：一年内不再询问（适合带 hash 的静态资源）
Cache-Control: public, max-age=31536000, immutable
# HTML 入口：每次协商，避免用户拿到旧引用
Cache-Control: no-cache
ETag: "5f8d3a2b-1c4e"
指令作用
max-age=N相对过期秒数，优先级高于 Expires
s-maxage=N仅共享缓存（CDN）生效，覆盖 max-age
no-cache可缓存，但每次使用前必须协商（不是不缓存）
no-store完全禁止缓存（含本地磁盘）
must-revalidate过期后必须回源验证
immutable有效期内即使用户刷新也不回源
stale-while-revalidate先用过期副本渲染，后台异步刷新

ETag vs Last-Modified：Last-Modified 精度到秒，内容没变但 mtime 变会误判；ETag 是内容指纹（弱 ETag W/"..." 允许语义等价），更精确。优先级：Cache-Control > Expires，ETag 存在时优先于 Last-Modified。

工程实践组合：带 hash 的资源用 max-age=31536000, immutable；HTML / 无 hash 入口用 no-cache；用户私有数据必须 no-store，绝不能被 CDN 缓存。

五、Cookie / Session / Token / JWT 鉴权 ​

方案存储状态跨域撤销适用
Cookie + Session服务端 Session Store有状态需 SameSite=None; Secure即时传统 Web / 同域
Token（不透明串）客户端服务端可查自由即时（黑名单）微服务 / 移动端
JWT客户端（自包含）无状态自由难网关校验、跨服务

JWT 为 header.payload.signature 三段 Base64URL，前两段可解码阅读，签名由服务端密钥生成，前端无法伪造也无法验证：

ts
function decodeJwtPayload(token: string): Record<string, unknown> {   // 只读取 exp，切勿据此做权限判断
  const [, payload] = token.split('.');
  const json = atob(payload.replace(/-/g, '+').replace(/_/g, '/'));    // Base64URL → Base64
  return JSON.parse(decodeURIComponent(escape(json)));
}
const { exp } = decodeJwtPayload(token) as { exp: number };            // exp 为秒级时间戳
const expired = Date.now() / 1000 > exp - 30;                          // 留 30s 提前量

要点：JWT 无法即时撤销，必须短过期（15 分钟）+ Refresh Token 续期；payload 可读，绝不能放密码等敏感信息；Refresh Token 存 HttpOnly Cookie（防 XSS 窃取），Access Token 存内存。

六、CORS 预检与长连接 ​

CORS 预检（Preflight）：非简单请求（方法非 GET/HEAD/POST，或 Content-Type 非三种安全值，或带自定义头）会先发 OPTIONS 探路，服务端回 Access-Control-Allow-* 后才发真实请求。带 Authorization 头的接口必然触发预检，完整规则见 浏览器跨域机制。

Keep-Alive：HTTP/1.1 默认长连接（Connection: keep-alive），复用 TCP 避免重复握手；HTTP/2 天然单连接多路复用。Node 需把 server.keepAliveTimeout（默认 5s）与网关 idle timeout 对齐，否则出现偶发 ECONNRESET。

七、企业级请求层设计：三层架构 ​

成熟请求层应分层，越往下越通用、越往上越业务，依赖单向：

业务代码 → 端点定义层(endpoints) → 信封契约层(envelope) → 传输层(transport) → fetch / axios
每层只能调用下一层：endpoints 单处定义 URL/方法/类型；envelope 统一解包 { code, message, data }；
transport 负责超时 / 取消 / 重试 / 去重 / 错误归类 / token 注入。

7.1 传输层：超时、取消、重试、去重、错误归类 ​

ts
// transport.ts
export type ErrorKind = 'network' | 'timeout' | 'http' | 'business' | 'canceled';
export class ApiError extends Error {
  constructor(public kind: ErrorKind, message: string, public status?: number, public code?: number | string) {
    super(message); this.name = 'ApiError';
  }
}
type ReqOptions = RequestInit & {
  timeout?: number;        // 默认 30s
  retries?: number;        // 仅网络错误 / 5xx / 429 才重试
  retryBaseDelay?: number; // 指数退避基准，默认 300ms
  dedup?: boolean;         // 相同 key 的并发请求只发一次
  signal?: AbortSignal;
};

const inflight = new Map<string, Promise<Response>>();
const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));

function withTimeout(signal: AbortSignal | undefined, ms: number) {
  const ctrl = new AbortController();
  const timer = setTimeout(() => ctrl.abort(new ApiError('timeout', '请求超时')), ms);
  signal?.addEventListener('abort', () => ctrl.abort(signal.reason), { once: true }); // 融合外部取消
  return { signal: ctrl.signal, done: () => clearTimeout(timer) };
}

export async function request<T>(url: string, opts: ReqOptions = {}): Promise<T> {
  const { timeout = 30_000, retries = 0, retryBaseDelay = 300, dedup, ...init } = opts;
  const key = dedup ? `${init.method ?? 'GET'}:${url}:${init.body ?? ''}` : '';
  if (key && inflight.has(key)) return inflight.get(key)!.then((r) => r.clone().json() as Promise<T>);

  const exec = async (): Promise<Response> => {
    let lastErr: unknown;
    for (let attempt = 0; attempt <= retries; attempt++) {
      const { signal, done } = withTimeout(opts.signal, timeout);
      try {
        const res = await fetch(url, { ...init, signal });
        done();
        if (res.status >= 500 || res.status === 429) {  // 只对 5xx / 429 重试，4xx 是业务错
          if (attempt < retries) { await sleep(retryBaseDelay * 2 ** attempt + Math.random() * 100); continue; }
        }
        return res;
      } catch (e) {
        done();
        if ((e as Error).name === 'AbortError') {
          const reason = opts.signal?.reason;
          throw reason instanceof ApiError ? reason : new ApiError('canceled', '请求已取消');
        }
        lastErr = e;
        if (attempt < retries) { await sleep(retryBaseDelay * 2 ** attempt + Math.random() * 100); continue; }
      }
    }
    throw new ApiError('network', (lastErr as Error)?.message ?? '网络异常');
  };

  const p = exec();
  if (key) { inflight.set(key, p); p.finally(() => inflight.delete(key)); }
  return (await p).json() as Promise<T>;   // 交给信封层解包
}

设计要点：超时用 AbortController 而非 Promise.race（后者不中断底层连接，只是提前 reject，连接仍占用）；指数退避 + 抖动（base * 2^attempt + random()）避免重试惊群；只重试网络错误 / 5xx / 429，绝不重试 4xx 和非幂等 POST；去重用 inflight Map 缓存 in-flight Promise；错误归类让各层按 kind 分支（timeout 提示重试、business 弹窗、canceled 静默）。

7.2 信封契约层：统一响应结构 ​

约定所有接口返回同一信封，在一处解包，业务层只面对 data：

ts
export interface Envelope<T> { code: number; message: string; data: T; traceId?: string; }
export async function unwrap<T>(p: Promise<Envelope<T>>): Promise<T> {
  const res = await p;
  if (res.code !== 0) throw new ApiError('business', res.message || `业务错误 ${res.code}`, undefined, res.code);
  return res.data;
}
export const getUser = (id: string) => unwrap(request<Envelope<User>>(`/api/user/${id}`));

关键：HTTP 200 不代表业务成功——后端常把业务错误塞在 code 里，信封层必须把 code !== 0 转成异常，避免业务代码到处 if (res.code === 0)。

7.3 端点定义层：接口单处定义 ​

ts
export const endpoints = {

7.4 拦截器自动注入 token（含并发刷新） ​

ts
import axios from 'axios';
const http = axios.create({ baseURL: '/api', timeout: 30_000 });
let refreshing: Promise<string> | null = null;

http.interceptors.request.use((cfg) => {
  const token = getAccessToken();
  if (token) cfg.headers.Authorization = `Bearer ${token}`;
  return cfg;
});

http.interceptors.response.use(
  (res) => res,
  async (err) => {
    const { config, response } = err;
    if (response?.status === 401 && !config._retried) {
      config._retried = true;
      refreshing ??= refreshToken().finally(() => { refreshing = null; });
      const token = await refreshing;   // 并发 401 共用同一次刷新
      config.headers.Authorization = `Bearer ${token}`;
      return http(config);
    }
    return Promise.reject(err);
  },
);

八、Axios 拦截器 vs fetch 封装 ​

维度Axios原生 fetch
超时timeout 内置需 AbortController 手写
拦截器请求 / 响应拦截器需自行封装
错误判定非 2xx 自动 reject4xx/5xx 也 resolve，需手判 res.ok

取消CancelToken（旧）/ signalsignal
体积约 13KB（gzip）0（内置）

结论：中后台追求效率用 axios 的成熟拦截器链；追求零依赖 / 流式（SSE、AI）用 fetch。axios 两个常见坑：timeout 默认 0（永不超时）；拦截器里 throw 的 error 会丢失原始 config。

九、并发控制与竞态处理 ​

竞态（Race Condition）：快速切换筛选条件时，先发的慢请求后返回、覆盖了正确结果。标准解法是「只认最后一次请求」。

ts
// 方案 A：AbortController 取消上一次（推荐，真取消）
let controller: AbortController | null = null;
async function search(keyword: string) {
  controller?.abort(new ApiError('canceled', '被新请求取代'));
  controller = new AbortController();
  return request<Envelope<Item[]>>(`/api/search?q=${keyword}`, { signal: controller.signal });
}

// 方案 B：latest-ref 序号校验（无法取消时兜底，如 WebSocket 回包）
let seq = 0;
async function searchRef(keyword: string) {
  const mySeq = ++seq;
  const data = await request<Envelope<Item[]>>(`/api/search?q=${keyword}`);
  if (mySeq !== seq) return;    // 已有更新请求发出，丢弃本次结果
  render(data.data);
}

并发池：批量请求时用计数游标限制并发数（如 limit = 6），避免 200 个详情请求瞬时打爆连接——用 Array.from({ length: limit }) 起 N 个 worker，共享 cursor 轮转消费任务数组，最后 await Promise.all 收敛结果。

十、实战要点与常见坑 ​

  1. fetch 的 4xx/5xx 不抛异常：必须判断 res.ok，否则把 500 当成功解析会静默出错。
  2. Promise.race 做超时是假取消：底层连接不中断，高并发下连接数泄漏；用 AbortController。
  3. 重试非幂等接口 / 无抖动退避：POST 下单重试会造成重复订单（需幂等键）；所有客户端按同一节奏重试会形成惊群，必须指数退避 + 抖动。
  4. 信封层漏解包：业务层直接拿 code 判断，语义散落各处，改后端结构就全站炸。
  5. 拦截器 401 刷新未加锁：三个请求同时 401 会触发三次刷新，旧 refresh token 作废导致用户被登出。
  6. no-cache 误当 no-store：前者仍缓存并协商，后者才彻底禁止；登录态响应必须 no-store。
  7. 缓存碰本地时钟 / HTML 做长缓存：客户端改时间会让基于 Expires 的强缓存错乱（一律优先 max-age）；HTML 若做长缓存，发布后旧 HTML 会引用不存在的旧 JS 而白屏。
  8. 301 迁移坑：POST 被降级成 GET 丢 body，API 迁移用 307/308。

面试要点 ​

  1. 强缓存 vs 协商缓存，no-cache vs no-store？ 答：强缓存（Cache-Control/Expires）命中直接读本地不发请求，协商缓存（ETag/Last-Modified）发请求由服务端回 304 决定；no-cache 仍缓存但每次校验，no-store 完全不缓存。
  2. HTTP/2 为什么还有队头阻塞？HTTP/3 如何消除？ 答：HTTP/2 多条流共用一条 TCP 连接，丢包时 TCP 按序重传阻塞后续所有流；HTTP/3 基于 QUIC 把流下沉到传输层，各流独立重传。
  3. 401 和 403 前端该怎么分别处理？ 答：401 是未认证，跳登录或触发 token 刷新；403 是已认证但无权限，提示无权限而非登出。
  4. 请求超时为什么不能用 Promise.race？ 答：它只让 Promise 提前 reject，不中断底层请求，连接仍占用；应用 AbortController 真正取消。
  5. 重试策略要注意什么？ 答：只重试网络错误 / 5xx / 429，绝不重试 4xx 和非幂等 POST；用指数退避 + 抖动避免惊群。
  6. 接口竞态（快速切换筛选）怎么解？ 答：AbortController 取消旧请求，或 latest-ref 序号只认最后一次返回，二者可配合使用。
  7. JWT 有什么坑？ 答：无法即时撤销（需短过期 + 黑名单）、payload 可读不能放敏感信息、前端不得据此做权限判断。
  8. 请求层为什么要分三层？ 答：传输层管通用网络能力、信封层统一解包契约、端点层单处定义接口，依赖单向，改任一层不波及上层业务。
