IM 即时通讯前端 ​

对应 JD 的「IM 即时通讯」C 级差异化项（2 份提及，见 #8 鹏开信息），也是 P0 能力缺口。IM 前端难在一致性与时序：消息不能丢、不能重、不能乱、要能补偿、要多端同步。本文按「能力模型 → 消息模型 → 时序与去重 → 离线补偿 → 渲染优化 → 未读多端 → 长连接工程化 → 常见坑」组织。

一、IM 核心能力 ​

能力说明前端关键点
单聊一对一实时消息会话级连接复用、消息状态机
群聊多人会话成员变更、@提醒、消息合并
消息卡片富媒体 / 结构化消息类型分发渲染、卡片降级
会话列表按最近消息排序未读数、置顶、免打扰、草稿
历史消息上滑加载分页游标分页、列表位置保持
多端同步PC / 移动同时在线已读同步、消息漫游

IM 前端本质是「一个长连接 + 一套消息模型 + 一套本地持久化 + 一套列表渲染」的组合，四个部分各自可替换。

二、消息模型 ​

一条消息在前端是有状态机的对象，字段设计决定后续所有逻辑的正确性：

ts
type MsgStatus = 'sending' | 'sent' | 'failed' | 'read';

interface Message {
  clientMsgId: string;      // 客户端生成（UUID），用于本地乐观显示 + 服务端幂等去重
  serverMsgId?: string;     // 服务端返回的唯一 ID（落库后才有）
  seq?: number;             // 会话内递增序号，服务端分配，用于排序与补拉
  conversationId: string;
  senderId: string;
  type: 'text' | 'image' | 'file' | 'card' | 'system';
  content: unknown;
  status: MsgStatus;
  createdAt: number;        // 服务端时间（不要用客户端时间排序，多端会漂移）
  localCreatedAt: number;   // 本地乐观时间，仅用于发送前显示
}

为什么需要两个 ID：

  • clientMsgId：发送前本地就能生成，用来做乐观 UI（消息立刻上屏标「发送中」），也用作服务端的幂等键（重试不会产生重复消息）。
  • serverMsgId：服务端落库后返回，多端漫游与去重的权威标识。
  • seq：会话内序号，是排序与「增量拉取」的基准（拉 seq > lastSeq 的部分）。

状态机：sending（本地已上屏，未收到 ack）→ sent（收到服务端 ack，携带 serverMsgId/seq）→ failed（超时或服务端拒绝，可点击重发）。重发时复用同一个 clientMsgId，服务端按幂等键去重。

三、消息时序保证与去重 ​

乱序与重复来自三个源头：网络重传、多端并发、重连补拉与实时推送重叠。统一用「序号 + 去重表 + 排序插入」兜底：

ts
class ConversationStore {
  private list: Message[] = [];
  private lastSeq = 0;                          // 已应用的最大序号
  private seen = new Set<string>();             // 幂等键集合（clientMsgId / serverMsgId）

  // 收到任意来源（实时推送 / 补拉 / 自己发送的 ack）的消息，统一入口
  apply(msg: Message) {
    const key = msg.serverMsgId ?? msg.clientMsgId;
    if (this.seen.has(key)) return;             // 去重：同一消息只应用一次
    this.seen.add(key);

    if (msg.clientMsgId && this.isMine(msg)) {
      // 自己的消息：按 clientMsgId 就地更新状态，不新增条目
      const exist = this.list.find((m) => m.clientMsgId === msg.clientMsgId);
      if (exist) { Object.assign(exist, msg); return; }
    }

    if (msg.seq != null) {
      if (msg.seq <= this.lastSeq) return;       // 迟到的历史消息，丢弃（已处理过区间）
      this.lastSeq = msg.seq;
    }
    // 按 seq（服务器时间/序号）插入正确位置；无 seq 的本地消息放末尾
    const idx = this.list.findIndex((m) => (m.seq ?? Infinity) > (msg.seq ?? Infinity));
    idx === -1 ? this.list.push(msg) : this.list.splice(idx, 0, msg);
  }
}

要点：排序只用服务端 createdAt / seq，绝不依赖客户端时间（设备时钟不同步会永久乱序）；去重键优先 serverMsgId，无则 clientMsgId；lastSeq 是增量同步的核心水位，补拉就是「拉 seq > lastSeq」。

四、离线消息补偿 ​

断线期间的增量消息靠「本地水位 + 区间拉取」补齐，而不是重拉整个会话。

ts
// 断线期间的消息补偿流程
async function syncOnReconnect(convId: string, lastSeq: number) {
  // 1) 拉取缺失区间（服务端接口按 seq 增量返回，带上限 N 条）
  let cursor = lastSeq;
  let hasMore = true;
  while (hasMore) {
    const page = await api.pullMessages({ convId, sinceSeq: cursor, limit: 200 });
    page.list.forEach((m) => store.apply(m));
    cursor = page.maxSeq;
    hasMore = page.hasMore;              // 单次不拉全，避免大群灌爆内存
  }
}

// 2) 拉取完成后，再叠加实时推送（推送可能已包含部分区间，靠去重表吸收）
// 3) 本地持久化：把消息落 IndexedDB，冷启动先渲染本地、后台再校准

本地持久化（IndexedDB）：让冷启动秒开、离线可读，并与服务端增量校准：

ts
const db = await openDB('im', 1, {
  upgrade: (d) => {
    const s = d.createObjectStore('messages', { keyPath: 'serverMsgId' });
    s.createIndex('byConvSeq', ['conversationId', 'seq']);   // 按会话 + 序号查询
  },
});
// 冷启动：先读本地按 seq 排序渲染，再向服务端拉 lastSeq 之后的增量
const cached = await db.getAllFromIndex('messages', 'byConvSeq', IDBKeyRange.bound([convId, 0], [convId, 1e12]));

要点：补偿顺序是「先补拉区间、再应用实时推送」（推送可能覆盖部分区间，靠去重表吸收）；分页有上限（大群一次几万条会卡死）；sinceSeq 用本地最大 seq，注意本地无消息时用 0。别用时间戳做增量游标：多端时钟不一致会导致漏消息，seq 是单调的、可靠的。

五、消息渲染优化 ​

消息列表是典型的「双向无限 + 频繁插入」列表，直接全量渲染会卡死。

  • 虚拟列表：只渲染视口内 + 缓冲区的消息。注意 IM 的特殊性——列表是倒序生长的（新消息在底部），上滑加载历史时必须保持滚动位置不跳动。
ts
// 上滑加载历史时保持位置：记录当前 scrollHeight，插入后补偿
async function loadMore() {
  const prevHeight = listEl.scrollHeight;
  const page = await api.pullMessages({ convId, beforeSeq: oldestSeq, limit: 50 });
  page.list.forEach((m) => store.prepend(m));
  await nextTick();
  listEl.scrollTop += listEl.scrollHeight - prevHeight;   // 补偿新增高度，视觉不跳
}
  • 消息气泡 / 富文本：不同 type 分发到不同渲染器（文本 / Markdown / 图片 / 卡片），文本消息要防 XSS（见 Web 安全），Markdown 需 sanitize。
  • 表情与图片视频：表情走雪碧图或 SVG，图片用缩略图 + 懒加载 + loading="lazy"，视频走 音视频 的 playsinline 方案。
  • 增量渲染：新消息只插入增量的 1 条，而非重渲染整个列表；用不可变 key（serverMsgId / clientMsgId）保证 diff 正确。
  • 合并系统消息：连续「xx 加入群聊」合并成一条，减少条目。

六、未读数与红点 ​

未读数有三层：会话列表红点、底部 Tab 红点（跨会话汇总）、具体消息位置。核心是「本地自增 + 服务端校正」：

收到新消息（自己不在当前会话）
  → 会话未读 +1（本地立即反馈）
  → 全局未读 +1
打开会话并停留
  → 上报已读（带 maxSeq / lastReadSeq）→ 服务端清未读
  → 本地未读归 0
多端已读同步
  → 服务端下发「已读至 seq」事件 → 其他端本地归 0

要点：「进入会话」不等于「已读」——要区分「进入可见区」与「停留超过阈值 / 滚动到底」再上报，避免误清红点；未读数必须服务端为准 + 本地乐观，多端并发打开时以服务端的已读水位收敛；@我 的红点独立计数，不能被普通未读覆盖。

七、多端同步与状态一致性 ​

同一账号在 PC / 移动同时在线时，状态必须收敛：

状态同步源前端处理
消息服务端推送（多端各收一份）各端独立 apply，靠 serverMsgId 去重
已读服务端广播收到已读事件 → 本地归零 / 更新对端已读位
草稿本地 + 可选同步按会话存本地，多端是否同步由产品定
撤回 / 删除服务端事件按 targetMsgId 就地改状态
在线状态心跳上报慎用实时状态，协议开销大

关键是把「消息」当作服务端的权威事实，各端只做投影（projection）：本地永远不发明消息内容，只按服务端下发的 seq 序列去重、排序、渲染。这样任一端离线再上线，只要补拉区间就能收敛到同一状态。

八、输入法与富文本 ​

  • 输入法合成（IME）：中文输入过程中 input 事件会夹杂拼音，需用 compositionstart / compositionend 判断，避免「正在输入」提示与 @ 高亮在合成中被误触发。
ts
let composing = false;
input.addEventListener('compositionstart', () => { composing = true; });
input.addEventListener('compositionend', () => { composing = false; });
input.addEventListener('input', () => {
  if (composing) return;               // 合成中不触发发送逻辑 / 联想
  updateSendButton();
});
  • @ 提及：需按光标位置维护「提及区间」，删除时整体删除（不当成普通字符），发送时把用户 ID 一并写入消息元数据而非仅文本。
  • 多行 + Enter 发送：Enter 发送、Shift+Enter 换行（桌面端），移动端默认换行、点发送键发送；输入框用 contenteditable 时要处理粘贴内容净化。
  • 草稿：按键防抖存本地，切换会话或刷新后恢复。

九、WebSocket 长连接在 IM 中的工程化 ​

IM 的长连接不是「连上就行」，而是一组状态治理（详见 实时通信 的心跳与重连）：

  • 登录态生命周期：token 过期前主动重连（重连后重新鉴权），避免「连上了但发不出消息」。
  • 前后台切换：监听 visibilitychange / RN 的 AppState，回前台立即重连 + 补拉。
  • 连接去重：多标签页（PC 多开）共用一个连接（BroadcastChannel / SharedWorker）或各自独立，取决于产品；共用能省服务端连接数但同步逻辑更复杂。
  • 发送队列：断线期间待发消息入本地队列，重连后按序补发，超时标失败。
  • ack 机制：每条消息要求服务端回 ack，前端以 ack 驱动状态机（sending → sent），无 ack 超时（如 10s）标失败可重发。

十、常见坑 ​

  1. 用客户端时间排序：多端时钟漂移导致消息永久乱序，必须用服务端 seq / createdAt。
  2. 重发产生重复消息：重发未复用 clientMsgId，服务端无幂等键，出现两条。
  3. 上滑加载历史列表跳动：未补偿新增 scrollHeight，用户视线被弹走。
  4. 补拉与实时推送重叠未去重：同一消息被应用两次，出现重复气泡。
  5. 未读数与服务端不一致：本地自增但未消费服务端已读事件，多端打开后红点不收敛。
  6. 大群一次拉全量：几万条消息一次性拉取 / 渲染，内存与主线程双双爆。
  7. IME 合成中触发发送：拼音被当成消息内容或误触发 @。
  8. 图片消息未压缩：原图直传导致流量与渲染双重负担，应先上传压缩图 + 原图按需。
  9. 消息渲染未做 XSS 防护：富文本 / Markdown 直接 innerHTML，被注入脚本（见 Web 安全）。
  10. 连接状态只连不监控：重连次数、ack 超时率、补拉耗时无指标，线上问题难定位。
  11. 本地持久化未做版本迁移：IndexedDB 结构变更无 upgrade 分支，老用户读到脏数据。
  12. 已读上报过于频繁：每滚动一条就上报，打爆服务端，应按阈值 / 防抖批量上报。

面试要点 ​

  1. clientMsgId 和 serverMsgId 各有什么用？ 答：前者用于乐观 UI 与服务端幂等去重，后者是落库后的权威 ID，用于多端漫游与去重。
  2. IM 消息乱序怎么根治？ 答：排序只认服务端 seq / 服务端时间，客户端时间因时钟漂移不可信。
  3. 消息重复投递怎么处理？ 答：用幂等键集合（serverMsgId / clientMsgId）去重，同一消息只应用一次。
  4. 离线消息怎么补偿？ 答：以本地 lastSeq 为水位，分页拉 seq > lastSeq 的区间，有限上限，补拉后再应用实时推送。
  5. 为什么增量游标用 seq 而不是时间戳？ 答：seq 单调可靠，时间戳受多端时钟不一致影响会漏消息。
  6. 上滑加载历史为什么列表会跳？怎么解决？ 答：新内容插入使 scrollHeight 变化；记录插入前后高度差并补偿 scrollTop 即可。
  7. 未读数怎么保证多端一致？ 答：本地乐观自增 + 服务端已读水位校正，消费服务端已读事件广播后本地归零。
  8. 「进入会话」就等于已读吗？ 答：不等于，应结合停留时间 / 滚动到底再上报已读，避免误清红点。
  9. 中文输入法下有什么坑？ 答：合成（IME）期间会夹杂拼音，需用 compositionstart/end 判断，避免误触发发送与 @ 高亮。
  10. 发送状态机怎么设计？ 答：sending → sent（收到 ack 带 serverMsgId/seq）→ failed（超时可重发，重发复用同一 clientMsgId）。
  11. 消息列表怎么优化性能？ 答：虚拟列表 + 增量插入 + 不可变 key，图片懒加载与缩略图，系统消息合并。
  12. WebSocket 断线重连在 IM 里要额外做什么？ 答：重连后重新鉴权、补拉离线区间、补发本地发送队列，并监听前后台切换触发重连。
